## 1. 身份模型（已定，取代早前的 3.a/3.b/3.c）

- **一个 IM 会话（私聊 / 群）= 一条 role**。一个 `<gateway root>/.onlyne/config.toml` 里
  每个 **会话** 在 spec 里对应一条 `[[client]]`（`role = "tg-group-7788"`，一把密钥，
  一行 ACL），收件箱就是那条会话。**一条 role 不承载多个会话**——那会让路由无法书写，
  也会让一个收件箱混进几个平台会话。
- **网关是宿主，不是 role**：它读若干 role 的配置与密钥，替每条各持一条 role link。
  这与 `placement = external` 的「一个 DSH 服务多个 role」是同一件事（`AGENTS.md` §11）。
- **平台坐标不进 wire**：`Principal` 保持 role-only，`Principal::Gateway` 不再用于
  会话寻址。gateway id / platform / channel / conversation 住在网关配置的 `[[chat]]`
  行里，按 role 索引。

## 2. 为什么改掉了「一个 client 多会话」

早前的 3.b 让网关成为**一条** `[[client]]`、每个会话是它下面的一个 session。那是反模式：

- **路由写不出来**：`[[route]]`、`allowed_targets`、ledger 的收件人判定都以 role 名为键；
  「role 下的第 N 个会话」没有名字，ACL 也无从表达「这个人能和那条群说话」。
- **收件箱串味**：server 的投递是 per role；一条 role 多会话，则投递行落进哪条会话
  需要 client 侧再判一次，而 server 已按 role 排好队。
- **特例扩散**：会话若走 `Principal::Gateway`，`relay::send`、`check_acl`、store 的
  `ledger_for_role` 都要为 gateway 再开一条分支（见下 §3），而 role 路径一条都不用改。

「一个会话一条 role」把上面全部消掉：入站、出站、ACL、路由、ledger、会话表、TUI/web
都是 role 的既有路径。

## 3. 出站投递：零 server 改动

会话是 role，则出站就是**普通 role 投递**：某 agent 发 `to = { role = "tg-group-7788" }`，
`relay::send` 走 `resolve_target` 的 role 分支，写一行 `to_json = {"role":{"role":"tg-group-7788"}}`，
`ledger_for_role`（`store/server.rs:1375`，按 `json_extract(to_json,'$.role.role')`）自然选中它，
网关**替这条 role** `pull` → ack。**没有 gateway 特例，没有 `$.gateway.*` 收件人判定。**

早前 3B 文档里「必须在 `ledger_for_role` 补 `$.gateway.*`」的那条改动**作废**：
那正是 `Principal::Gateway` 寻址带来的代价，现在不需要了。

`gateway_host.rs` / `render_send` / `pump_outbound` 对这条路径**不再涉及**：它们是旧
adapter-gateway 传输（网关挂在 adapter socket 上）。role-link 宿主取代它。

## 4. 网关宿主：替 N 条 role 各持一条 link

- 网关进程读 `<root>/.onlyne/config.toml`（`[server]` + `[[im.backend]]` + `[[im.push]]`），
  再扫 `<root>/conversations/*/`，每个子目录一条会话：目录名是 role，密钥固定在
  `<dir>/.onlyne/keys/role.key`，坐标在 `<dir>/.onlyne/config.toml` 的 `[[chat]]`。

  ```toml
  # <root>/.onlyne/config.toml
  [server]
  endpoint = "host:17899"
  cert_pin = "sha256/…"

  [[im.backend]]
  gateway = "tg1"
  run = ["onlyne-im-backend-telegram", "--gateway", "tg1"]

  [[im.push]]
  mode = "trigger"
  run = ["/abs/im-in.sh"]
  timeout = "10s"
  ```

  ```toml
  # <root>/conversations/tg-group-7788/.onlyne/config.toml
  [[chat]]
  gateway = "tg1"
  conversation = "-1007788"
  ```

- 每个会话目录建一条到 server 的 role link（TLS + ed25519，复用 `onlyne-net` 的
  握手：读密钥、签名 challenge、被 `AclTable` 认作该 role）。`hello` 用目录名。
- 每条的 `[[chat]]` 把它与平台坐标对齐；后端报来的事件按 `gateway + conversation`
  反查目录，再落到那条 role 的脚本上。
- `[[im.backend]]` 一个 id 一个 `BackendHost` 子进程；同一 id 声明两次、或某条会话的
  `gateway` 无后端可用，都在加载期按名字拒收。
- 复用一处即可：`onlyne-wire` 的 frame codec + `onlyne-net` 的 `handshake`；
  不依赖 `onlyne-client`。

## 5. 触发脚本与出站渲染

> role**（一个网关根一条 role），`chat` 是那条会话的 chat key；脚本把 `chat` 写进投递文本
> 的第一行，收件人自选。下面的「会话 role」是 v2.2 的说法。

事件 JSON 里 `role` 字段是网关反查到的会话 role；脚本按 `role` 组 `send`，收件人自选。

## 6. `generate` 的职责

> 2026-10-13：本节作废，见 `docs/v2.3-CHAT-PROTOCOL.md` §7。`generate` 现在往注册表里
> 加一条会话（slug + 坐标 + 铸出的 `chat.key`），集群半边写的是**网关 role 一条**
> `[[client]]` 与它的双边 ACL，不再一会话一条 role。

新增一个会话要「一条 `[[client]]` + 一把密钥 + 一行 ACL」。`generate` 负责：

- 给会话分配 role 名（如 `tg-group-7788`；目录名即 role）。
- 写密钥文件到 `conversations/<role>/.onlyne/keys/role.key`，并写会话 `config.toml`。
- 向 server root 的 `spec.toml` 追加 `[[client]]`（走 admin socket 的 `SpecApply`），
  并补全 `allowed_targets` 与对端的 `allowed_senders`。

半配状态由 loader 兜底：`validate_owes_targets` 现在读的是与 `acl_edges` 同一条双边规则——
发送方 `allowed_targets` 指名接收方**且**接收方 `allowed_senders` 指名发送方（或是 role 自己的
名字，或发送方是 `_supervisor` 这种单边 reach）。缺任何一半都在加载时按名字拒收并给出补救，
而不是等到 completion 被拒才发现。

## 7. 落地顺序

1. `onlyne-im-backend`：标准帧 + payload + `Backend` trait。**已落地。**
2. `onlyne-im` 宿主：N 条 role link + chat 表 + `trigger` 脚本。
3. 出站投递（普通 role 路径，零 server 改动）。
4. Telegram 后端。
5. `heartbeat` + 其余平台。
