# Reply threads: a conversation is a message list, not a stream

Status: design (2026-10-14). Supersedes the one-message shape §5.1/§5.2 of
`docs/v2.3-CHAT-PROTOCOL.md` left as its degenerate case.

## 0. 一句话

一个会话是**一条消息列表**。回复指向列表里的某一条消息；指向**不是最新那条**时，开一个
分支。今天「一次只见一条」是列表长度为 1 的特例。

## 1. 为什么从「流」改成「列表」

现在一次投递只带一条平台消息（它的 id 记在 `chat.jsonl`，回复默认指它）。这在一问一答
里够用，遇到三件事就不够：

1. **上下文要自带。** 人看群聊看得见上文，模型看不见——它只拿到刚到的这一条。邮件列表
   的做法是每条回复带一段历史， agent 才可能回答「你刚才说的那个」。
2. **参与者要显式。** 群里说话的几个人各有一个平台 id，回复要能指名。现在的 `ImSender`
   只用于日志，不进投递。
3. **回复要能指任意一条。** 顺序回复（回最新那条）只是最常见的一种；指着一条三分钟前的
   消息接着说，是人的日常动作。

## 2. 数据模型

五个概念，全部住在网关侧，core 不变（v2.3 的不变量继续成立）。

```text
Conversation  一个平台会话。身份仍是 chat key。持有若干条 List。
Message       列表里的一条。id 是平台自己的那条 id（event.id / send 的返回值）。
Participant   一个 IM 用户：平台 id + 显示名。属于 Conversation，不属于 List。
List          一条回复链：锚在它的根上。一条消息的 list 是它回复链的根。
Reference     指向任意一条消息的指针，**不是结构**，住在 metadata 里。
```

### 2.1 两种链接，语义不同（2026-10-14 定）

这是整个模型的分界线，也是先前实现错的地方：

| | 归谁 | 作用 | 例子 |
|---|---|---|---|
| **reply**（`Message::parent`） | 结构 | 形成树；决定消息属于哪个 list | 回复某条消息 |
| **ref**（`Reference`） | metadata | 只指向，**不动任何结构** | 引用、表情回应、贴纸来源、编辑的原件、转发 |

把两者混成一个 `parent` 会造成两个错：给一张贴纸开一个分支，以及**顺序回复链每跳都开新
列表**——因为按直接父锚定的话 `m0 → m1 → m2` 会算出三个 list。

**list 由回复链的根决定。** 一条消息的 list 是「沿 parent 走到头那个根」的 id，记录时算
好写进 `Message::list`（ATProto 的 `{root, parent}` 一对，读的时候 O(1)，不必走链）：

- 回复一条**根**消息 → 加入那个根所在 list（ATProto/Nostr 的规则）；
- 回复一条**列表内**的消息 → 留在同一个 list（Slack 的 thread、飞书的回复列表就是这种：
  列表天生一个 fork，列表内可以有向前引用）；
- 回复空 → 自己是根，开新 list。

list 的存储 id：`branch_id(chat_key, root_id) = hex(sha256(...))[0..6]`，确定性、无服务
器、跨重启稳定（`sha256`，不是进程内随机 seed 的 `DefaultHasher`）。

### 2.2 转换层：三个形状，一个模型（2026-10-14 定）

同一棵树，平台携带链接的方式不同，中间得有一层转换（`threadlink.rs`）：

| 形状 | list 是什么 | 回复携带什么 | 平台 |
|---|---|---|---|
| `FlatList` | 一个扁平列表，锚在根上 | 根 id + 列表内的 parent | Slack thread、飞书回复列表 |
| `Chain` | **就是**那条前向指针链本身 | 只有 parent | QQ 的 `msg_id` |
| `Headers` | `In-Reply-To` + `References` 链 | parent + 从根到 parent 的整条链 | 邮件 |
| `Flat` | 无 | 什么都不带，上下文靠正文引用 | 无法表达的渠道 |

入站方向同一个函数（`assign_list`）：平台报了什么就折成什么——报了 list（Slack/飞书）就
听它的，只报了 parent（QQ/Telegram）就取那条消息的 list。

这一层是**纯函数**，输入一条记录好的消息与平台形状，输出该平台要携带的链接。后端因此
不必自己推导 list，也不会各自推错。

## 3. 投递文本的形状

v2.3 只约定了第一行。这里加一个**列表块**，紧跟在第一行之后：

```text
<chat:7f3a9c2e…>
<msg:ROBOT1.0_AdAX>                 ← 回复指向哪条（前缀即可，见 §4）

Participants:
  operator (u_4C9443AA)
Recent messages:
  ROBOT1.0_AdAX  from operator: 测试一下
  0f3a9c2e1b04   from pi: 在的，说
  a19b2c3d4e5f   from operator: 那个接口什么时候好

<模型要读的正文>
```

块是给模型读的**可解析文本**，不是 XML：网关用行前缀切它（`Participants:` / `Recent
messages:`），模型靠行首的 id 认出可回复的候选。窗口有界（缺省 20 条），超出的从最老的
开始丢——一个会话的完整历史在 `chat.jsonl`，投递只带够用的那一段。

**没有这个块的投递就是今天的行为**：第一行仍是唯一硬约定，块整个缺席时 `link.rs` 回落
到「最后一条入站」。这就是「一次一条是特例」的字面意思。

## 4. 唯一前缀匹配（小巧思）

回复要指一条消息，而平台 id 动辄 40 字符以上。规则：

- `<msg:PREFIX>` 里写**前缀**就行，长度不限，能唯一确定即可。
- 网关在**当前列表窗口**里解析：正好一条以它开头 → 就是它；零条或多于一条 → 拒绝，并把
  候选的 id 连同类比写进拒绝理由（模型据此改长一点再试）。
- 全 id 当然合法，它是自己的前缀。

这让 `onlyne_send` 的调用方能写 `<msg:AdAX>`，也让 `<msg:ROBOT1.0_AdAXNfweQ…>` 全写。
前者是给人用的短形式，后者是给人复核的完整形式。

## 5. 各渠道适配（本轮不做）

分支怎么落到平台上，是后端的事，core 与网关都不关心：

| 平台 | 顺序回复 | 跨分支回复 |
|---|---|---|
| Telegram | `reply_to_message_id` | 同上，指向被回复那条 |
| 飞书 | 新消息，正文引用前文 | 同左 |
| QQ | `msg_id`（被动，5 分钟 5 次） | 超窗后主动消息，或落入首个会话消息 |

适配的形状由 `ImPayload` 现有的 `reply_to` 承担（已是平台消息 id），加一个
`branch` 字段供需要它的后端用。**这是下一轮**，且要在真有第二个分支可测之后。

## 6. 落点

| 件 | 在哪 |
|---|---|
| `thread.rs` | 网关：`Participant` / `Message` / `Branch` / `Thread`，前缀解析，窗口读取 |
| `chatlog.rs` | 每行加 `parent` 与 `branch`；列表是它的一次有界读取 |
| `link.rs` | 投递里出现 `<msg:…>` 时解析前缀；解析结果成为 `reply_to` |
| `trigger.rs` | `PushInput` 带 `participants` 与 `recent`（§5.1 的形状） |
| `im-in.sh` | 脚本把这两个数组渲染成 §3 的块 |
| 每个后端 | 决定分支怎么显示（§5） |
| `threadlink.rs` | 转换层：`LinkShape` 四种形状，`outbound` / `assign_list` 两个纯函数 |

### 6.1 记录怎么落盘（2026-10-14 定）

**一个 role 一份主记录，所有渠道聚合**：`<workspace>/.onlyne/history/main.jsonl`，追加
写，按到达顺序。一个 role 服务多个渠道，主记录是它唯一的聚合视图——我们的设计天生
支持，不需要 per-channel 分文件。

**每个分支一个文件**：`history/branches/<branch-id>.jsonl`。读一个分支就是读一个文件，
不用扫主记录过滤。分支 id 由 `thread::branch_id(chat_key, anchor)` 派生，所以拿得到
消息就拿得到文件名，不需要注册表。

**两份记录是链接，不是副本**：分支文件第一行带 `fork_of`（它从主记录哪条叉出去：
`chat_key` + `platform_message`）；每一行都带 `branch`。两边各自都能找到另一边。

不做 SQLite：§9 的所有权表里这份记录不是权威（平台才是，ledger 管投递），给它上数据库
是给非权威副本配权威设施。需要跨会话聚合/并发写那天，那是**新表**的事，走
`AGENTS.md §8` 的 schema 升级路径，而不是替换这份追加写的文本。

### 6.2 分支文件从哪开始

以**第一条被回复的消息**为起始：那条消息本身进新分支文件的首行（带 `fork_of`），它之
后的回复跟着进去。顺序回复不产生新分支——它落在同一个 anchor 上。

## 7. 验收

- core 零改动：`Principal`、两张 schema、`onlyne-client/src/delivery.rs` 的模板一行不动。
- 一条前缀歧义必须**拒绝并列出候选**，不能猜。
- 回复一条不在窗口里的消息（窗口已滚走）拒绝，理由说清并指向 `chat.jsonl`。
- 没有 `<msg:…>` 也没有列表块的投递，行为与 v2.3 逐字节相同。

## 8. 在一个本集群没记录的讨论下被 @（2026-10-14 定）

现实里最常见的一击：机器人在一个**早已存在**的回复列表里被 @，而 Onlyne 此前没记过这个
线程的任何消息——机器人后加的、线程早于网关、或它当时不在群里。飞书、Telegram、Slack
都会遇到；QQ 是简单情况（只有一层 ref，没有 list，所以"没记录的历史"不存在）。

**结构上拿得到，而且不需要历史。** chat key 认的是会话（`chat_id` / `open_id`），线程坐标
认的是消息（`root_id` / `parent_id` / `thread_id`）。于是这条消息就是"一条 parent 指向我们
没见过的 id 的消息"：`thread::assign_list` 的 `(Some(target), None)` 分支把它变成以那条为
锚的新 list，**记录从中间开始**，此后该线程里的每条回复正常入列。和 adopt 同一个性质：
身份由坐标导出，不由历史导出。所以模型一行不用改。

**内容上拿不到就不编。** 只有两个诚实来源：

| 来源 | 给什么 | 代价 |
|---|---|---|
| 平台事件自带 | Telegram 的 `reply_to_message` 带被回复消息**全文**；飞书返回 `root_id`/`parent_id` 但**不带正文**；Slack 只给 `thread_ts`；QQ 只有一层 ref | 免费，深浅各家不同 |
| 平台历史 API | 整个线程 | 要 scope（飞书读群历史需 `im:message.group_msg`，实测无权限答 `230027`），且属**操作员授权** |

第三个来源是"组装一个摘要喂给模型"，§10 明令禁止（组装出来的摘要本身就是上下文污染）。
所以第二来源的落点是 **`[[im.push]]` 触发脚本**：它拿着事件 JSON 与操作员的授权，拉不拉、
拉多深是**操作员策略**（§2：编排不属于 core）。

**两个来源都没有时，把缺口写出来，不要糊过去。** 投递正文里显式声明：

```text
[这条消息落在一个本集群没有记录的讨论里：锚 om_xxx。
 要上文请由 [[im.push]] 脚本拉取（飞书需 im:message.group_msg）。]
```

**承载字段**：`ImEvent.reply`（`ImReply { parent, root, thread }`，`onlyne-im-backend`）。
飞书按官方 schema 填三个 id（只在回复场景返回，所以开新讨论时不带）；缺失即缺字段，老平台
的字节与 v2.3 逐字节相同。
