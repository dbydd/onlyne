# 现场运维报告复核（2026-10-21）

对象：`issues/20261021-cluster-operations-field-report.md` 的五个问题。逐条核对代码与今天的 v2.11 改动，记录结论、故障密度与建议，作为后续拆解的依据。

## 逐条结论

| 问题 | 结论 | 依据 |
|---|---|---|
| 1 同名角色 socket 二义 | 需复现后再定 | 插件 `socket.mjs` 的既有测试要求"多个匹配客户端时拒绝，不从中挑一个"。报告描述的是回退到无人监听的 socket。两条路径不一致，先用一次多义场景确认实际走哪条 |
| 2 离线角色消息阻塞全局 | 机制未核实，现象可信 | 现场有 `queued` 堆积与在线角色 `stalled` 的读数。是否真由排队头阻塞信道调度，需要一次 `watch` 与账本样本对照。若成立，缺的是每角色非阻塞调度与离线死信，不是任何新概念 |
| 3 离线角色 reject 死锁 | 设计缺口，确认 | `crates/onlyne-cli/src/verbs.rs:1080` 明确拒绝非 client 表面：`{verb} requires a role workspace or client socket`。管理员带授权标志时仍无 admin 路径 |
| 4 `send` 不能发 note | 报告有误 | `SendArgs` 已含 `--note`（`verbs.rs:1187`），示例脚本里长期在用。真实问题是习惯性把提醒当 task 发，而 task 占 `max_sessions` 槽位 |
| 5 resume 后 role prose 丢失 | 真实缺口，确认 | `plugins/onlyne-agent-pi/src/pi-surface.mjs:266`：prose 为空时直接返回，日志即现场那行警告。prose 只在首次 welcome 下发，resume 路径没有重新取值 |

## 故障密度

| 模块 | 累计故障 | 共同形状 |
|---|---|---|
| 客户端会话生命周期 `onlyne-client/session/dispatch` | 会话被误判退出、恢复后伪造镜像行、resume 能力恒假、空闲心跳误退休 | "这个会话还活着吗"由五处各自回答 |
| IM 网关 `onlyne-im` | 空拉取忙循环、列表答复前的事件被丢弃、上报取消挂起拉取 | 长轮询与连接读写循环耦合 |
| 插件 `plugins/onlyne-agent-pi` | 子会话冒认父别名、同名角色寻址、resume 丢 prose | 从环境反推身份 |
| CLI 管理面 `onlyne-cli/verbs.rs` | `reject`/`ack` 绑死 client socket | 运维动词与角色进程绑死 |
| 服务端调度 `onlyne-server` | 离线角色消息堆积 | 无每角色隔离与死信 |

## 建议的减法

1. 合并 `exited` 与 `offline`：连接全断只降为 `offline`，`exited` 只由所有者显式声明。v2.11 §6 已列为未决项。这是唯一能一次消掉一整批误判的动作。
2. 授权管理员从 admin socket 清理目标行，不再借活着的兄弟工作区解死锁（问题 3）。
3. 插件寻址读 body 的 `.onlyne.json` 声明，多义时拒绝并打印候选；resume 时重新获取 prose（问题 1、5）。

不拆 crate。crate 边界按意义切得没问题，故障来自"同一个问题有多个所有者"，与目录结构无关。

## 架构反思（走向 v3）

目标初衷是做一个 agent 网络，但由于不断在“谁还活着”、“消息到了哪一步”上补丁，导致系统逐渐具备了操作系统内核式（进程监控、生命周期五维状态机、心跳死信、跨进程镜像与垃圾回收）的过度复杂度。
根本原因：**把“消息到了没有”拆成了多维状态机，并在服务端维护客户端会话的镜像副本。**

### v3 演进方向（大减法）
1. **彻底移除服务端会话镜像表**：服务端只管消息路由与账本（谁欠谁回执）。看板通过账本投影与实时事件流推算，砍掉 `ghost_sweeps`、`stale_working` 以及由此衍生的“误判退出”整条问题链。
2. **状态机降维**：会话状态机从五维降为二维（agent 存活状态、delivery 交付状态），大幅精简 22 个生命周期事件。
3. **单一事实所有者铁律**：严禁在多个地方维护同一状态的同步副本。

### 现阶段（v2 维护期）实施原则
不进行 v3 级别的大重构，聚焦在当前框架下消除显式设计断层与死锁，不引入新实体或复杂机制。

## 集群命名（问题 1 的正解）

联邦里被夹在两个域之间的那个 agent，才是真正尴尬的地方：它的 body 落在成员域，它的工作区却在中心域，而两边的 role 名相同。域与域之间本身是隔离的，不需要给 role 名加前缀。需要命名的是**集群**。

做法：注册文件带上客户端所属集群（`welcome.cluster`，即 spec 的 `[server] name`），pi-onlyne 先按集群比对，再按工作区树比对，两者都对不上才拒绝。role 名、ACL、账本、wire 一律不变。

## 域间协议（v3 备选）

- ANP 1.2：DID 身份、命名、发现、Agent Description、联邦中继，成熟度分层（认证/命名/描述/发现/消息已发布，授权 ANP-05 与支付 ANP-10 仍是草稿）。P1 的 non-goals 明确不做 online status 与副本一致性，正是本地该管的部分。
- A2A 1.0：任务生命周期（8 个 TaskState）、artifact、SSE 与 push 回调、三种绑定、Rust SDK。规范工程更成熟，但它的 Task 状态机正是我们决定在域内拆掉的东西。
- 定位：A2A 做北向 facade（对外表现为一个标准 agent，Task 状态由账本投影），ANP 做身份层（DID 替代跨域共享私钥）；域内继续只保留账本、附着、子进程三张表。两个协议都不进域内传输。

## v3：自己的协议

v3 定义一份自己的 agent 通信协议。ANP 与 A2A 作为参考与互操作对象，不作为规范来源。这两份协议各自解决了一半问题，而我们要的那一半它们都明确不做。

### 从 ANP 取

- 分层边界：域间协议不碰域内传输。
- P1 的 non-goals 值得照抄进自己的规范：history pull、read status、online status、内部副本一致性，四项都声明不做。
- Agent Description 用 `interfaces` 数组声明 MCP / OpenRPC 能力，资源节点据此被发现。
- 跨域身份用 DID 一类可验证标识，替代"同一把私钥抄进两个 spec"。

### 从 A2A 取

- `spec/a2a.proto` 作为唯一权威，文档与 SDK 由它生成；变更走 deprecation 生命周期。
- 长任务的双通道：流式更新与 push 回调分开。
- `Part` / `Artifact` 的产物模型（文本、文件引用、结构化数据，带 media type）。
- Task 状态机只在"对端不透明"这一侧成立，域内不复制。

### 从自己的故障里取

- 存活不进协议。协议只穿透不可否认的事实：签名、地址、能力声明。
- 一个事实一个所有者，禁止维护同步副本。
- 名字必须显式声明，禁止从目录、cwd、进程反推。
- 队列按角色隔离，离线目标不阻塞在线角色的调度。
- 状态维度能降就降；五维降到二维省掉的不只是代码，还有一整类不可测的交互。

### 规范最小集（草案）

身份、信封与幂等键、错误码、能力描述与发现、可选的任务对象（仅边界）、明确写出的 non-goals。域内的账本、附着、子进程三张表不进规范。

### 判据

任何新特性必须先声明它活在哪一层（域内 / 边界）；存活判定只允许来自域内。这两条写进规范正文，作为拒绝扩展的依据。
