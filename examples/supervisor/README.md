# supervisor-demo — Minimal Cluster Operator Agent and Running-Lights Ring

The entire setup uses only Onlyne's own product surface: prose in the spec, workspaces generated by
`generate`, sessions launched by `onlyne-client run`, task dispatch through `send`, and finalization
through the ledger. The demo does not invent any new mechanism.

The cluster contains one operator agent, `_supervisor`, plus a five-member ring `a,b,c,d,e`.
`_supervisor` is the user's cluster operator agent, whose pi process runs in the user's own terminal
(one tab when using Orca). It uses the `onlyne` CLI to dispatch tasks, inspect the ledger, and start
or stop the cluster. The server manages the five roles on the ring: whenever a task arrives, the
client launches a pi session (one tab each when using Orca); the session exits immediately after it
finishes, and its tab closes with it.

## Structure

```
examples/supervisor/
├── README.md                 本文件
├── run.py                    一键脚本（python3 标准库；无 shell 依赖）
└── templates/                进 spec.template_root 的角色模板
    ├── _supervisor/          AGENTS.md + .pi/{settings.json,onlyne.json}
    └── a/ b/ c/ d/ e/        同一份 ring worker 内容
```

The runtime tree is under `/tmp/onlyne-sup` (changeable through `SUP_DEMO_ROOT`). The cluster spec,
server state, workspaces for all six roles, and the record file `lights.txt` are all there. The path
is this short because macOS limits Unix socket paths to 104 bytes, while the worktree itself is
already 93 bytes deep; placing the runtime inside the repository would therefore hit `bind:
Unsupported socket address`. Only the sources (templates and script) remain in the repository.

## Model (D15)

- **A worker role's session lifecycle belongs to its own client**: the server handles routing,
  queueing, the ledger, and ACL; after receiving a task, the client creates a session for it,
  combines plugin report, heartbeat, delivery/recovery, and reconcile facts, and handles
  settlement, retirement, and publishing the exit.
- **The supervisor's process belongs to the user and terminal**: it is an ordinary pi session, and
  the user talks to it in a tab. The server never spawns, recycles, or probes it. Its `[[client]]`
  entry does only two things: register the operator's identity (`admin = true`; the admin socket's
  `send` requires a registered `--from` with the admin bit set), and provide the ACL anchor. `generate`
  also produces its key.
- **Each ring member knows only its immediate predecessor and successor**: `allowed_targets`
  contains the downstream edge and receipt edge, while `allowed_senders` is the corresponding other
  half. `Spec::acl_edges` emits an edge only when both sides recognize it.

## One Command: `run.py`

```bash
cargo build --workspace                            # 前置
python3 examples/supervisor/run.py up              # 起集群，把 supervisor 标签页推到眼前
python3 examples/supervisor/run.py up "再开一轮"    # 自定义交给 supervisor 的第一句话
python3 examples/supervisor/run.py lights          # 脚本直接派一轮环（派活不经模型）
python3 examples/supervisor/run.py send "RING=a,b,c,d,e FILE=/tmp/onlyne-sup/lights.txt K=1 TOTAL=10"
python3 examples/supervisor/run.py status          # roles / sessions / ledger
python3 examples/supervisor/run.py stop            # 收摊
```

Every step performed by `up` is expressed in the product's own terms (idempotent and safe to repeat):

1. `onlyne-server init --root /tmp/onlyne-sup` creates the cluster root and copies `templates/` into
   `/tmp/onlyne-sup/.onlyne/templates` (rendering the script's own path placeholders to actual values
   during the copy).
2. It writes seven `[[client]]` entries into the spec: `_supervisor` with `admin = true`, and `a..e`
   each with its own neighbor table. Keys initially use all-zero, structurally valid placeholders.
3. `onlyne --server-root /tmp/onlyne-sup generate --role _supervisor --role a --role b --role c --role d --role e --out /tmp/onlyne-sup/ws --force` generates
   the six workspaces `/tmp/onlyne-sup/ws/demo/{_supervisor,a,b,c,d,e}` (including real keys and
   template content). The script uses the printed `[[client]]` fragment to **replace** the placeholder
   entry. Putting the keys in the spec is something the script does on the operator's behalf by
   following the precedent of e2e case 9; in a real deployment, a person makes that decision.
4. `onlyne server start` + `onlyne-client run` ×5: the script puts the foreground clients in the
   background (in their own session, with logs at `<ws>/.onlyne/logs/client.log`) and records their
   pids for `stop`.
5. It waits for the five ring roles to come online, opens `_supervisor`'s pi as a tab (`orca terminal
   create`), and uses the `up` argument as the first message. **The script does not wait for the ring
   to finish**: the supervisor dispatches work itself, so `up` prints its instructions and exits.

Each session tab runs the full interactive pi TUI (there is no `--mode rpc` in `session_command`).
Task bodies do not travel through argv: the client renders `{task}` as the task **id**, and the
pi-onlyne plugin injects the body when handling `assign`. As a result, you can directly see the model
read the task, do the work, and report completion in the TUI.

## One Running-Lights Round

The ring is `RING=a,b,c,d,e` and runs for two laps, totaling `5 × 2 = 10` hops. The task text has only
four fields:

```text
RING=a,b,c,d,e FILE=/tmp/onlyne-sup/lights.txt K=1 TOTAL=10
```

When `a` receives K=1, it appends `1:a` to the record file, then uses the pi plugin tool
`onlyne_handoff` to pass the same text to `b` with K increased by one; `b` appends
`2:b` and hands off to `c`… When `e` reaches K=10, it does not forward; it reads the file and uses
`onlyne_complete` to return the file contents. The ledger has one row per task (the root task plus
nine handoff subtasks), and every subtask records its own `parent_task` and `hop`. `handoff` follows
the product's own path: it rereads the parent task's row, attaches the new task beneath `parent_task`,
and sets `hop` to the parent row's value plus one.

The entire chain cold-starts pi `len(RING) * 2` times and adds ten model turns, so completion is
measured in minutes. `run.py`'s default task asks the supervisor to start this round; when the record
file reaches `TOTAL` lines, all the lights are on.

## Watch It Live

The appeal of this demo is that it really moves. Run `run.py up` in an Orca tab and you will see:

1. **Supervisor tab**: its title is `onlyne-supervisor`, and it contains the interactive pi with cwd
   `ws/demo/_supervisor`, so its `AGENTS.md` and the cluster paths are already loaded. It first
   dispatches work with
   `onlyne ... send --from _supervisor --to a --force --yes-i-am-supervisor-not-other-role`, then tracks
   progress with `wc -l lights.txt` and `ledger --task <id>`, and finally reports the file contents
   and ledger rows. This tab does not close when it finishes; **keep talking to it**: `dispatch another
   task`, `inspect the ledger`, or `stop every role except planner`.
2. **Session tabs on the ring**: for each pi-session hop, tabs light up in order:
   `a → b → c → d → e → a → …`. Each tab contains the full pi TUI (an initial session whose body is
   injected by the adapter), so you can see the model read the task, append a line with `echo`, and
   then `handoff` to the next letter; when the session completes, pi exits by itself and Orca reclaims
   the tab. Ten hops mean ten light-on/light-off transitions and form the visual centerpiece of the
   demo. `lights.txt` grows in real time. Every line from
   `onlyne --server-root /tmp/onlyne-sup sessions --json` includes
   `observed.host.orca.pane_key`, the real pane to which that session is bound:
   `pane_key = "<tabId>:<leafId>"`.
3. **TUI**: open another tab and run `target/debug/onlyne-tui --server-root /tmp/onlyne-sup`.
   Page 1 is the role network: all five ring members are online. `_supervisor` does not appear—the
   position is the operator's own, and its `[[client]]` entry only registers the operator's identity,
   with no client process and therefore no box on the graph. The work it dispatches and the queued
   receipts are still visible in the ledger and through `ledger` on page 2. Page 2 is the per-task
   swarm view, with ten rows laid out by hop and their status advancing with each ack. For a single-frame
   reading, use
   `target/debug/onlyne-tui --server-root /tmp/onlyne-sup --once --page 2 --state all`,
   which reveals the `reason` field on settled rows. See the TUI's own help line for key bindings.
4. **Teardown**: `run.py stop` closes the supervisor tab it opened (checking again and reporting an
   error if it could not close it), removes leftover session tabs from Orca, and then sends SIGTERM to
   the five clients and server the script launched.

The two session hosts are two arrangements of the same protocol. The default (on an Orca machine) is
the TUI: tabs are for people to watch, and the adapter injects the task body into the initial session.
For headless use (CI, no Orca), use `export ONLYNE_BACKEND=exec`; sessions become child processes of
the client, and the supervisor also runs as a child process and writes its output to
`/tmp/onlyne-sup/logs/supervisor.log`. To use a script-driven stdin pipe on a machine with tabs, switch
`session_command` back to its rpc form (`pi --mode rpc --session-id {session} --session-dir .pi/sessions -ns`).
The cost is that the tab contains only a JSON stream, but the benefit is that the host can push later
turns over stdin. Both routes deliver task bodies the same way, and neither uses argv as a body channel.

## Run a Single Role on Its Own

After generation, each workspace is an ordinary Onlyne workspace; the template script is responsible
only for arranging them:

```bash
onlyne --server-root /tmp/onlyne-sup roles --json
onlyne --server-root /tmp/onlyne-sup ledger --task <task id>
onlyne --server-root /tmp/onlyne-sup watch --follow     # 看这一单的流转
```

The session list includes pane bindings as recorded:

```bash
onlyne --server-root /tmp/onlyne-sup sessions --json | jq '.data[0].observed'
```

## Dashboard Wiring (Optional)

Point `onlyne-board`'s `serverRoots` at the cluster root (`~/.config/onlyne-sessions/config.json`),
and refreshing gives you the connection view: tabs ∩ live sessions, with only panes connected to this
workspace lit.

## Boundaries

- The demo proves the delegation mechanism: task dispatch, cross-role messages, parent-child handoff
  ledger entries, closed receipt loops, and ledger inspection. What the model answers is outside the
  validation scope.
- Sessions live and die with tasks: one task creates one session, and settlement immediately returns
  its slot. Cold-starting pi takes several seconds per task; this is an inherent cost of the
  architecture.
- `_supervisor`'s entry point is the admin surface (admin socket). This is not an exception special
  to the demo: an operator agent should inherently have access to the local admin socket.
- The head of the ring sends the root task's completion receipt to `_supervisor`; this is the built-in
  upstream channel. In the spec, a ring member's `allowed_targets` contains only ring members, so the
  receipt does not travel over that edge; instead, it uses the task's origin role. When `_supervisor`
  is offline, receipts queue in the ledger (`state = queued`). These queued rows are the operator
  agent's inbox: they are pulled and settled as soon as its client connects; the operator can also use
  `ledger` to inspect them first and then decide how to finish them.
- Windows support is the daemon IPC's concern. `run.py` itself has no shell dependency.

# supervisor-demo — 最小版集群操作 agent 与流水灯环

整套东西只用 Onlyne 自己的产品面：spec 里的 prose、`generate` 出的工作区、
`onlyne-client run` 拉起的会话、`send` 派活、ledger 收尾。演示没有发明新机制。

集群里有一个操作 agent `_supervisor`，外加一条五元环 `a,b,c,d,e`。`_supervisor`
是用户的集群操作 agent，它的 pi 进程跑在用户自己的终端里（在 Orca 里就是一个
标签页）。它用 `onlyne` CLI 派活、看账、开关集群。环上五个角色归服务器管：每来
一个任务，客户端就拉起一个 pi 会话（在 Orca 里各占一个标签页）；会话跑完即退出，
标签页随之关闭。


## 模型（D15）

- **worker 角色的 session 生命周期归各自的 client**：server 负责路由、排队、账本与 ACL；
  client 收到 task 后为它新建 session，组合 plugin report、heartbeat、delivery/recovery 与
  reconcile 事实，负责结清、退役和发布退出。
- **supervisor 的进程归用户和终端**：它就是普通的 pi 会话，用户在标签页里跟它

  登记操作者身份（`admin = true`；admin socket 的 `send` 要求 `--from` 已登记且

- 环上每个成员只认识自己的前后邻居：`allowed_targets` 放下行边和回执边，
  `allowed_senders` 是配套的另一半。`Spec::acl_edges` 只在两边都认这条边时才发射它。

2. 往 spec 里写七条 `[[client]]` 条目：`_supervisor` 带 `admin = true`，

4. `onlyne server start` + `onlyne-client run` ×5：脚本自己把前台 client 放到后台

5. 等环上五个角色上线，把 `_supervisor` 的 pi 开成一个标签页（`orca terminal

`--mode rpc`）。任务正文不走 argv：`{task}` 在客户端渲染成任务 **id**，正文由
pi-onlyne 插件在 `assign` 时注入。所以 TUI 里能直接看见模型读任务、干活、交差。

## 一轮流水灯

环是 `RING=a,b,c,d,e`，跑两圈，共 `5 × 2 = 10` 跳。任务文本只有四个字段：

```text
RING=a,b,c,d,e FILE=/tmp/onlyne-sup/lights.txt K=1 TOTAL=10
```

`a` 收到 K=1：追加 `1:a` 到记录文件，再用 pi 插件工具 `onlyne_handoff` 把同样的文本交给
`b`，K 加一；`b` 追加
`2:b` 交给 `c`……`e` 到了 K=10 不再转发，它读文件、用 `onlyne_complete` 把文件内容
交回。账本里每个任务一行（根任务加九个 handoff 子任务），每个子任务都记着自己的
`parent_task` 和 `hop`。`handoff` 走产品自己的路径：回读父任务行，把新任务挂在
`parent_task` 下，`hop` 取父行加一。

整条链要冷启动 `len(RING) * 2` 次 pi，再加十轮模型回合，跑完按分钟计。`run.py`
的默认任务是让 supervisor 去开这一轮；记录文件长到 `TOTAL` 行，灯就全亮。

## 实地观看

这套演示的看点就是它真的在动。在 Orca 标签页里跑 `run.py up`，你会看到：

1. **supervisor 标签页**：标题是 `onlyne-supervisor`，里面是交互式 pi，cwd 是
   `ws/demo/_supervisor`，所以它的 `AGENTS.md` 和集群路径都已经加载好。它先用
   `onlyne ... send --from _supervisor --to a --force --yes-i-am-supervisor-not-other-role` 派活，再用 `wc -l lights.txt` 和
   `ledger --task <id>` 盯进度，最后把文件内容和账本行报回来。这个标签页跑完不关，
   **继续跟它说话**就行：`再派一单`、`看看账本`、`停掉 planner 之外的角色`。
2. **环上的会话标签页**：每跳一个 pi 会话，按 `a → b → c → d → e → a → …` 挨个亮起。
   标签页里是完整的 pi TUI（初始会话，正文由适配器投进来），能看见模型读任务、用
   `echo` 追加一行、再 `handoff` 给下一个字母；会话完成时 pi 自己退出，Orca 跟着
   回收标签页。十跳就是十次亮灭，这是演示的视觉主体。`lights.txt` 实时变长。
   `onlyne --server-root /tmp/onlyne-sup sessions --json` 的每一行都带
   `observed.host.orca.pane_key`，也就是这条会话绑定的真实 pane：
   `pane_key = "<tabId>:<leafId>"`。
3. **TUI**：另开一个标签页，跑 `target/debug/onlyne-tui --server-root /tmp/onlyne-sup`。
   第 1 页是角色网络：五个环成员在线。`_supervisor` 不上图——它是操作者自己的位置，
   `[[client]]` 条目只登记操作者身份，没有客户端进程，图上不给它盒子；它派出去的活和
   排队的回执，在第 2 页的账本和 `ledger` 里照样看得到。第 2 页是逐任务的 swarm
   视图，十行按 hop 排开，状态跟着 ack 往前走。单帧读取用
   `target/debug/onlyne-tui --server-root /tmp/onlyne-sup --once --page 2 --state all`，
   这样可以看到已结清行的 `reason` 字段。按键看 TUI 自己的帮助行。
4. **收摊**：`run.py stop` 关掉它开的 supervisor 标签页（关完会再查一遍，没关掉就

两种会话载体是同一个协议的两种摆法。默认（Orca 机器上）是 TUI：标签页给人看，
初始会话由适配器注入任务正文。无头场合（CI、没有 Orca）用 `export ONLYNE_BACKEND=exec`，
会话变成客户端自己的子进程，supervisor 也作为子进程把输出写进
`/tmp/onlyne-sup/logs/supervisor.log`。想在带标签页的机器上走脚本驱动的 stdin 管道，
把 `session_command` 换回 rpc 形态即可（`pi --mode rpc --session-id {session} --session-dir .pi/sessions -ns`）。
代价是标签页里只剩 JSON 流，好处是宿主能用 stdin 推后续轮次。两条路的任务正文投递
一样，argv 都不是正文的通道。

## 边界

- 演示证明委派机制：任务下发、跨角色消息、handoff 的父子账、回执闭环、账本可查。
  模型答什么不在验证范围。
- 会话按任务生灭：一单起一个 session，结清即归还槽位。pi 冷启动每单要几秒，这是这套架构的固有成本。
- `_supervisor` 的入口是管理员面（admin socket）。这不是演示的例外：操作 agent
  本来就该拿本机 admin socket 的访问权。
- 环首把根任务的完成回执发给 `_supervisor`，这是内置的上行通道。spec 里环成员的
  `allowed_targets` 只含环内成员，所以回执不走那条边，而是走任务的出发角色。
  `_supervisor` 离线时，回执在账本里排队（`state = queued`）。这批排队行就是操作
  agent 的收件箱：接上客户端就被拉走并结算；操作者也可以先用 `ledger` 看清，再决定
  怎么收尾。
- Windows 适配是 daemon IPC 的事。run.py 本身不依赖 shell。
