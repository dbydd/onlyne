# cancel 不是终态，也不收 host resource

状态：draft，未开 issue。2026-10-15 由 alexandria 集群 supervisor 提交（omp 会话）。
现场来自一次真实运维：一个 supervisor 用 `control cancel` 停了 9 个任务，
client 会话照跑、盘上继续出文件、server 重启后这些行被重投，于是取消被完全撤销。

## 一句话

`control cancel` 与 `repair close|fail` 在语义上结算了「这活我不想要了」，
但既没有停掉承载它的 host resource，也没有把行落到不会被重投的终态；
于是取消的意愿在三个地方同时丢失——进程继续干活、账上仍可复活、运维看不出真相。

## 现场（可复现的判定链）

```bash
# 1. 取消，回执是 ok
onlyne control cancel --task <id> --reason "..." --from _supervisor \
  --force --yes-i-am-supervisor-not-other-role --to scriber
# -> {"ok":true,"data":{"kind":"control","state":"in_flight", ...}}
#    注意：状态仍是 in_flight

# 2. 行仍在途
onlyne ledger --server-root . --role scriber --state in_flight
# -> 该 task 仍列出

# 3. 会话照跑，产物继续落盘
ps -eo pid=,command= | grep ONLYNE_TASK_ID=<id>
# -> fish -l -c env ONLYNE_... ONLYNE_TASK_ID=<id> pi --session-id <id> ...
# -> 被取消的任务取消了半小时后，raw/ 下还在出新目录

# 4. 重启即复活：server 把未结算行重投（这是文档写明的 at-least-once 语义）
#    9 个已取消任务全部复活，占满该 role 的 4 个 session 槽位
```

处置只能落到 onlyne 之外：

```bash
# a. 按 pid 连子树手杀（fish wrapper + pi 子进程，4 组共 8 个进程）
os.kill(pid, SIGTERM)                       # 或者 PGID
# b. 再对每条账 repair close，行才落到不会再被重投的终态
onlyne repair close --server-root . --task <id> --reason "..."
```

判据一句：**cancel 表达了意愿，但既没杀掉 host resource，也没把行落终态；
因为不是终态，一次重启就把它撤销了。**

运维视角的默认假设是「cancel 之后这活死了」。三条子问题各自都可单独成立，
但合起来才是本 draft 的主体：

1. 回执误导。`ok:true` 只说明控制帧被接受，不说明任务被停。
   运维据此认为收工，直到在盘上看见新文件才发现没停。
2. 进程不受 cancel 影响。host resource（Tern block / pane / exec child / zellij session）
   的关闭目前挂在「会话自己结束」上：`cancel` 客户端会去问插件收尾，
   但插件没有义务及时回答（而且插件进程可能已经卡在上游长流上）。
   客户端侧不存在超时后强关的路径。
3. 结算与停进程是两件事，且都不完整。`repair close|fail` 落账不碰进程；
   `control cancel|recycle` 想碰进程但不保证。两边都缺一个「有界宽限后强制」
   的动作。

## 与现有语义的关系

- `docs/operations.md` 已写：`recycle` 与 `cancel` 结束任务，
  一条插件永不应答的话由 client 在三个 heartbeat 间隔后兜底结算。
  这是**结算侧**的兜底；本 draft 要补的是**执行侧**的兜底，
  以及让回执能表达「已请求未确认」。
- `[[hook]]` 的 `delivery_blocked` / `turn_end_without_complete` 已经在
  把异常推到运维面；本 draft 的缺口是同一条路上「运维主动停了但没停掉」这一类
  没有事件、没有故障、没有读数。
- 重启重投本身是正确的 at-least-once 语义，不该改。
  要改的是「已被取消的任务不该在重投集合里」——即取消必须是**终态**。

## 三个可改点（按性价比排序）

### A. cancel 落终态（最小改动，先做这个）

现在取消后行的状态取决于客户端有没有及时回答。让 `control cancel` 在
接受时就把该 task 的 ledger 行推进到终态（语义接近 `repair close`，
但保留 `operator cancel` 这个 reason），并且这个终态不进重启重投集合。

副作用要想清楚：task 可能已经有部分落盘的产物。终态化之后会话若还在跑，
它的 `complete` 会拿 `already_settled`（这条回执已经在 2.2.0 有了），
所以幂等有现成形状；真正要决定的是「结算 vs 让它跑完」哪个是默认。
我倾向**默认结算 + 保留继续跑的选项**，理由是运维下 cancel 的那一刻
通常就是要它停。

### B. host resource 的有界强关

`control` 面加一个 kill 型动词（或在 cancel/recycle 上加一个 `--hard` 变体）：
有界宽限（默认 3 个 heartbeat 间隔，可配）后由 client 直接关掉 host resource
（Tern block retire / pane kill / kill child process group）。
现在运维手杀 pid 是必须，这就是设计缺口。

关键细节：**杀的是进程组**。本次现场里每组是 `fish wrapper + pi 孩子`，
只杀 wrapper 会留下孤儿 pi 继续写盘。Tern/Orca 的 block retire 路径
要覆盖到 exec child 的进程组，不能只发一个 SIGTERM 给直接子进程。

### C. 把存活度接进读数

运维判断「停成功了没有」现在只能靠 `ps`。希望 `sessions --task <id>`
（或者 `control probe`）带回：

- host 的 pid 或 backend handle
- alive 位（host resource 是否还在）
- 该会话对账本行的当前视图

`control probe` 已经存在但不回这些，把它补成运维真正要看的那一格。

## 验收形状（给后续实现用）

以本 draft 的复现链做验收，三件事都要为真：

1. `control cancel --task <id>` 之后，`onlyne ledger --state in_flight` 不再有该 task。
2. 同上命令之后，`ps` 里 `ONLYNE_TASK_ID=<id>` 的会话及其子进程在宽限内消失
   （Tern block 也 retire）。
3. 重启 server 后，`onlyne ledger` 不出现任何 `reason=operator cancel` 之外的重投行；
   被取消的 task 保持 terminal。

另外两条回归，别把好的部分改坏：

- 一次 `cancel` 打在一个**已经自然完成**的 task 上，回 `already_settled`，不报错。
- `cancel` 之后会话若仍递交 `complete`，账本保持第一次的终态与 reason，
  `out_head` 不被覆盖。

## 我这边已做的规避

规则写进了本仓 supervisor 的岗位口径（`.supervisor/AGENTS.md` 规模纪律）：

> **停任务要连会话一起收**。`control cancel|recycle` 只是下单给 client 去停会话，
> 真正在干活的是该会话的 pi 进程；会话不收，agent 继续跑、产物继续落。
> 下单后确认那条会话的 pi 进程已退（`ps -eo pid,command | grep ONLYNE_SESSION_ID`），
> 仍在跑就按 pid 收掉整棵子树。停任务这一步的验收是「进程没了」，
> 不是「命令回了 ok」。

这条能防住同类事故，但它同时是一个信号：**本该由框架保证的事情，
现在压在使用方的纪律上。** 一个 supervisor 忘了这一步，就会重演本 draft 的开头。

## 影响面

- 中到高。这是事故类缺陷，不是体验问题：规模越大（role 多、任务密）越容易撞上，
  而集群的可扩展性恰恰建立在「运维可以随时叫停」上面。
- 与本仓无关地影响所有用 `control` 面做运维的集群。
