# v2.1.0 — the hosting-runtime gap list

`crates/onlyne-adapter/HOSTING-RUNTIME.md` is the specification of record for the
hosting-runtime interface. This document is its v2.1.0 update: what landed since it was
written, what it still gets wrong about the tree, and the change each remaining gap
needs, in the shape a reviewer can apply.

Read at workspace version `2.0.0` (`Cargo.toml:27`).

**Evidence rule.** Every claim below carries a `path:line` I read myself. Nothing here was
executed: no build, no test run, no benchmark. Where a claim is a *reading of a code path*
rather than an observed behaviour it is marked `[INFERENCE]`. No measurement appears in this
document because none was taken.

---

## 1. Status

### 1.1 The direction of the drift

The specification is behind the code, in one direction only: **the tree moved and the
document did not.** Of the four gaps `HOSTING-RUNTIME.md:209-269` names, three are already
closed in the source — G1's sharpest edge, all of G3's vocabulary, and all of G4 — and G2's
decoder has been replaced by the fix that document recommends, in the shape AGENTS.md now
describes. What the document still lists as missing is, in three of four cases, present.

The exceptions run the other way, and they are the two this document is for:

1. The connection carries no name for the process behind it (`AgentMount` has no `runtime`
   field — `crates/onlyne-proto/src/adapter.rs:158-169`), so the document's own discovery
   recipe has nothing to run on.
2. The host has no `suspend` and no `close` to send (`HostOp` has neither —
   `crates/onlyne-proto/src/adapter.rs:440-481`; `SuspendArgs` and `CloseArgs` do not exist
   anywhere under `crates/`).

Two of the document's wire examples do not match the wire, and both are corrected in §7.
Three sibling documents repeat the stale claims: `docs/STATUS.md:78-80` and
`docs/STATUS.md:131-133`, `docs/v2-REMAINING.md:111-129`, and the inventory table inside
`HOSTING-RUNTIME.md:198-208` itself.

## 2. The gaps

### G1 — the connection is no longer a session; what is left is its *name*

**What the spec requires.** One connection serves one `(runtime, role)` pair and
multiplexes that role's sessions over it, keyed by `session_id`
(`HOSTING-RUNTIME.md:36-55`, `:215-226`). `HelloAck`'s `session_id` becomes the connection's
own identity "or is dropped for a runtime mount", and the mount gains `runtime`
(`HOSTING-RUNTIME.md:221-226`).

**What the code does today.** Every routing fact G1 was about is on the wire: the host
names the session in `open` (`adapter.rs:508-510`), the runtime names its conversation back
(`adapter.rs:534-543`), the client keeps both (`transport.rs:608-611`), and `assign` names
the session (`adapter.rs:602-603`, filled at `delivery.rs:675` and `delivery.rs:837`).
Reports can name one too (`ops.rs:105`, `:116-117`). A hosting mount's `welcome` carries no
`session_id` at all, because `mount.session` is absent and the ack copies it
(`serve.rs:163-175`). The document's own §4 heading — "`assign` — one field short" — is
already marked landed (`HOSTING-RUNTIME.md:164-172`).

Two things remain, and neither is the connection shape:

**(a) The SDK hands a hosting runtime one report sender for the whole connection.**
`AgentHandle` owns exactly one `ReportSender` (`onlyne-adapter/src/lib.rs:1305-1320`), whose
counter is one `AtomicU64` (`:935-941`, `:1057-1059`) and whose session binding is a single
`Option<String>` overwritten by `bind_session` (`:962-964`). `report_sender()`
(`:1522-1524`) hands out clones of that one sender. A runtime serving four conversations
needs four independent `(generation, seq)` counters — the spec says so
(`HOSTING-RUNTIME.md:190-194`) — and the SDK gives it one. Note also that
`ReportSender::heartbeat` writes `session_id: String::new()` (`:984-1001`, `:990`), so a
beat built through the SDK names no session at all.

**(b) The mount has no field that names the process.** `AgentMount` is
`#[serde(rename_all = "snake_case", deny_unknown_fields)]` with `role`, `session`,
`task_id`, `pid` (`adapter.rs:158-169`). The document's own `hello` example sends
`{"role": "builder", "runtime": "dsh"}` (`HOSTING-RUNTIME.md:103`), and that frame is
refused today (§G1 failure below).

**The exact failure an external hosting runtime hits.** Two, in order of how early they bite.

*The hello.* `mount.runtime` → `Mount::decode(MountKind::Agent, value)` →
`serde_json::from_value::<AgentMount>` (`adapter.rs:262`) → `deny_unknown_fields` rejects it
→ the custom `HelloArgs` decoder propagates (`adapter.rs:317-320`) → the whole first frame
is undecodable in `serve_plugin` (`serve.rs:136-137`), which returns an error that closes the
connection with a single `tracing::debug!` (`serve.rs:112-114`). No error frame reaches the
runtime: it sees a socket that goes quiet after its `hello` and then closes. `[INFERENCE]`
(read off that path; not executed).

*The idle sweep, which is worse because it is silent and destructive.* `resumable()` asks
whether the connection declared `Capability::Resume` (`dispatch/idle.rs:103-115`).
`suspend_locked` then marks the slot suspended, **drops its transport**, and queues a
backend close (`idle.rs:180-199`, `:189`). The next delivery for that family takes
`Placement::Resume` (`dispatch/scope.rs:120-137`) into `resume_delivery`
(`delivery.rs:254-336`), which calls `inner.backend.spawn(...)` (`delivery.rs:285-295`) —
a no-op for `ExternalBackend`, which starts nothing (`backend/external.rs:52-67`) — and then
arms the reconnect window `slot.dropped_at = (!self_driven()).then_some(now)`
(`delivery.rs:325`), because `SessionBackend::self_driven` defaults to `false`
(`backend/port.rs:30-32`). The hosting runtime was never told, still holds the live
conversation, and the client is now waiting for a mount that will never arrive. `[INFERENCE]`
The document's own `hello` example declares `resume`
(`HOSTING-RUNTIME.md:102`), so a runtime written against the specification walks into this.

**Change.**

1. `AgentMount` gains `runtime` (§3.1 for the diff). It is the process's own name and is
   used for logs, for the G5 gate, and for refusing a second runtime per role.
2. `AgentHandle` gains a second-sender seam, in `crates/onlyne-adapter/src/lib.rs`:

   ```rust
   // beside report_sender(), :1522-1524
   pub fn report_sender_for(&self, generation: u64) -> ReportSender {
       ReportSender::new(self.io.clone(), generation)
   }
   ```

   `ReportSender::new` already takes `(io, generation)` (`:944-951`); the handle does not
   currently expose `io` (`:1306`), so this is the whole change. One sender per session,
   built when `open` is answered. Call sites to update: none in the tree — no consumer in
   `crates/` sends more than one session's reports per handle today.
3. `ReportSender::heartbeat` (`lib.rs:984-1001`) takes the session id as a parameter rather
   than writing `String::new()`, so a hosting runtime's beats are attributable. The host
   tolerates either (the field is `#[serde(default, skip_serializing_if = "String::is_empty")]`,
   `ops.rs:116-117`); a runtime cannot tolerate not knowing.
4. Leave `HelloAck.session_id` alone. It is `Option` (`adapter.rs:352-353`) and a hosting
   mount already leaves it `None` (`serve.rs:163-175`); redefining it would be a wire change
   no hosting runtime needs.

**Compatibility posture.** *An older peer* (a v2.0.0 client receiving a v2.1 runtime) refuses
the `hello` outright, because `deny_unknown_fields` — §3.1 has the exact decode path and the
reason the revision gate in §3.5 is not optional. *A newer peer* must refuse exactly one
thing: a `hello` that carries `mount.runtime` under `protocol: 1` (§3.5). Nothing else in
this gap is breaking; a runtime that omits `runtime` behaves identically to today.

### G2 — the mount is tagged by `kind`: landed, with one stale sentence

**What the spec requires.** `Mount` should stop being `#[serde(untagged)]`
(`HOSTING-RUNTIME.md:228-242`); either `#[serde(tag = "kind", content = "mount")]` or the
payloads matched against the `kind` already sitting beside them in `hello.args`.

**What the code does today.** The second option, exactly as the document recommends it.
`Mount::decode(kind, value)` matches on the kind and hands the payload to the one struct that
owns it (`adapter.rs:254-272`); `HelloArgs` has a hand-written `Deserialize` that reads
`kind` first and leaves `mount` a `Value` until then (`adapter.rs:290-330`); an admin kind
with a payload is refused rather than dropped (`adapter.rs:313-320`). AGENTS.md §8 already
describes this (`AGENTS.md:252-255`). The `untagged` derive survives only for a caller
holding a `Mount` on its own (`adapter.rs:229-238`, and its own doc comment at `:213-228`),
which no `hello` path uses.

**The exact failure.** None on the wire. The residual is one stale sentence:
`crates/onlyne-adapter/PROTOCOL.md:44` still tells a plugin author that "the host matches the
payload's field set against the variants in declaration order", and names the consequence
("adding a field to one payload changes which variant answers"). That is no longer the rule
for any frame that arrives on a socket.

**Change.** No Rust change. One documentation edit, in the same commit as §3.1:
`crates/onlyne-adapter/PROTOCOL.md:44` → say that the payload is decoded by the `kind` beside
it, that each payload still denies unknown fields, and that adding a field to one payload
therefore breaks only that payload's readers. Deleting the standalone `untagged` derive is
**not** in scope (§6).

**Compatibility posture.** Unchanged in both directions. This gap is already closed.

### G3 — the capability set: landed, and the host half is missing

**What the spec requires.** Three capabilities added and a decision about whether `resume`
stays (`HOSTING-RUNTIME.md:244-257`); host-side `suspend` and `close` requests that a runtime
may refuse with `forbidden` (`HOSTING-RUNTIME.md:177-188`).

**What the code does today.** The three capabilities exist, with the documentation the spec
asks for — `resume` is explicitly the spawned-runtime statement (`adapter.rs:74-83`),
`HOSTING` is the three, and `is_hosting` is "any of the three"
(`adapter.rs:141-148`). `HostOp::Open` exists (`adapter.rs:463-478`) with `OpenArgs` and
`OpenedArgs` (`:505-543`). The client stands a transport for a hosting mount
(`serve.rs:667-670`), polls every 250 ms for a session it has staged with no transport
(`serve.rs:18`, `:259`, `:266-271`, `:591-619`), stages a slot with no spawn when a standing
connection exists (`delivery.rs:130-137`), and binds the answer under the host's own name
(`transport.rs:597-616`). AGENTS.md documents the agent-mount behaviour in the table
(`AGENTS.md:259`).

**Three defects remain.**

**G3.1 — there is no host-side `suspend` or `close`.** `HostOp` is
`Welcome | Assign | RenderSend | Probe | Recycle | ConfigGet | Nudge | Open | Bye`
(`adapter.rs:443-481`); `HostOp::name()` has no arm for either (`adapter.rs:483-497`); the
SDK's `Host::host_op` sends anything that is not `open` to `unknown_op`
(`onlyne-adapter/src/lib.rs:1150-1157`); and the client has no call site — the closest shape
to copy is `recycle_plugin` (`dispatch/transport.rs:638-657`). `Capability::Suspend` and
`Capability::Close` are therefore *declared and never consulted* anywhere in `crates/`
outside `adapter.rs` itself.

**G3.2 — the gate is the wrong predicate.** `is_hosting` is true if **any** of the three is
declared (`adapter.rs:144-148`), and that predicate decides two things: whether the mount
becomes a standing transport (`serve.rs:667-670`) and whether a staged session skips the
spawn (`delivery.rs:130`). But the frame actually sent is always `open`
(`serve.rs:591-599`). A runtime that declares only `close` is therefore asked for a session
it never declared it could open. On the Rust SDK the default answer is
`Err(UnknownOp, "open is unsupported")` (`lib.rs:1167-1172`), the client logs "a hosting
runtime refused to open a session; the delivery waits" (`serve.rs:600-606`), and the
delivery sits staged forever. `[INFERENCE]`

**G3.3 — `host_capabilities` never names the new operations.** The `welcome` hardcodes
`vec![Capability::Probe, Capability::Recycle]` (`serve.rs:203`) although the field's own
document says it names "capabilities the host itself will exercise against this plugin"
(`adapter.rs:357-358`). A runtime cannot tell from the `welcome` that this host will ask it
for sessions, only from the fact that it is being asked.

**The exact failure an external hosting runtime hits.** It declares `open` and gets asked,
which works. It declares `close` and gets asked for a session it cannot answer, which stalls
its delivery until the client's reconnect window ends. It declares `suspend`, `close`, or
both — as `HOSTING-RUNTIME.md:180-182` instructs — and gets no `suspend`, no `close`, and no
release it can expect: the client's own idle sweep may suspend the slot unilaterally
(G1(b)) or never touch it (`idle_close = 0`), and the runtime is not on either path.

**Change.** §3.2 has the diff. The call sites:

- `crates/onlyne-proto/src/adapter.rs` — add `SuspendArgs`, `CloseArgs`, the two `HostOp`
  variants, and the two `HostOp::name` arms.
- `crates/onlyne-adapter/src/lib.rs` — two arms in `Host::host_op` (`:1150-1157`) and two
  default hooks beside `open_session` (`:1167-1172`) that answer
  `Err((ErrorCode::Forbidden, …))` rather than `UnknownOp`: a runtime that cannot release a
  session must say so by name, which is what `HOSTING-RUNTIME.md:184-188` asks for.
- `crates/onlyne-client/src/session/dispatch/transport.rs` — `suspend_plugin` and
  `close_plugin` beside `recycle_plugin` (`:638-657`), capability-gated through the
  connection's declared set and sent with `io.request` (**not** `io.notify` — see §3.2).
- `crates/onlyne-client/src/session/dispatch/idle.rs` — `suspend_locked` (`:140-200`) is
  where a release belongs for a hosted slot: ask first, and mark `suspended` on `ok` only.
- `crates/onlyne-client/src/session/dispatch/retire.rs` — `retire_idle_locked` +
  `close_retired` (`:402-414`), `reclaim_exited_resources` (`:567`) and `close_all` (`:466`)
  are the three paths where a hosted session's `close` request belongs.
- `crates/onlyne-client/src/session/adapter_socket/serve.rs:203` — name the new
  capabilities in `host_capabilities`, under the revision gate (§3.5).

**Compatibility posture.** *An older peer* never sees `suspend` or `close`: the client sends
them only to a connection that declared the matching capability, and a v2.0.0 runtime cannot
declare one — `Capability` is a closed enum (`adapter.rs:55-100`) and an unknown variant fails
the whole `hello` decode, which is a refusal rather than a silent drop. *A newer peer* must
refuse a `hello` carrying a capability it does not know, and it already does by decoding.
The one genuinely breaking item here is G3.3, which is why it rides the revision gate.

### G4 — `MountKind::Cluster` and `bridge`: landed, close it

**What the spec requires.** `MountKind::Cluster`, and a decision on `bridge` — rename
`gateway` or add beside it (`HOSTING-RUNTIME.md:259-269`).

**What the code does today.** Both names exist (`adapter.rs:46`, `:50`) and `Mount::decode`
answers `cluster` with `ClusterMount` and both `gateway` and `bridge` with `GatewayMount`
(`adapter.rs:264`, `:265-270`). The naming question is answered: `bridge` is the wire name
for the surface the frozen gateway crates still call a gateway, and the payload did not move
(`adapter.rs:47-50`, `:265-267`). AGENTS.md records it (`AGENTS.md:254-255`).

**The exact failure.** None, and none reachable: an agent mount serves neither kind.

**Change.** None. Delete G4 from the gap list and mark it landed wherever it is restated
(`HOSTING-RUNTIME.md:259-269`, `docs/v2-REMAINING.md:128-129`, `docs/STATUS.md:78-80`).

**Compatibility posture.** Unchanged. This gap was already closed.

### G5 — `runtime` cannot name a hosting runtime (the discovery gap)

**What the spec requires.** Read every `<digest>.json` in the runtime directory, keep the
ones with `kind == "client"`, `placement == "external"`, and `runtime` naming this process,
then dial (`HOSTING-RUNTIME.md:57-90`, and the pseudocode at `:65-71`). The document's own
argument is that this pair is why a hosting runtime needs no configuration file listing the
roles it serves (`HOSTING-RUNTIME.md:80-85`).

**What the code does today.** The registrations carry both fields —
`kind`, `role`, `root`, `pid`, `version`, `runtime`, `placement`
(`onlyne-wire/src/socket.rs:222-249`), and the field's own doc says `runtime` is "the field
external-runtime plugins match to find their clients" (`:235-238`). But the value written is
the **session backend's name**: `AdapterSocket::registration` passes
`self.dispatch.runtime_name()` (`session/adapter_socket/socket.rs:42-49`), which returns
`backend.name()` (`dispatch/outbound.rs:327-329`), and for the external placement that is the
constant `"external"` (`backend/external.rs:36-38`). The client republishes the file when the
drive resolves (`runtime/runloop/config.rs:305`, `:337-346`), which changes the *drive* in
the name, never the process behind it.

**The exact failure an external hosting runtime hits.** The rule "runtime names this process"
matches either every external client or none, never the intended subset. The role is the only
field that is actually unique — one client serves one role (`socket.rs:225`, `serve.rs:708`),
so the dsh-side plugin selects on `placement == "external"` ∧ `role ∈ configured roles`
(`plugins/onlyne-bridge/src/discovery.ts:99-120`, and the module note at `:10-24` explains
why). Two consequences follow, both on the onlyne side:

1. **Nothing holds a role to one runtime.** `stand_transport` appends any hosting mount to
   `inner.standing` (`dispatch/transport.rs:572-582`); it refreshes only the *same*
   connection. A second resident runtime mounting the same role is accepted, and both poll
   `offer_staged` every 250 ms (`serve.rs:266-271`) against the same staged slot, whose
   `staged_hosting_session` filter is only satisfied once a transport exists
   (`dispatch/slots.rs:601-615`). Two runtimes can be asked for one session inside one tick,
   and `hosted_session_ready` writes `transports.insert(...)` last-writer-wins
   (`transport.rs:612-614`). `[INFERENCE]`
2. **An operator cannot tell which process is serving a role.** `onlyne status`-class
   readers see `runtime: "external"` for every role on the machine, and the connection itself
   carries no name either (`AgentMount`, `adapter.rs:158-169`).

**Change.** §3.4 adds the one field that can carry it, and §4 chooses where it lives. In
short: the client publishes `hosting_runtime` from a new workspace-config key beside
`placement` (`onlyne-config/src/client.rs:54-55`), the runtime matches it against its own
name, and the client refuses a second hosting mount for a role it already holds.

**Compatibility posture.** `RegistrationFile` has no `deny_unknown_fields`
(`onlyne-wire/src/socket.rs:221`), so a new field is invisible to an old reader and absent to
a new one — additive in both directions. See §3.4 for the one behaviour change.

## 3. Proposed wire changes

Each item is written as the diff a reviewer would apply. Every mount payload in this
protocol is `deny_unknown_fields` (`adapter.rs:159`, `:173`, `:181`, `:195`); each change
below says what that means for an old peer and a new one.

### 3.1 `AgentMount.runtime` — additive in serde, breaking in deployment

`crates/onlyne-proto/src/adapter.rs:158-169`:

```diff
 #[derive(Debug, Clone, PartialEq, Eq, Serialize, Deserialize, JsonSchema, Default)]
 #[serde(rename_all = "snake_case", deny_unknown_fields)]
 pub struct AgentMount {
     pub role: String,
+    /// The name this runtime answers to.
+    ///
+    /// The connection is the unit of identity and it says nothing about the
+    /// process behind it, so this is where a resident runtime names itself:
+    /// what an operator reads in a log, what a client matches against the
+    /// `hosting_runtime` a registration publishes, and what a second runtime
+    /// mounting the same role is refused for not holding.
+    ///
+    /// Absent from a frame written by a runtime that predates it, which is a
+    /// spawned plugin and never needed one.
+    #[serde(default, skip_serializing_if = "Option::is_none")]
+    pub runtime: Option<String>,
     #[serde(skip_serializing_if = "Option::is_none")]
     pub session: Option<String>,
     #[serde(skip_serializing_if = "Option::is_none")]
     pub task_id: Option<String>,
     #[serde(skip_serializing_if = "Option::is_none")]
     pub pid: Option<u32>,
 }
```

Notes a reviewer needs:

- **No struct-level `default` on `AgentMount`** (`adapter.rs:158-159`), so the field itself
  must carry `#[serde(default)]`. That is exactly what the three sibling `Option` fields do
  (`:162-168`).
- `skip_serializing_if` is what keeps a spawned runtime's `hello` byte-identical to today's;
  the field is absent from the frame, so the standalone untagged `Mount` derive is unaffected
  and `AgentMount` still wins the first-variant position it already holds.
- **An old runtime's frame still decodes** under a new client: absent → `None`.
- **A new runtime's frame does not decode under an old client**: `deny_unknown_fields` →
  `unknown field 'runtime'` at `adapter.rs:262` → the `HelloArgs` decoder fails
  (`:317-320`) → `serve_plugin` fails before the handshake (`serve.rs:136-137`) → the
  connection closes with no error frame (`serve.rs:112-114`). That is the whole reason the
  revision gate in §3.5 exists: the field must not travel on a `protocol: 1` hello.

### 3.2 `HostOp::Suspend` / `HostOp::Close` — additive, and safe behind the capability gate

`crates/onlyne-proto/src/adapter.rs`, beside `OpenArgs` (`:505-529`):

```diff

+/// runtime keeps it.
+#[derive(Debug, Clone, PartialEq, Eq, Serialize, Deserialize, JsonSchema, Default)]
+#[serde(rename_all = "snake_case", default)]
+pub struct SuspendArgs {
+    pub session_id: String,
+    #[serde(default, skip_serializing_if = "String::is_empty")]
+    pub reason: String,
+}
+
+/// `close`: end one session.
+#[derive(Debug, Clone, PartialEq, Eq, Serialize, Deserialize, JsonSchema, Default)]
+#[serde(rename_all = "snake_case", default)]
+pub struct CloseArgs {
+    pub session_id: String,
+    #[serde(default, skip_serializing_if = "String::is_empty")]
+    pub reason: String,
+}
```

and in `HostOp` (`:463-481`), after `Open`:

```diff
     Open(OpenArgs),
+    /// Release one session's slot; the conversation stays with the runtime.
+    Suspend(SuspendArgs),
+    /// End one session.
+    Close(CloseArgs),
     /// The host is going away.
     Bye(ByeNotice),
```

`HostOp::name` gains two arms (`:483-497`). `HostOp` itself carries no
`deny_unknown_fields` (`adapter.rs:441-442`), but an unknown `op` tag is still fatal for the
**whole frame**: `AdapterMsg` is untagged with disjoint `op` vocabularies
(`adapter.rs:712-722`), so a v2.0.0 runtime offered `{"op":"suspend"}` fails `Plugin`,
fails `Host`, fails `Res`, and the reader cannot decode the frame
(`onlyne-adapter/src/lib.rs:450-467`). The connection ends; it is not a refused request.

That is why the client must gate on the declared capability, which it already has in hand
(`serve.rs:228`, `:259`):

```rust
// crates/onlyne-client/src/session/dispatch/transport.rs, beside recycle_plugin (:638-657)
pub async fn suspend_plugin(&self, session_id: &str, reason: &str) -> bool {
    let Some((io, capabilities)) = self.session_transport(session_id) else { return false };
    if !capabilities.contains(&Capability::Suspend) { return false; }
    let answer = io.request(AdapterMsg::Host(HostOp::Suspend(SuspendArgs {
        session_id: session_id.to_string(),
        reason: reason.to_string(),
    }))).await;
    matches!(answer, Ok(body) if body.ok)
}
```

**`io.request`, not `io.notify`.** `HostDispatcher::serve` drops any host-originated frame
without an `id` (`onlyne-adapter/src/lib.rs:1230-1231`), so a notification is never answered
and the client would wait out its request timeout. `open` already gets this right
(`serve.rs:596-598`, against `AdapterIo::request` at `lib.rs:340-373`).

- **An old peer** is never sent these: it cannot have declared the capability, because
  `Capability` is a closed enum and an unknown variant fails the hello decode
  (`adapter.rs:298`, `:317-320`).
- **A newer peer** must refuse a `hello` naming `suspend`/`close` when it does not implement
  them, and it gets that refusal from the decoder for free. The SDK's default hook answers
  `forbidden`, not silence, per `HOSTING-RUNTIME.md:184-188`.

### 3.5 The revision gate

`PROTOCOL_VERSION` is `1` (`crates/onlyne-proto/src/lib.rs:87`) and is compared once, before
the welcome callback (`onlyne-adapter/src/lib.rs:742`), with a `protocol_version` error and a
`bye` as the refusal (`:784-818`). v2.1.0 should:

1. Set `PROTOCOL_VERSION = 2` (`onlyne-proto/src/lib.rs:87`).
2. Replace the equality at `lib.rs:742` with a membership test `{1, 2}`, and carry the
   negotiated revision into `ServerConnection` (`lib.rs:821-826`) so the client's later
   decisions can read it.
3. Under revision 1, the client must: refuse a mount that carries `runtime`
   (`mount_allowed`, `serve.rs:706-712`, returning
   `Err((ErrorCode::Invalid, "mount.runtime needs adapter protocol 2"))`), keep
   `host_capabilities` as it is today (§3.3), and never send `suspend`/`close` — though it
   could not anyway, since a revision-1 runtime cannot declare them.
4. Under revision 2, all of §3.1–§3.4 is live.

This buys one thing that matters more than the version number: a new runtime talking to an
old host gets the `protocol_version` refusal and the `bye` (`:784-818`) instead of a socket
that closes behind its `hello` with no error frame. That is the difference between a
diagnosable deployment fault and a mystery, and it costs one `matches!`.

## 4. The discovery problem

The requirement is that a resident runtime finds *its* clients and no others, with no
operator-maintained role list. Four answers, each with its cost.

**(a) A new registration field.** `RegistrationFile.hosting_runtime` (§3.4), written by the
client from a workspace-config key. *For:* it puts the fact where discovery already looks —
the same file, the same directory scan, the same `list_registrations` seam
(`socket.rs:326-357`) — and the client is the party that knows which socket it published.
*Against:* the operator must name the runtime in two places (the client's `config.toml` and
the runtime's own configuration), and a mismatch is silent in the direction that hurts: the
runtime simply does not dial. *Also against:* it names a runtime the client has never seen,
so it cannot be validated; it is a promise, not a handshake.

**(b) A new mount field.** `AgentMount.runtime` (§3.1), written by the runtime at `hello`.
*For:* it is the only one of the four that binds a claim to the connection that makes it, so
the client can log and record "role `builder` is served by `dsh`" and can refuse a second
runtime (§G5, first failure). *Against:* it cannot drive discovery. The client never dials anyone
(`HOSTING-RUNTIME.md:87-90`), so by the time this field arrives the choice of which clients to
dial has already been made by the runtime. It is a label, not a selector.

**(c) An operator-configured allowlist, on the client.** The workspace `config.toml` lists
the runtimes permitted to serve the role, and the client refuses a `hello` from any other
name at `mount_allowed` (`serve.rs:706-712`, which already has the refusal shape at
`:148-154`). *For:* enforcement rather than discovery — a rogue process cannot take the role.
*Against:* a list is more config to keep in step, and it still leaves the runtime to guess
which sockets to dial, so it does not solve the discovery half on its own.

**(d) Matching on role.** What the dsh-side plugin does today: dial every registration with
`kind == "client"`, `placement == "external"`, and a role on the runtime's own list
(`plugins/onlyne-bridge/src/discovery.ts:99-120`). *For:* zero wire change, works today, and
the role is the one field that is genuinely unique (one client, one role —
`socket.rs:225`, `serve.rs:708`). *Against:* two configurations must agree, the runtime's
list is a list of the things it wants rather than a statement of what it is, and nothing on
the onlyne side stops a second runtime from mounting the same role (§G5, first failure).

**Recommendation: (a) + (b) + the last half of (c), and (d) as the fallback.**

The selection rule the runtime runs becomes three predicates instead of two:

```
kind == "client"
  and placement == "external"
  and role ∈ this runtime's configured roles
  and (hosting_runtime is absent or == this runtime's own name)
```

and the client takes one new action: hold at most one standing transport per role
(`stand_transport`, `dispatch/transport.rs:572-582`), refusing a second hosting mount for a
role it already stands — unless the mount names the same `mount.runtime` (a re-hello, which
today refreshes in place at `:575-581`). That is where (b) earns its place: without a name on
the connection the client cannot tell a re-hello from a second runtime, and would have to
refuse both.

With `hosting_runtime` unset, the rule degrades exactly to (d), which is the dsh side's
current behaviour and needs no code change there. So the ordering is safe: the field ships,
the operator may fill it in, and nothing breaks for anyone who does not.

Not recommended: making `RegistrationFile.runtime` mean the hosting process. It already means
the session backend, and the backend is chosen by `(drive, placement)` at runtime
(`runtime/runloop/config.rs:291-329`, `backend/select.rs:144-173`); overloading it would break
every reader that today reads it as a backend name, for no field that `hosting_runtime` does
not already carry.

## 5. A conformance fixture

The claim "the protocol supports this" should stop being a claim about a document. What
exists today is scenario 19 (`crates/onlyne-testkit/tests/scenarios.rs:2518-2615`) with the
`serve_hosting` script (`:2429-2442`) and the two script steps `mark_mounted` /
`require_opened` (`crates/onlyne-testkit/src/lib.rs:633-660`). It proves one real thing: one
process, one connection, two families, two `open` requests, two sessions, both `Attached`.

It does not prove the rest, and the reasons are specific:

- The fake's beats come from **one** counter for the whole script
  (`onlyne-testkit/src/lib.rs:676`, `:706`, base at `:924`), and `report_ready` names the
  literal `"sim-session"` (`:670-674`) rather than the assigned id. A runtime with one counter
  per connection passes scenario 19 and would fail against a host with a per-session
  watermark.
- Nothing suspends or closes, so the `SuspendArgs` / `CloseArgs` path of §3.2 is unexercised.
- Nothing carries `mount.runtime`, so §3.1's decode is unexercised in both directions.
- Discovery is not reachable from one fake process: it is a second process reading a
  directory.

One fake process is still enough for everything except the directory scan. The fixture should
be `scenario_20_a_hosting_runtime_routes_by_session_and_releases_on_request`, one
`FakeAgent` with `serve_hosting(2)`, asserting in order:

1. **`open` carries the host's name.** The fake's ledger already records every answer
   (`onlyne-testkit/src/lib.rs:408-424`, readable through `opened_sessions()` at `:179-181`).
   Assert two entries, distinct, and equal to the two `session_id`s the ledger's session rows
   carry — proving `hosted_session_ready` binds under the host's key and parks the runtime's
   own name in `backend_ref` (`transport.rs:608-610`).
2. **The second `open` carries the first's `resume_handle`** when the scope is `task`
   (`dispatch/slots.rs:632-645`), and the runtime's answer is what comes back. This is the
   opaque-handle round trip the spec describes at `HOSTING-RUNTIME.md:140-147`.
3. **Per-session counters, interleaved.** Two `ReportSender`s, one per session, each starting
   at `SEQ_BASE`, beats interleaved across both. Every beat must be accepted, which is the
   observable form of "the watermark is per session". To make it fail loudly for a runtime
   that shares one counter, the fake must send session B's beat **below** session A's
   current `seq` — a single shared counter cannot express that, and the host must still take
   it (`accept_report_generation`, `onlyne-adapter/src/lib.rs:1062-1064`).
4. **`suspend` is asked, not assumed.** After the first delivery settles, assert the client
   sent `HostOp::Suspend` for that `session_id` and that the slot's row reads `idle` with the
   transport gone; assert the **same connection** then receives the second family's `assign`
   (`serve.rs:266-271` keeps polling the standing transport).
5. **A refusal is honoured.** A second script answers `suspend` with
   `Err((ErrorCode::Forbidden, "…"))` (`onlyne-adapter/src/lib.rs:1167-1172` is the shape);
   assert the client leaves the session attached and does not mark it suspended. This is the
   "refusal, never silence" rule of `HOSTING-RUNTIME.md:184-188`, and it is the one that
   currently has no implementation to test.
6. **The gate is per capability.** A third script declaring `open` alone is never sent
   `suspend` or `close`; a fourth declaring `close` alone is never sent `open` (G3.2). Both
   are assertions over the frames the fake read, not over state.
7. **`mount.runtime` round trip.** The fake's `hello` carries `mount.runtime` under
   `protocol: 2`; assert the client accepts it and that the connection log line names it. The
   negative case — `protocol: 1` with `mount.runtime` — asserts the `invalid` refusal from
   §3.5, which is the one behaviour in this document that would otherwise ship untested.

Discovery gets the cheap substitute, not a fake process: a table test over
`list_registrations`-shaped input (the reader is `onlyne-wire/src/socket.rs:326-357`) feeding
the selection rule from §4, asserting that a `hosting_runtime` naming another runtime is
skipped, an absent one is not, and a `placement` other than `external` is not.

## 6. Out of scope

- **G4, `MountKind::Cluster` and `bridge`.** Landed (`adapter.rs:46`, `:50`, `:265-270`),
  and neither kind is reachable from an agent mount. The document's rename question is already
  answered in the code and in `AGENTS.md:254-255`. Close the gap; change nothing.
- **Deleting the standalone `#[serde(untagged)]` derive on `Mount`**
  (`adapter.rs:229-238`). No frame arrives through it — `HelloArgs` decodes kind-first
  (`:306-330`) — so it is a cleanup with no behavioural content, and it belongs in its own
  commit rather than in a protocol change.
- **Renaming `resume`.** `HOSTING-RUNTIME.md:249-254` asks for a decision. Decision: keep it,
  and keep hosting runtimes from declaring it. Its own doc comment already says it is the
  spawned-runtime statement (`adapter.rs:74-83`), and G1(b) is the reason a hosting runtime
  must not claim it: declaring `resume` is what makes `resumable()` true
  (`dispatch/idle.rs:103-115`) and the sweep take the transport away. Fixing `suspend` (§3.2)
  is the fix; renaming `resume` would be a second, unnecessary one.
- **Redefining `HelloAck.session_id` as connection identity.**
  `HOSTING-RUNTIME.md:221-222` offers it. Not needed: the field is `Option`
  (`adapter.rs:352-353`) and a hosting mount already leaves it `None` (`serve.rs:163-175`).
- **The gateway / bridge / tools surfaces.** `deliver`, `register_channel`, `health`,
  `typing`, `render_send` (`adapter.rs:394-400`, `:448-449`), the tools token's one-session
  binding (`dispatch/state.rs:509-535`), and the mount op tables that enforce them
  (`onlyne-adapter/src/lib.rs:1248-1292`). A hosting runtime is an agent mount; none of this
  is reachable from one.
- **Per-session watermarks in the host reducer.** Already per session
  (`ops.rs:337-342`, `lib.rs:1062-1064`). What is missing is the *runtime-side* discipline
  and the SDK seam to express it (G1(a)); no host change is owed.
- **One process serving several roles.** Already the case: one connection per
  `(runtime, role)` is exactly what the spec asks for (`HOSTING-RUNTIME.md:36-55`), and the
  client publishes one registration per role workspace. The gap list above is about what
  happens *inside* one connection.
