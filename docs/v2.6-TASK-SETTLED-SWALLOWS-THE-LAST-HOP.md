# `task_settled` 会吃掉一个任务的最后一跳

状态：**已修复**。2026-10-16 由 alexandria 集群 supervisor 提交（omp 会话）。
现场来自一次真实运维：一个 role 会话正常收尾、把自己那一跳的 `completion` 发出，
紧接着同一个进程退出，server 的释放路径把这条**刚发出、还没人读过**的 completion
判成 `rejected: task_settled`——于是这一跳永远送不到收件人。

> **修复记录（2026-10-17）。** 机制有一处与本稿不同：派发行在正常路径里由客户端
> **完成时** ack，而不是任务一开始就 ack。现场链是「第一次 exited 写入时派发行仍在飞 →
> 旧代码重投它 → 客户端经重投守卫重新 ack → 第二次 exited 写入读到 `acked` 并拒收
> completion」。判据恒真的结论不变，错在拿派发行的投递状态回答任务结论。
>
> 修法：`release_exited_delivery` 现在从**触发释放的那次写入本身**取 verdict
> （`projection.rs` 把已应用投影的 `outcome` 传进来），不再回读会话行（池化会话的
> 下一次任务会污染回读），也不再读派发行。completion 行整行不碰、ticket 保留；只释放
> 退出会话所属 role 收到、且 ticket 归属匹配的行。
>
> 有 verdict 时按是否存在**完成回执**分两种情况：
>
> - 有 `kind=Completion` 行（工作完成、verdict 已发出）：产生的它的那条 Task 派发行落
>   `acked`。client 的 ack 走持久 intent 队列、每 200 ms 才刷一次，退出写入可能先到；
>   拒收会写成「没收到」，与事实相反，且终态无法被迟到的 ack 修正。
> - 没有回执（完成被义务门禁拒绝，例如未履行的 `owes_targets`）：不动它，交回 TTL 与
>   重投规则，最终由 reconnect grace 落 `session_dead`。把它 ack 会把「没履行」写成
>   「已完成」。
>
> `release_refused` fault 删除：正常完成不再产生拒收。回归：
> `crates/onlyne-server/tests/release_exited_delivery.rs` 四个用例在旧代码上三个失败，
> 修复后全绿；`scenario_02_handoff_chain`（派发行被判 `rejected`，子任务永不 `acked`）
> 与 `scenario_20`（未履行义务不得 `acked`）都通过。

## 一句话

`release_exited_delivery` 用「该 task 的**第一条 `kind=task` 行**是否已终态」当作
「任务是否已完成」的证据；但那条行落 `acked` 只表示**投递被收件人收下**，
不表示任务有结论。派发行在任务**刚开始跑**的那一刻就已经是 `acked`。
于是判据恒真：任何会话正常退出时，它手上那条在飞的 completion 都会被自己判死。

**结论先说**：这里缺的不是一个判断，而是一个概念——**「这条投递被收下了」与
「这个任务有结论了」是两件事，而账上把第一件写成了 `acked`、读的时候当成第二件。**

## 现场（可复现的判定链）

task `54f72e05`（family `051c77f6`，MF-IceDrift + UVI 两页精读的第三轮复判）。
socrates 会话 `54f72e05` 在退出前后，账上按序发生（`onlyne history --since 2650 --limit 50`）：

```text
seq 2674 20:25:36.694  ledger in_flight  socrates->master completion msg=81b5e247 task=54f72e05
seq 2675 20:25:36.694  session socrates life=exited agent=running deliv=accepted seq=1004 gen_live=true
seq 2676 20:25:36.695  ledger queued     master->socrates  task       msg=5d5d5737 task=54f72e05
seq 2677 20:25:36.714  ledger acked      master->socrates  task       msg=5d5d5737 task=54f72e05
seq 2678 20:25:36.741  session socrates life=exited agent=gone  deliv=accepted seq=1005 gen_live=false
seq 2679 20:25:36.741  ledger rejected   socrates->master completion msg=81b5e247 reason=task_settled
```

三点可以直接读出来：

1. **`81b5e247`（socrates→master 的 completion）从 `in_flight` 直接落 `rejected`，
   `acked_at` 为空**——它一次都没被投出去过。
2. 拒它的时刻（`2679`）**晚于**任务派发行被 ack 的时刻（`2677`，`acked_at=20:25:36.714`）。
   也就是说，拒它用的「任务已终态」证据，正是它自己所在任务的**开跑**记录。
3. 那条 completion 的内容是「放行：七处复判全过，已交 scraper 拆知识点收束本族」——
   **这是本族的定稿放行**。它被吃掉后，master 永远不知道这一族已经放行。

复现命令（环在跑时）：

```bash
onlyne ledger --server-root <root> --msg-id 81b5e247-df6e-420e-91f1-3d524ec044a3
# state=rejected  reason=task_settled  acked_at=null
onlyne ledger --server-root <root> --msg-id 5d5d5737-b5fa-461b-86ff-902dd166d567
# state=acked  kind=task  enqueued_at=20:15:20  acked_at=20:25:36
```

第二条是**派发行**（master→socrates，`kind=task`），它的 `acked_at` 与拒收同秒。
第一天看很难相信：一条「已 acked」的派发行在账面上就是「任务已完成」。

## 机制（逐行）

三处代码，串起来就是缺陷：

1. **证据来源取错行的语义**。`onlyne-server/src/ghosts.rs:66-75`：

   ```rust
   pub(crate) fn task_ledger_state(state: &State, task_id: &str) -> Result<Option<LedgerState>> {
       let rows = state.ledger.ledger_task(task_id, TASK_ORIGIN_ROW_LIMIT)?;
       Ok(rows.iter().find(|row| row.kind == MsgKind::Task).map(|row| row.state))
   }
   ```

   注释自己写着这是「派发行（the dispatch row that created the work）」——
   `relay::task_origin` 拿它回答「谁派的活」，那是正确的用途。但
   `release_exited_delivery` 拿同一个函数回答**另一个问题**：「这个任务有结论了吗」。

2. **`acked` 被读成 `Done`**。`ghosts.rs:50-56`：

   ```rust
   pub fn settled_outcome(state: LedgerState) -> Option<Outcome> {
       match state {
           LedgerState::Acked => Some(Outcome::Done),
           LedgerState::Rejected | LedgerState::Expired => Some(Outcome::Failed),
           LedgerState::Queued | LedgerState::InFlight => None,
       }
   }
   ```

   这条映射用在降级清扫（ghost sweep）里是对的：**清扫的场景**是会话僵死、
   `working` 行没有主人，此时派发行已被 ack 就意味着「活确实有人接、并已交代完」，
   拿它当兜底证据说得过去。它错在**被复用**到了「任务还在正常推进」的路径上。

3. **释放路径拿它当判据并当场拒收**。`relay.rs:912-955`：

   ```rust
   let settled = ghosts::task_ledger_state(state, task_id)?.and_then(ghosts::settled_outcome);
   ...
   if settled.is_some() {
       state.ledger.fail_one(&row.msg_id, RELEASE_SETTLED_REASON)?;   // ← task_settled
   } else if apply_automatic_requeue(state, &row)? { ... }
   ```

   调用点：`projection.rs:148-150`，`Report::Heartbeat` 写入一条 `lifecycle=exited`
   的投影之后（`outcome.applied && exited`）。`lifecycle=exited` 是**正常收尾**
   与**进程暴死**共用的一个词，这里没有区分。

**为什么这条路径本来是对的（它要防的是什么）**：客户端重连的 `hello` 会声明它
还持有哪些投递（`relay.rs:764-802` 的 `Claim`）。一个已经被结算、但客户端仍声称
持有的行，如果被重投，就会让**同一个任务被做第二遍**——2026-10-15 真实发生过的
重复判决（见下文）。`task_settled` 就是为挡住这一类而加的。它挡住了那个问题，
**代价是把正常收尾的最后一条上报也一起挡住了**。

## 为什么不能靠「等它 ack」修

一个自然的想法是：延迟释放，等收件人 ack 那条 completion 再说。这修不掉本缺陷：
拒收发生在 `lifecycle=exited` 的写入路径上，而这条写入**在收件人能看到投递之前**
就已经发生（`2675` 早于任何 master 侧的事件；master 侧压根没有这条 msg 的任何事件）。
换句话说，投递根本没分发，谈不上等 ack。

## 影响面

- **高**：这不是边角情况，而是**每个正常收尾且带 completion 的会话**都会撞上的路径。
  判据恒真（派发行必然 `acked`），所以只要「会话带在飞 completion 退出」，
  这一跳就丢。当晚 20:25:36 那一秒里，socrates 的两个会话（`54f72e05`、`a7abcf90`）
  都走了同一条路径：前者被拒，后者侥幸没被拒（任务结算时刻不同），这本身就是竞态证据。
- **症状隐蔽**：账上落 `rejected`、原因 `task_settled`，运维很容易读成「任务早已结算，
  这一跳是多余的」——**语义完全反了**：是这一跳被自己的任务判死了。
  本仓 supervisor 一开始也这么误读过，直到对着 seq 逐帧读完事件链才反过来。
- **判据是竞态，同一个动作两种结局**：同一秒里 socrates 的另一个会话 `a7abcf90`
  走了**完全相同**的路径（20:44:47：completion `b5c186a7` 落 `in_flight` →
  会话 exited → 释放路径），结果却**被重投并成功送达**：

  ```text
  seq 2681 20:44:47.343  ledger in_flight  socrates->master completion msg=b5c186a7 task=a7abcf90
  seq 2682 20:44:47.344  session socrates sess=a7abcf90 life=exited seq=1004
  seq 2683 20:44:47.344  ledger queued     master->socrates  task       msg=ef85bde1 task=a7abcf90  ← 派发行被重投，此刻是 queued
  seq 2684 20:44:47.376  session socrates sess=a7abcf90 life=exited agent=gone seq=1005
  seq 2685 20:44:47.376  ledger queued     socrates->master  completion msg=b5c186a7 task=a7abcf90  ← 重投，不是 rejected
  seq 2686 20:44:47.514  ledger in_flight  master->socrates  task       msg=ef85bde1
  seq 2687 20:44:47.515  ledger acked      master->socrates  task       msg=ef85bde1
  seq 2688 20:44:47.574  ledger in_flight  socrates->master  completion msg=b5c186a7
  seq 2689 20:44:47.575  ledger acked      socrates->master  completion msg=b5c186a7  ← 送达
  ```

  差别只在**释放发生的那一瞬，派发行是什么状态**：`a7abcf90` 的派发行在
  `.344` 刚被重投成 `queued`，到 `.376` 释放时还没被任何 client 认领，
  `settled_outcome(Queued)` 回 `None`，于是走了 `apply_automatic_requeue`（正路）；
  `54f72e05` 的派发行在 `.695` 重投成 `queued`、`.714` 被认领成 `acked`，
  到 `.741` 释放时已是 `acked`，判据命中，completion 当场被打死。
  **窗口约 27–32 ms**，谁先谁后取决于有没有 client 在那几十毫秒内认领派发行。
  也就是说：同一个正确实现、同一个动作，**送达与否由一次资源竞争决定**。

- **与既有缺陷叠加**：这一跳丢掉后，下游 role 停在原地。本次侥幸靠 `a7abcf90`
  那条并行判决（「本族已由另一路 socrates 放行」）把信息补了回来——**不是框架救的**。

## 三个可改点（按性价比排序）

### A. 把「有结论」的判据与「被收下」分开（最小、先做这个）

给任务一条**独立的终态判据**：不要从 `kind=task` 的投递行取 `acked`。
选项（择一，实现前先定）：

- 在账上加一条显式的任务结局行（`kind=task_result` / 或给 task 行加一个
  `verdict` 列，只在 `complete`/`cancel`/`close` 时写），
  `task_ledger_state` 改读它；
- 或退一步：`release_exited_delivery` 只在**该 task 的所有在飞行都已结算**时
  才认「已终态」——即判据从「派发行 acked」改成「没有未结算的投递」；
- 或最小止血：`settled_outcome` 里把 `Acked` 拆出来，
  让释放路径只认 `Rejected | Expired`（真·失败），`Acked` 交回给正常的重投/等待路径。

三条都要回答同一个问题：**任务级结论的权威载体是谁**。我的倾向是第一条
（显式结局行），因为后两条都在「用投递行的形状推断任务级事实」，同一类错误换个
地方还会再犯。

### B. 区分「正常收尾」与「暴死」

`lifecycle=exited` 一词两用是这条路径的入口。client 侧知道自己的会话是
「跑完了正常落结束」还是「进程被打断」，应该把这个区分带上投影（例如
`exit_kind: graceful | killed | crashed`），释放路径只在**暴死**时走 requeue/拒收，
正常收尾时把在飞行交给正常的投递流程。

### C. 拒收要能被看见

现在这条拒收只落在 ledger 行的 `reason` 上，`faults` 面**没有**任何条目
（当晚的 open faults 里没有它）。一次「本该送达的定稿放行被静默吞掉」，
在告警面上是零信号。建议：`fail_one(RELEASE_SETTLED_REASON)` 同时推一条 fault，
或至少在 `onlyne faults` 里可查；这样运维能看见，而不是靠逐帧读事件发现。

## 与现有语义的关系

- `docs/operations.md` 描述 `acked` 为投递被接收方收下，本 draft 不主张改这个词，
  而是主张「**任务结论不能从它推**」。
- `docs/v2.5-CANCEL-NOT-ENFORCING.md` 处理的是「取消了但没停住」；
  本 draft 是反面：**没取消，却被当成已经结束**。两条都指向同一个未回答的问题——
  账上没有一个明确的「task 级结局」位。

## 验收形状（给后续实现用）

以本 draft 的现场做回归，三件事都要为真：

1. 一个会话**正常收尾**并发出 completion 后退出，该 completion 必须送达收件人
   （`state=acked`），不得落 `rejected`。
2. 一个**派发行已 acked、任务仍在推进**的场合，会话暴死引发的释放**不得**
   以 `task_settled` 拒收在飞行。
3. 客户端重连声明仍持有已结算投递时，原 `Claim` 防线仍然生效——
   **不要把 2026-10-15 那次重复判决放回来**。
