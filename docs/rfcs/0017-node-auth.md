# RFC 0017：节点认证、密钥与信任

状态：Draft。依赖：RFC 0001、0002、0007、0011。本文是目标契约；`packages/lib` 是参考实现，符合性以第 7 节场景为准。

本文规定节点身份认证、密钥发行与存放、密钥交换的状态机与信任边界。宿主通过库的公开接口读取阶段、提交确认、接收事件；接口形状与宿主义务在 [《lib 宿主契约》](../contracts/lib-host.md) 另行规定。

## 1. 分工：传输加密与身份认证

TLS 只负责传输加密，不承载节点身份。节点身份由应用层签名认证：调用方对请求签名，服务方用已持有的调用方公钥验签。公网节点通常部署在反向代理之后，TLS 在代理上终结；mTLS 需要代理透传客户端证书，多数现成配置不支持，而应用层签名对代理透明。

- 跨主机流量 MUST 走 HTTPS。证书用系统 CA 或公共 CA 签发；证书的域名只证明「到达了这个域名」，不证明「这就是该 node_id」。节点身份由签名验证单独确认。
- TLS 可以由反向代理终结。代理部署 MUST 满足：SSE 不缓冲、超时大于业务等待窗口、保留客户端地址。Onlyne 服务自身监听回环地址也是合法形态。
- 回环开发绑定（RFC 0001 §1）用未验证的 `Onlyne-Actor` 声明，只能用于回环监听。

算法：签名使用 Ed25519。密钥指纹是公钥的 SHA-256，展示为前 16 个十六进制字符。

## 2. 密钥发行与存放

每个节点一把长期身份密钥，随 node_id 生成。库 MUST 通过 `plugins.keys` 钩子取得密钥材料，不在库内部决定存放位置；位置由宿主决定。

发行与存放的强制检查（创建即设权限、加载时校验、位置不可用时启动失败）属于宿主侧义务，见 [《lib 宿主契约》](../contracts/lib-host.md) §3 与 [《OMP 宿主契约》](../contracts/omp.md) §4。协议要求只有一条：节点身份在信任关系存在期间保持同一把密钥，宿主 MUST NOT 静默生成新密钥。

本节点公钥从私钥推导。**对端公钥是网络事实，进持久存储**，与发现记录同库；文件系统里没有对端公钥。

密钥轮换：节点生成新密钥，向每个已信任对端出示旧密钥签名的轮换陈述。对端验过 `previous_signature` 后更新指纹、保留自己的批准位并把旧指纹记入 `history`；验不过时 MUST 以 `id_conflict` 拒绝。轮换不传播给第三方。同一时间最多一次未确认的轮换：上一轮的送达义务未清除前 MUST NOT 再次轮换，否则对端持有的证明会被跳过，之后任何陈述都无法通过它的密钥核对。

轮换只覆盖轮换发生时已经成行的对端。若某对端的首次批准在轮换期间仍在途，轮换方没有它的行，旧钥证明不会为它保留，窗口关闭后旧私钥也已删除；此后该对端仍钉着旧钥，任何来自本节点的新钥陈述都只能得到 `id_conflict`，本节点也无法知道它钉的是哪把钥。这种关系 MUST 用撤销后重新确认恢复，宿主 MUST 把 `id_conflict` 与这条重做步骤一起呈现给用户，MUST NOT 自动撤销。让陈述携带「对端钉住的指纹」并据此补发旧钥证明，需要把旧钥保留到这类关系全部解决，属于未决扩展，不属于本版。

## 3. 交换状态机

### 3.1 持久行

| 字段 | 含义 |
|---|---|
| `node_id` | 对端身份 |
| `public_key` / `fingerprint` | 对端公钥与其指纹；撤销后置空 |
| `state` | `pending` / `trusted` / `revoked` |
| `local_approved` | 本节点用户已确认 |
| `remote_approved` | 对端陈述证明它已确认 |
| `base_url` | 对端的服务地址 |
| `first_seen` / `last_checked` | 首次成行与最近核实时间 |
| `history` | 轮换前的旧指纹 |

### 3.2 阶段投影

阶段是宿主唯一可见的信任状态，由三个持久字段推导。宿主 MUST 读这个投影，MUST NOT 自行组合 `state` 与两个批准位：

| 持久状态 | `local_approved` | `remote_approved` | 阶段 | 含义 |
|---|---|---|---|---|
| 无行 | — | — | 无记录 | 从未交换 |
| `pending` | true | false | `requested` | 本侧已批准，等对端 |
| `pending` | false | true | `invited` | 对端已批准，等本侧用户 |
| `trusted` | true | true | `exchanged` | 双方批准，可签名通信 |
| `revoked` | false | false | `revoked` | 已撤销，入站被拒 |

`pending` 行至少有一侧批准；两侧都批准时行直接是 `trusted`，不存在「两个批准位都为真却仍是 pending」的持久行。

### 3.3 转移

| 当前 | 事件 | 结果 | 副作用 |
|---|---|---|---|
| 任意 | `begin(node)` | 不变 | 读对端 `GET /keys`，返回会话；不落库、不发送 |
| 无记录 / `requested` / `revoked` | 本地确认（`confirm(指纹)`） | `requested` | 本侧批准落库，写入送达义务，POST 介绍信 `approved=true` |
| `invited` | 本地确认 | `exchanged` | 双方批准已在本机成立，行直接 `trusted`；同样发出介绍信 |
| `exchanged` | 重复本地确认 | `exchanged` | 只刷新时间与地址；不写新义务，不重发 |
| `requested` | 重复本地确认 | `requested` | 视为重试：写新的送达义务并重发介绍信 |
| `requested` | 收到 `approved=true` 的陈述 | `exchanged` | 消费 nonce，落库 |
| `requested` | 收到 `approved=false` 的陈述 | `requested` | 消费 nonce，落库，刷新核实时间；对端尚未批准 |
| `exchanged` | 收到带有效轮换证明的陈述 | `exchanged` | 更新指纹，旧指纹入 `history`；保留本侧批准位，不降级 |
| 任意非 `revoked` | 本地撤销 | `revoked` | 公钥置空；此后入站介绍信以 `forbidden` 拒绝 |
| `revoked` | 本地确认 | `requested` | 重新交换，旧历史丢弃 |
| 任意阶段且送达义务未清 | 维护环到重试窗口 | 不变 | 用新 nonce 重发介绍信，更新义务的尝试时刻 |

首次接触收到 `approved=false` 的陈述 MUST 以 `invalid_request` 拒绝：没有既存关系可以回答，这样的陈述不构成任何一侧的事实。

### 3.4 不变量

1. 签名请求只在行为 `trusted` 时发出。未信任时传输层 MUST 以可重试的 `unavailable` 报告「先完成密钥交换」，MUST NOT 降级为明文或未签名请求。
2. 一次交换只建立一对关系，信任不可转让。
3. 陈述的签名覆盖发送方、接收方、公钥、地址、批准位、时间（epoch 毫秒）、nonce，以及回执上的 `reply_nonce`；篡改或被重放的陈述 MUST 拒绝。回执没有 `reply_nonce`、或它不等于本次发送的 nonce 时，发送方 MUST 视为没有送达。
4. 时间戳超出 5 分钟窗口 MUST 拒绝；nonce 在窗口内单次消费。
5. 对端公钥变化必须附旧钥签名的证明，否则 `id_conflict`。
6. 撤销是单向终止：被撤销后，本节点拒绝该对端的一切入站交换；只有本侧重新确认能恢复关系。
7. 预置 `trust_seeds` 指纹不符时 MUST 拒绝并报告看到的指纹。

### 3.5 送达义务与重驱

本地批准与「批准陈述已由对端持久记录」是两个事实。本地批准或轮换 MUST 在发送前持久记录独立的送达义务。义务保存目标与待送达的密钥版本，独立于信任行的阶段。对端主动发来的陈述只证明对端自己提交的事实，不解除本侧送达义务。

- 对端成功响应 MUST 在持久记录请求陈述后签发，响应签名绑定该请求的 nonce。发送方核验该响应后才能解除对应版本的送达义务。旧版本响应不得清除新版本义务。
- 无响应、响应丢失、响应验签失败或对端因时钟窗口拒绝时，义务保留。维护环为该义务生成新 nonce 并重发，包括本侧已经为 `exchanged` 的情况。重复陈述不反向触发新的送达义务。
- `/introductions` 的请求与错误响应都不带 Onlyne 签名，因此拒绝本身不可认证。对端报「已撤销」（`forbidden`）或「无证明换钥」（`id_conflict`）时，本侧 MUST 只让义务进入退避，MUST NOT 删除它：伪造的拒绝不能永久终止一次已经批准的送达。义务只由对端的签名陈述或本侧撤销结束。
- 对端尚未批准时，也可以确认已记录本侧陈述。此时本侧保留 `requested`，结束送达义务，等待对端用户决定。
- 重启后恢复未完成义务。存在义务时库保持维护活动；具体重试间隔属于库设计。

宿主 MUST NOT 调用重驱；它由库的维护环驱动。

## 4. 域与信任边界

域只表达节点的协议归组与发现范围（RFC 0011），不授予信任，也不产生自动连接。

- 共同加入同一域不产生任何自动密钥交换或自动信任。每个节点对的信任关系必须逐对显式建立，且可被任意一侧独立撤销。
- 经网络发现（含同一 region 候选）取得的节点仅为线索级候选。对端未进入 `exchanged` 阶段前，禁止向其发送签名业务请求，收到的请求亦按未信任处理。
- 跨域通信与域内通信遵循完全相同的逐对认证规则；跨域信任不传递，同一域内亦不传递。

## 5. 请求签名

每个跨主机请求携带：

```
Onlyne-Sig: v1 <actor> <timestamp> <nonce> <signature>
```

签名载荷是规范 JSON（键排序、无多余空白）：

```
onlyne-request-v1 { actor, target, method, path, digest, timestamp, nonce,
                    content_type, idempotency_key, retry_until, last_event_id }
```

`digest` 是请求体字节的 SHA-256；`target` 是接收方 node_id；`path` 含查询串。

响应携带 `Onlyne-Response-Sig`，载荷为 `onlyne-response-v1 { target, nonce, status, digest }`，`nonce` 取自对应请求。

- 服务方用持有的发送方公钥验签；未持有公钥时返回 401，并在错误详情中携带自己的公钥与指纹。
- timestamp 偏移超过 5 分钟拒绝；nonce 在时间窗内不得重复，已见 nonce 记入持久存储。
- 验签失败、公钥与已信任记录不符时返回 401。
- 调用方校验响应签名；没有响应签名或签名不符时，该响应 MUST 视为不可信。

回环 `none` 绑定不携带签名头，沿用 `Onlyne-Actor`。

## 6. 宿主契约

库拥有协议与状态机；宿主只做四件事：存放密钥、提供时钟、显示状态、响应事件。接口形状、宿主义务与符合性场景在 [《lib 宿主契约》](../contracts/lib-host.md) §2–§6 规定。本节保留协议侧的原则：

- 宿主 MUST 只读阶段投影，MUST NOT 从持久字段自行组合状态。
- 确认界面 MUST 同时显示双方指纹；`confirm` MUST 回传显示过的指纹。
- 拒绝一条 `invited` 行用撤销，不用本地确认。
- 事件是提示而非事实来源：宿主漏掉一个事件，下一次维护环收敛；宿主 MUST NOT 把事件当作唯一持久记录。
- 宿主 MUST NOT 运行自己的消息维护计时器；节奏归库。
- 宿主 MUST NOT 把收到对端陈述当作送达完成的证据；持久送达义务只有在收到对端签名确认后才清除（§3.5）。

## 7. 验收

独立实现按以下场景判定符合性：

- 公开 `/keys` 与指纹一致；交换后双方行、阶段与通知事件逐一成立。
- 篡改陈述、重放 nonce、跨身份搬用陈述全部拒绝。
- 双方批准进入 `exchanged`，签名发送通过并落库；轮换后对端指纹与历史正确，轮换陈述带旧钥证明。
- 撤销后发送被拒，撤销事件到达宿主；被撤销的对端不能靠新交换自行恢复。
- `begin` 会话展示对端指纹，`confirm` 用错指纹失败、用对指纹成功。
- 发送失败留下送达义务，`hasPendingWork` 为真；窗口过后维护环用新 nonce 重发，对端回执到达后义务消失。
- 双方批准后最后一封介绍信丢失，且期间没有发生轮换：网络恢复后两端都到达 `exchanged`，发送义务清空，全过程无需再次人工确认。跨轮换的情形见 §2，不在本条内。
- 首次接触收到 `approved=false` 的陈述返回 `invalid_request`，不落库。
- 同域节点之间未经显式确认不发生任何密钥交换；发现目录列出的同域候选按未信任处理。

已知不覆盖：首次批准在途时发生轮换（见 §2）。这类关系按 §2 用撤销后重新确认恢复，不列为符合性场景。
