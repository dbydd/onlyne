# RFC 0017：节点认证、密钥与信任

状态：Draft。依赖：RFC 0001、0002、0007、0011。本文规定节点身份认证、密钥发行与存放、密钥交换和信任边界的目标契约。`packages/lib` 尚无对应实现；本文是首个实现必须满足的规范。

## 1. 分工：传输加密与身份认证

TLS 只负责传输加密，不承载节点身份。节点身份由应用层签名认证：调用方对请求摘要签名，服务方用已持有的调用方公钥验签。这样选择是因为公网节点通常部署在反向代理之后，TLS 在代理上终结；mTLS 需要代理透传客户端证书，多数现成配置不支持，而应用层签名对代理透明。

- 跨主机流量 MUST 走 HTTPS。证书用系统 CA 或 Let's Encrypt 等公共 CA 签发；证书的域名只证明「到达了这个域名」，不证明「这就是该 node_id」。节点身份由签名验证单独确认。
- TLS 可以由反向代理终结。代理部署 MUST 满足：SSE 不缓冲、超时大于业务等待窗口、保留客户端地址。Onlyne 服务自身监听回环地址也是合法形态。
- 回环开发绑定维持现状：HTTP、`Onlyne-Actor` 未验证声明（RFC 0001 §1）。该绑定只能用于回环监听。

算法：签名使用 Ed25519。密钥指纹是公钥的 SHA-256，展示为前 16 个十六进制字符。

## 2. 密钥发行与存放

每个节点一把长期身份密钥，随 node_id 生成，存放在宿主文件系统。库 MUST 通过插件钩子取得密钥材料，不在库内部决定存放位置；存放策略由宿主（如 OMP 插件）执行。

| 位置 | 用途 | 权限 |
|---|---|---|
| 项目 `<cwd>/.onlyne/keys/<node_id>/` | 默认。身份随项目走，适合 CI 与一次性 agent | 目录 0700，私钥 0600 |
| 全局 `~/.config/onlyne/keys/<node_id>/` | 可选。身份随机器走，多项目共用一个节点 | 同上 |

发行时的强制检查：

1. 创建即设权限：目录 0700、私钥 0600，不依赖 umask。
2. 项目位置在 git 工作区内且 `.onlyne/keys/` 未被 ignore 时，MUST 拒绝创建，提示加 ignore 或改选全局。
3. 加载时校验：私钥文件组可读或全局可读时 MUST 拒绝使用，报错说明修复命令（`chmod 600`）。

公钥不分目录存放。本节点公钥从私钥推导；**对端公钥是网络事实，进 SQLite**，与发现记录同库：字段含 node_id、公钥、指纹、验证状态、首次与最近核实时间。公钥不在文件系统里出现。

密钥轮换：节点可生成新密钥并向已信任对端出示旧密钥签名的轮换声明；对端确认后更新记录并保留旧指纹历史。轮换不自动传播给第三方；信任链上每对关系分别确认。

## 3. 密钥交换与握手

首次交换遵循双边显意同意（TOFU 带确认）：A 信任 B 需要两侧各一次用户确认。

```
A 勾选 B（UI）
  → A 弹窗：B 的 node_id、域、B 公钥指纹（来自 B 的服务描述）、A 将出示的指纹
  → 确认后 A 发介绍请求（携带 A 公钥 + 请求签名，证明持有私钥）
  → B 侧出现待确认条目；B 的用户确认（看到 A 的 node_id、域、指纹）
  → 双方互持对方公钥，状态 trusted
```

- 请求与确认都必须携带**双方指纹**。UI MUST 显示指纹；用户带外核对指纹是对自签场景中间人攻击的唯一防御，协议不做自动核对承诺。
- 一次握手只建立一对关系。信任不可转让：A 信任 B、B 信任 C，不产生 A 对 C 的任何信任。
- 无头节点提供非交互路径：`config.toml` 预置 `[[trust]]` 种子（node_id + 指纹），首次连接按指纹匹配自动确认。指纹不匹配时拒绝并报告看到的指纹。

## 4. 域与信任传递

域传递**发现范围**，不传递**认证**。

- 与一个已认证节点握手后，自动取得它看到的域成员候选列表（经 `GET /discovery` 候选交换，现状已有）。候选进 SQLite 发现目录，与 DNS-SD 结果同级：是线索，不是信任。
- 认证仍然逐节点建立。UI 提供批量动作降低操作成本：右列勾选多个节点后「信任所选」，一次弹窗显示全部待信任条目的指纹清单，逐条确认或全选。
- 禁止「域内默认全连接」：任何把「共同加入域」提升为「自动信任」的行为都违反本节。理由：RFC 0011 规定域自由加入、无准入审批，域内自动信任等价于「谁加入域，谁获得全域信任面」。
- 经已认证节点**中转访问**其他节点是独立特性，本 RFC 不定义，v3 首版不实现。中转节点对经过流量是天然的中间人位置。

## 5. 请求签名

每个跨主机请求携带签名头：

```
Onlyne-Sig: v1 <key_id> <timestamp> <nonce> <signature>
Onlyne-Sig-Content: method + "\n" + path + "\n" + sha256(body)
```

- `key_id` 为发送方 node_id；`signature` 对 `timestamp + "\n" + nonce + "\n" + sha256(body)` 与内容摘要拼接后签名。
- 服务方用持有的发送方公钥验签；未持有公钥（未信任）时返回 401，并在错误详情中携带自己的公钥与指纹，供首次交换使用。
- timestamp 偏移超过 5 分钟拒绝；nonce 在时间窗内不得重复，已见 nonce 记入 SQLite。
- 验签失败、公钥不匹配已信任记录时返回 401 并记入对端验证状态。

回环 `none` 绑定不携带签名头，沿用 `Onlyne-Actor`。

## 6. 库接口

安全机制在 lib 实现，宿主只提供存放与用户确认。`OnlyneNode` 新增 `trust` 服务：

| 接口 | 效果 |
|---|---|
| `keys.generate(auth)` | 生成密钥对，经插件钩子写入宿主选定位置 |
| `keys.describe(auth)` | 返回本节点公钥与指纹 |
| `trust.request(target)` | 向 target 发介绍请求（携公钥与签名） |
| `trust.list(auth)` | 信任表：node_id、指纹、状态（pending/trusted/revoked）、时间 |
| `trust.accept(auth, entry)` | 确认一条待确认握手，落库 |
| `trust.revoke(auth, node_id)` | 撤销信任，删除对端公钥记录 |
| `trust.rotate(auth)` | 密钥轮换：生成新钥，向全部 trusted 对端发轮换声明 |

`authenticate` 插件钩子语义扩展：HTTP 层先验签名，通过后把 `actor` 交给既有授权检查。none 绑定行为不变。

## 7. 验收

- 跨主机明文 HTTP 被拒绝；HTTPS 下无签名或签名无效返回 401，携带服务方公钥。
- 私钥目录权限不达标时发行与加载都拒绝，错误信息含修复命令。
- git 工作区内未 ignore 的项目位置拒绝创建密钥。
- 握手两侧确认后才进入 trusted；单侧确认停留 pending，可取消。
- 预置 `[[trust]]` 指纹不匹配时拒绝连接并报告看到的指纹。
- 加入同一域不产生任何自动信任；批量动作只是 UI 合批，每对关系仍有独立记录与撤销。
- nonce 重放与超窗时间戳被拒绝。
- 对端公钥只存在于 SQLite；文件系统中无对端公钥。
