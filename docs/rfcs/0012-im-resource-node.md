# RFC 0012：IM 会话资源节点

状态：Draft。依赖：RFC 0001、0006、0011、0015。

## 1. 定位

IM 会话是事件驱动型资源节点。平台事件由 IM endpoint 首次接收并归属，随后推给当前 assignee。agent 不直接碰平台。

| 事实 | 持有者 |
|---|---|
| 平台事件、平台会话坐标、chat key 注册表 | IM endpoint |
| 路由绑定（哪个 agent 接手哪个会话） | IM endpoint |
| 平台凭据 | IM endpoint 所在宿主，agent 不接触 |
| 未解决事件引用、交接截点 | IM endpoint |
| 是否建立待办、怎么回复平台 | assignee |

IM endpoint 是资源节点，不是 agent，不调用模型。它只做事件接收、去重、归属、绑定和推送。

## 2. 会话身份

会话身份是应用层 chat key，不由平台坐标决定。

| 标识 | 作用 | 唯一性域 |
|---|---|---|
| `chat_key` | 会话的稳定身份，跨平台坐标不变 | 网关根 |
| 平台会话坐标 | 平台怎么称呼这个会话 | 平台 |
| 工作区 slug | 磁盘目录名，运营标签 | 网关根 |

`chat_key` 是 1～64 字符，字符集 `[A-Za-z0-9_:-]`。目录名是运营标签，协议不从中推断身份。

平台坐标与 chat key 的映射由 endpoint 持有。平台侧规范化会话 id 与注册 id 不一致时，endpoint 按注册表解析，不猜。

一个平台会话只能被一个工作区认领。一个 chat key 只能属于一个工作区。加载时交叉校验，冲突即拒绝启动。

## 3. 资源描述

```json
{
  "resource_ref": {"owner": "urn:onlyne:gateway:im", "id": "chat-01"},
  "kind": "im_conversation",
  "operations": ["read", "send", "list_events", "handover", "describe"],
  "requires": ["im_platform_send"],
  "binding": {"assignee": "urn:onlyne:agent:lazuli", "revision": "rev-a"},
  "event_id": "31"
}
```

`operations` 清单由 endpoint 声明。`send` 需要 `im_platform_send` 授权。`handover` 切换 assignee 和发送权。`read` 和 `list_events` 按当前 assignee 授权过滤。

## 4. 入站路径

平台事件到达顺序固定：

1. 后端子进程收到平台事件，以长度前缀 JSON 帧送给 endpoint。
2. endpoint 在一个持久事务里完成五件事：按 `(resource_ref, platform_event_id)` 去重、分配 `event_id`、记录首次归属与首次绑定 revision、追加会话日志、追加资源事件流。平台游标在同一事务里推进。
3. 事务提交之前，该事件不算已接收。崩溃后由平台重放，去重键保证只产生一条记录。
4. 提交之后，按事件的首次归属把事件推给该记录的接收者。当前绑定只决定尚未首次接收的新事件。
5. 推送失败时事件留在该资源的队列，暴露未送达记录。

去重在 endpoint 层完成，不依赖下游脚本。平台事件 id 可能只在一个会话内唯一，去重键必须带 `resource_ref`。

入站过滤有两个独立层次：

| 层次 | 检查什么 | 配置 |
|---|---|---|
| 监听策略 | 这个平台会话是否被接受 | deny 优先，空 allow 表示全收 |
| 发送者策略 | 这个平台发送者是否被接受 | 白名单，默认拒绝未知发送者 |

发送者策略是 v3 新增项。v2 只有平台会话过滤，任何群成员都能触发集群动作。

未注册且被允许的平台会话按 adopt 流程创建资源：分配 chat key、建立工作区、插入注册表。入站首触和出站首触都可以 adopt。

## 5. 出站路径

agent 通过资源操作发送，不直接持有平台凭据：

```json
{
  "operation_id": "op-01",
  "retry_until": "2026-10-23T04:00:00Z",
  "operation": "send",
  "expected_revision": "rev-a",
  "data": {
    "text": "图已更新，单位是 W/m²。",
    "reply_to_event": "31"
  }
}
```

校验顺序：

1. 认证调用方，确认它是当前 assignee 或被授权的代表。
2. 比较 `expected_revision` 与当前绑定。不匹配返回 `revision_conflict`。
3. 校验 `data` 匹配该操作的 schema。
4. 交后端渲染发送。
5. 记录本次发送使用的 revision 和平台结果。

`reply_to_event` 指向 endpoint 分配的 `event_id`，不指向平台消息 id。endpoint 负责把应用层引用翻译成平台的回复句柄。

**ack 与平台确认分离。** endpoint 接受发送请求后先返回 `pending`，平台确认后写结果并产生 `committed` 事件。平台失败记 fault 并保留原文，不把接受当作送达。

投递确认（`delivery_ack`）与平台确认是另一件事。`delivery_ack` 表示 assignee 已经在本节点持久保存事件正文或可恢复引用。endpoint 按 `event_id` 记录确认，并校验确认方是该事件的首次归属接收者。确认幂等。

## 6. 绑定与交接

绑定表是 endpoint 的局部状态：

```json
{
  "resource_ref": {"owner": "urn:onlyne:gateway:im", "id": "chat-01"},
  "assignee": "urn:onlyne:agent:lazuli",
  "revision": "rev-a",
  "updated_at": "2026-10-23T02:00:00Z"
}
```

交接按 RFC 0006 §5 的五步执行。IM 场景的关键点：

- 平台凭据留在 endpoint。接手者拿到的是发送权，不是平台令牌。
- 交接提交是生效点。提交前的事件保留首次归属，提交后的新事件取提交后的绑定。
- 交接提交要求该资源没有积压。存在未确认投递时提交返回 `conflict`，先清空积压再重试。
- 积压为零时，交接提交只改变后续事件的归属与发送权。已经接收的事件留在原 assignee 的本地副本。
- 接手材料包含未解决事件引用和 `cutoff_event_id`。目标按授权读取，不重新派发全部历史。
- 协议不提供把积压转给另一个节点的操作。积压只能通过确认或保留期终态清空。
- 原 assignee 可以分析旧工作，把结果发给新 assignee，由新 assignee 决定怎么回平台。

v2 的会话到 agent 绑定只活在推送脚本里，endpoint 既不存也不查。v3 把绑定提升为 endpoint 的一等状态，交接才有协议级的生效点和冲突判定。

## 7. 授权

| 操作 | 谁可以 |
|---|---|
| `read`、`list_events` | 当前 assignee；交接转入的未确认事件；owner 明确签发的历史读取授权 |
| `send` | 当前 assignee 或被授权代表 |
| `handover` | 当前 assignee 或 endpoint 明确授权的代表 |
| `describe` | 被授权查看该资源的节点 |

授权按会话判断，不按角色通配。v2 的服务端 ACL 是会话盲的：任何能触达网关角色的节点都能投递该根下任意 chat key。v3 的 endpoint 必须校验调用方与具体资源的绑定关系。

服务端 ACL 仍然存在，作为第一道门。它回答「这个角色能不能和网关通信」，不回答「这个角色能操作哪个会话」。第二道门在 endpoint。

## 8. 凭据

平台凭据的存放和传递：

| 环节 | 规则 |
|---|---|
| 存储位置 | 网关根的凭据目录，一个文件对一个后端，权限 0600 |
| 传递给后端 | 只给文件路径，经环境变量，不进 argv |
| 解析顺序 | 显式参数、凭据文件、平台惯用环境变量 |
| 文件内容 | 可写 `$NAME` 引用其他环境变量，`$$` 表示字面 `$` |
| 持有者 | 后端子进程读，网关自己不读值 |

交互登录先写后验是一种风险：凭据已落盘而验证失败时会留下无效文件。v3 要求登录失败时清理已写文件，或明确报告该文件需人工删除。

各平台的凭据编码不同：单 token、`app_id:app_secret` 对、`xapp:xoxb` 对。endpoint 按后端类型解析，不统一格式。

MCP 后端的秘密放在配置的 `env` 或 `env_file` 里，没有登录流程。它的认证状态只能看 MCP client 是否起来。

## 9. 恢复

### endpoint 重启

重启后重新读取根配置、扫描会话目录、交叉校验唯一性。chat key 从盘上读回，内存绑定按持久记录恢复。未恢复的绑定按 `unknown` 处理，不假定仍是原 assignee。

### 平台游标

平台游标必须持久化。v2 的游标全在内存，重启后回到起点，只能依赖平台自己保留的积压窗口。v3 要求：

- 游标随事件接收一起提交，和 `event_id` 分配同一事务。
- endpoint 退出时给后端写游标的机会，后端必须实现。
- 无法持久化游标的后端必须声明自己的重放窗口，超窗口的事件明确报告缺失。

### 积压与重放

接手者不可达时，事件留在该资源的队列，不阻塞其他资源。队列深度和保留期限由 endpoint 声明。该资源因此存在积压，交接被拒绝，直到这些事件被确认或给出明确终态。保留期到达时，endpoint MUST 写入 `expired` 终态并清除该投递义务，不得让积压无限保留。

重放时按事件的首次归属分发，不因绑定已切换而改写它。

积压按位置分四层，只有后两层属于协议状态：

| 层 | 内容 | 持有者 | 恢复方式 |
|---|---|---|---|
| 平台侧 | 平台尚未推给 endpoint 的消息 | 平台 | 平台自己的重放窗口 |
| endpoint 入站队列 | 已持久接收、尚未推给 assignee 的事件 | endpoint | 按 `event_id` 查询与重放 |
| assignee 本地队列 | 已推送、尚未确认接收或消费的事件 | assignee | 重新对账未确认义务 |
| thread 关注义务 | 已进入 thread、尚未注入模型的消息 | owner 与成员 | 关注清单与确认 |

交接只作用于 endpoint 已经持久接收的事件。平台侧尚未到达的事件不参与交接；交接提交后新到达的事件按提交后的绑定归属。

### 未 ack 投递

endpoint 与集群链路之间的未确认投递，在新连接建立时重新入队。重放可能产生重复推送，下游按 `event_id` 去重。

### 推送脚本

推送脚本至少执行一次。重试耗尽记 fault，事件保留在队列中等待人工或重试策略处理。脚本超时按配置强杀。

### 已知缺口

以下 v2 问题在 v3 必须有明确处置：

| 缺口 | v3 要求 |
|---|---|
| 网关级无去重，只在脚本层按 event id | endpoint 层去重，`(resource_ref, platform_event_id)` |
| 游标全内存，重启回放不确定 | 游标持久化，与事件提交同一事务 |
| ack 早于平台确认 | 先 `pending`，平台确认后才 `committed` |
| 无发送者白名单 | 发送者策略默认拒绝未知来源 |
| ACL 会话盲 | endpoint 校验具体资源的绑定关系 |
| 附件是平台句柄（file_id、url_private） | 附件落到工作区，消息带本地路径 |
| 会话绑定只在脚本里 | 绑定是 endpoint 的一等状态 |
| 登录先写后验 | 失败时清理或明确报告 |
| `<help>` 在 key 提取前拦截 | 帮助命令与会话消息分通道 |
| 日志只追加不轮转 | 轮转策略由 endpoint 声明 |

## 10. 验收

- 同一平台事件重复到达只产生一条 `event_id`。
- 在事务提交前崩溃，平台重放后只产生一条记录；事务提交后崩溃，事件正文与游标一起存在。
- 未授权节点投递到该会话被 endpoint 拒绝，服务端 ACL 放行也不通过。
- 存在未确认投递时，交接提交返回 `conflict`；清空积压后提交成功。
- 交接提交后新事件进入新 assignee，已接收事件留在原 assignee。
- 交接后原 assignee 的发送被 `revision_conflict` 拒绝，附带当前 revision。
- 确认方不是该代次的接收者时，确认不生效。
- endpoint 重启后 chat key 和绑定从盘上恢复，游标不回退到起点。
- 平台游标无法持久化时，明确声明重放窗口，超窗口事件报告缺失。
- 平台发送失败时 fault 保留平台原文，agent 看到的是 `pending` 之后的失败，不是接受。
- 未知平台发送者的消息被发送者策略拒绝，不进集群。
- 附件落到工作区，投递给 agent 的内容带本地路径而不是平台句柄。
- 接手者不可达时事件留在该资源队列，其他资源的推送继续。
