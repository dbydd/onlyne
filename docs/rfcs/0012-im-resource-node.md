# RFC 0012：IM 会话资源节点

状态：Draft。依赖：RFC 0001、0006、0011、0015。

## 1. 定位

IM 会话是事件驱动型资源节点。平台事件由 IM endpoint 首次接收并追加进会话日志，随后推给当前 handler。agent 不直接碰平台。

| 事实 | 持有者 |
|---|---|
| 平台事件、平台会话坐标、chat key 注册表 | IM endpoint |
| 路由绑定（哪个 agent 接手哪个会话） | IM endpoint |
| 平台凭据 | IM endpoint 所在宿主，agent 不接触 |
| 会话日志：追加写入、`event_id` 不复用 | IM endpoint |
| 是否建立待办、怎么回复平台 | handler |

IM endpoint 是资源节点，不是 agent，不调用模型。它做事件接收、去重、追加日志、绑定和推送。

endpoint 只交付资源操作与事件日志。把一条会话投影成哪种 agent 侧形状——消息列表、待办、执行上下文——属于接入层设计，随平台与宿主而变，本文不做规定。

一个连接器服务多条会话，一条会话一个资源。会话集合在运行时增减，endpoint MUST NOT 在配置期固定它。

## 2. 会话身份与 adopt

一个连接器是一条平台连接、一份凭据，不是一条会话。机器人加入的群、发来私聊的用户都在运行时变化，endpoint MUST 同时服务多个会话，并按平台坐标分别寻址。

| 标识 | 作用 | 唯一性域 |
|---|---|---|
| 连接器 | 一份凭据与一条平台连接 | 网关根 |
| 资源 id | endpoint 内一条会话的稳定身份 | endpoint |
| 平台会话坐标 | 平台怎么称呼这个会话 | 平台 |

资源 id 从平台坐标派生，`chat_id` 与 `open_id` 分别带前缀，例如 `lark-oc_6b14` 与 `lark-ou_sender`。派生规则 MUST 可逆：给定资源 id 能取回平台坐标，给定平台坐标能得到同一个资源 id。平台坐标字符集超出资源 id 字符集时，endpoint 用确定性编码，MUST NOT 让两个坐标映到同一个 id。

endpoint MUST 持久保存坐标到资源 id 的映射。平台侧改换会话坐标时，endpoint 按映射解析，MUST NOT 猜成新会话。

### adopt

平台会话首次出现时，endpoint 自动创建资源，分配事件游标、绑定与日志读者。adopt 由入站或出站首触触发，MUST NOT 需要重启或改配置。

- 入站首触：一条来自未登记会话的事件被监听策略与发送者策略放行，endpoint 在该事务内创建资源并追加该事件。
- 出站首触：一次发送指向未登记的会话，endpoint 先创建资源，再交平台渲染。
- adopt MUST 幂等。同一坐标的并发首触只产生一个资源，第二个请求复用已创建的那一个。

配置里的 `conversation` 是预绑定，可省略。省略时全部会话走 adopt；填写时该会话在启动时就建好资源，行为与 adopt 结果一致。预绑定 MUST NOT 限制 endpoint 服务其他会话。

### 监听与发送者过滤

入站过滤有两个独立层次：

| 层次 | 检查什么 | 配置 |
||---|---|---|
| 监听策略 | 这个平台会话是否被接受 | deny 优先，空 allow 表示全收 |
| 发送者策略 | 这个平台发送者是否被接受 | 白名单，默认拒绝未知发送者 |

发送者策略是 v3 新增项。v2 只有平台会话过滤，任何群成员都能触发集群动作。

被拒绝的事件不创建资源，也不产生事件 id。拒绝 MUST 记录为可观察的丢弃，MUST NOT 静默。

## 3. 资源描述

```json
{
  "resource_ref": {"owner": "urn:onlyne:gateway:im", "id": "chat-01"},
  "kind": "im_conversation",
  "operations": ["read", "send", "list_events", "handover", "describe"],
  "requires": ["im_platform_send"],
  "binding": {"handler": "urn:onlyne:agent:lazuli", "cursor": "31", "revision": "rev-a"}
}
```

`operations` 清单由 endpoint 声明。`send` 需要 `im_platform_send` 授权。`handover` 更换 handler，见 §6。`read` 和 `list_events` 读会话日志，按当前 handler 与 `log_readers` 授权过滤。

一条会话一个资源，一个 handler。交接的最小单位是会话：把一条会话转给别的 agent，其他会话的绑定不受影响。

## 4. 入站路径

平台事件到达顺序固定：

1. 平台事件由平台连接层送达 endpoint。连接层可以是 endpoint 进程内的连接器模块，也可以是经长度前缀 JSON 帧对话的子进程；本 RFC 只约束送达语义，不指定连接层的进程形态。
2. endpoint 在一个持久事务里完成四件事：按 `(resource_ref, platform_event_id)` 去重、分配 `event_id`、追加会话日志、追加资源事件流。事件不记录归属：它属于资源，不属于某个 agent。连接层持有的平台游标在事件接收后推进；无法由 endpoint 持久化的游标，由连接层声明自己的重放窗口（见 §9）。
3. 事务提交之前，该事件不算已接收。崩溃后由平台重放，去重键保证只产生一条记录。
4. 提交之后，向当前 handler 推送 `event_id > cursor` 的事件。绑定是唯一的路由依据，事件本身不带收件人。
5. 推送失败时事件留在该资源的队列，暴露未送达记录。

去重在 endpoint 层完成，不依赖下游脚本。平台事件 id 可能只在一个会话内唯一，去重键必须带 `resource_ref`。

一条事件落在它自己的会话资源上。事件的 `data` 带平台坐标与发送者，资源身份由平台坐标解析得到；同一连接器多条会话的事件 MUST NOT 落进同一个资源。

推送失败只阻塞该会话自己的队列，其他会话的推送与交接照常进行。

## 5. 出站路径

agent 通过资源操作发送，不直接持有平台凭据：

```json
{
  "operation_id": "op-01",
  "retry_until": "2026-10-23T04:00:00Z",
  "operation": "send",
  "expected_revision": "rev-a",
  "data": {
    "text": "图已更新，单位是 W/m²。",
    "reply_to_event": "31"
  }
}
```

发送目标是该资源自己的会话坐标。一条会话一个资源，寻址一条会话就是操作它的资源。`reply_to_event` 指向本资源内的 `event_id`；指向其他资源时返回 `invalid_request`，不跨会话引用。

校验顺序：

1. 认证调用方，确认它是当前 handler 或被授权的代表。
2. 比较 `expected_revision` 与当前绑定。不匹配返回 `revision_conflict`。
3. 校验 `data` 匹配该操作的 schema。
4. 交平台连接层渲染发送。
5. 记录本次发送使用的 revision 和平台结果。

`reply_to_event` 指向 endpoint 在该资源内分配的 `event_id`，不指向平台消息 id。endpoint 负责把应用层引用翻译成平台的回复句柄。

endpoint 持有坐标到资源 id 的映射。一次发送落在哪个资源上，由该资源的会话坐标决定；映射缺失时按 §2 的 adopt 规则先建资源再发送。调用方必须是该资源的当前 handler。

**ack 与平台确认分离。** endpoint 接受发送请求后先返回 `pending`，平台确认后写结果并产生 `committed` 事件。平台明确拒绝记 `aborted`，平台结果不明记 `unknown`，两者都保留平台原文；不把接受当作送达。

投递确认（`delivery_ack`）与平台确认是另一件事。`delivery_ack` 表示当前 handler 已经在本节点持久保存事件正文或可恢复引用。endpoint 按 `event_id` 记录确认，并校验确认方是当前 handler。确认把游标前移，重复确认幂等。确认不是交接的前置条件：交接只搬运游标，不搬运欠账。

## 6. 绑定与交接

绑定表是 endpoint 的局部状态：

```json
{
  "resource_ref": {"owner": "urn:onlyne:gateway:im", "id": "chat-01"},
  "handler": "urn:onlyne:agent:lazuli",
  "cursor": "31",
  "revision": "rev-a",
  "updated_at": "2026-10-23T02:00:00Z"
}
```

交接按 RFC 0006 §4 的三段式握手执行。IM 场景的关键点：

- 平台凭据留在 endpoint。目标拿到的是发送权，不是平台令牌。
- 探测携带的元数据由 endpoint 组织：平台、会话坐标、标题、操作清单。目标凭它判断自己能否接手，协议不解释这些字段。
- 受理交接即冻结入站投递：冻结期内到达的平台事件照常写入日志，不推给任何人。握手成功则从新游标起投给目标，失败则补投给原 handler。
- 切换是唯一生效点。切换前崩溃，恢复后仍是原 handler、原 revision。
- 交接不要求清空任何积压：游标是位置，不是欠账。
- 原 handler 若仍在 `log_readers` 里，可以读全量历史做收尾分析；移出后即失去历史读取权。

v2 的会话到 agent 绑定只活在推送脚本里，endpoint 既不存也不查。v3 把绑定提升为 endpoint 的一等状态，交接才有协议级的生效点和冲突判定。

## 7. 授权

| 操作 | 谁可以 |
|---|---|
| `read`、`list_events` | 当前 handler，或 `log_readers` 表里的节点 |
| `send` | 当前 handler 或被授权代表 |
| `handover` | 当前 handler 或 endpoint 明确授权的代表 |
| `describe` | 被授权查看该资源的节点 |

授权按会话判断，不按角色通配。v2 的服务端 ACL 是会话盲的：任何能触达网关角色的节点都能投递该根下任意 chat key。v3 的 endpoint 必须校验调用方与具体资源的绑定关系。

服务端 ACL 仍然存在，作为第一道门。它回答「这个角色能不能和网关通信」，不回答「这个角色能操作哪个会话」。第二道门在 endpoint。

## 8. 凭据

平台凭据的存放和传递：

| 环节 | 规则 |
|---|---|
| 存储位置 | 网关根的凭据目录，一个文件对一个平台，权限 0600 |
| 传递给连接层 | 只给文件路径，经环境变量或配置注入，不进 argv |
| 解析顺序 | 显式参数、凭据文件、平台惯用环境变量 |
| 文件内容 | 可写 `$NAME` 引用其他环境变量，`$$` 表示字面 `$` |
| 持有者 | 连接层读，网关自己不读值 |

交互登录先写后验是一种风险：凭据已落盘而验证失败时会留下无效文件。v3 要求登录失败时清理已写文件，或明确报告该文件需人工删除。

各平台的凭据编码不同：单 token、`app_id:app_secret` 对、`xapp:xoxb` 对。endpoint 按平台连接层类型解析，不统一格式。

MCP 连接层的秘密放在配置的 `env` 或 `env_file` 里，没有登录流程。它的认证状态只能看 MCP client 是否起来。

## 9. 恢复

### endpoint 重启

重启后重新读取根配置、扫描会话目录、交叉校验唯一性。chat key 从盘上读回，内存绑定按持久记录恢复。未恢复的绑定按 `unknown` 处理，不假定仍是原 handler。

### 平台游标

平台游标必须持久化。v2 的游标全在内存，重启后回到起点，只能依赖平台自己保留的积压窗口。v3 要求：

- 游标随事件接收一起提交，和 `event_id` 分配同一事务。
- endpoint 退出时给连接层写游标的机会，连接层必须实现。
- 无法持久化游标的连接层必须声明自己的重放窗口，超窗口的事件明确报告缺失。

### 积压与重放

handler 不可达时，事件继续写入日志，不阻塞其他资源，也不阻塞交接。推送重试与队列深度由 endpoint 声明；保留期限到达时，endpoint MUST 为该事件写入 `expired` 终态，不得让内容无限保留。终态只影响内容保留，不影响 `event_id`：该 ID 永不复用。

重放时按当前游标与当前 handler 分发。绑定切换后，未消费的事件由新 handler 接手，不需要任何改派操作。

积压按位置分四层，只有后两层属于协议状态：

| 层 | 内容 | 持有者 | 恢复方式 |
|---|---|---|---|
| 平台侧 | 平台尚未推给 endpoint 的消息 | 平台 | 平台自己的重放窗口 |
| endpoint 日志 | 已持久接收的全部事件 | endpoint | 按 `event_id` 查询与重放 |
| handler 本地队列 | 已推送、尚未确认消费的事件 | handler | 按游标对账 |
| agent 侧待办 | 接入层为持续处理建立的本地项 | 接入层 | 接入层自己的持久记录 |

交接只搬运游标。平台侧尚未到达的事件不参与交接；切换后新到达的事件按切换后的绑定归属。

### 未 ack 投递

endpoint 与集群链路之间的未确认投递，在新连接建立时重新入队。重放可能产生重复推送，下游按 `event_id` 去重。

### 连接层

推送脚本至少执行一次。重试耗尽记本地运行日志中的失败，它不是资源操作结果值；事件保留在队列中等待人工或重试策略处理。脚本超时按配置强杀。v2 的推送脚本是连接层的一种历史形态；v3 的连接层按[设计文档](../design/im/README.md)实现，语义不变：至少执行一次，失败不是操作结果值，事件留队。

### 已知缺口

以下 v2 问题在 v3 必须有明确处置：

| 缺口 | v3 要求 |
|---|---|
| 网关级无去重，只在脚本层按 event id | endpoint 层去重，`(resource_ref, platform_event_id)` |
| 游标全内存，重启回放不确定 | 游标持久化，与事件提交同一事务 |
| ack 早于平台确认 | 先 `pending`，平台确认后才 `committed` |
| 无发送者白名单 | 发送者策略默认拒绝未知来源 |
| ACL 会话盲 | endpoint 校验具体资源的绑定关系 |
| 附件是平台句柄（file_id、url_private） | 附件落到工作区，消息带本地路径 |
| 会话绑定只在脚本里 | 绑定是 endpoint 的一等状态 |
| 登录先写后验 | 失败时清理或明确报告 |
| `<help>` 在 key 提取前拦截 | 帮助命令与会话消息分通道 |
| 日志只追加不轮转 | 轮转策略由 endpoint 声明 |

## 10. 验收

- 同一连接器上两个不同平台会话的事件落在两个资源上，各自分配事件 id，互不串流。
- 未登记的会话收到第一条事件时 adopt 出资源，无需重启或改配置。
- 并发首触同一会话只产生一个资源，第二个请求复用已创建的那一个。
- 出站发送指向未登记会话时先 adopt 再发送。
- 一条会话交接后，同连接器其他会话的 handler 与游标不变。
- 发送省略 `conversation` 时目标是资源自己的会话坐标；`reply_to_event` 跨会话引用被拒。
- 同一平台事件重复到达只产生一条 `event_id`。
- 在事务提交前崩溃，平台重放后只产生一条记录；事务提交后崩溃，事件正文与游标一起存在。
- 未授权节点投递到该会话被 endpoint 拒绝，服务端 ACL 放行也不通过。
- 有未确认事件时交接照常成功：游标随之移动，未消费事件由新 handler 接手。
- 握手成功后新事件进入新 handler；握手失败时冻结期内的事件补投给原 handler，一条不丢。
- 交接后原 handler 的发送被 `revision_conflict` 拒绝，附带当前 revision。
- 确认方不是当前 handler 时，确认不生效。
- endpoint 重启后 chat key 和绑定从盘上恢复，游标不回退到起点。
- 平台游标无法持久化时，明确声明重放窗口，超窗口事件报告缺失。
- 平台发送失败时保留平台原文：平台明确拒绝记 `aborted`，平台结果不明记 `unknown`，两者都把原文放进 `details.source`；agent 看到的是 `pending` 之后的终态，不是接受。
- 未知平台发送者的消息被发送者策略拒绝，不进集群。
- 附件落到工作区，投递给 agent 的内容带本地路径而不是平台句柄。
- handler 不可达时事件留在日志，其他资源的推送与交接都不受影响。
