# RFC 0018：对端获取授权与握手投递

状态：Draft。依赖：RFC 0005、0011、0016、0017。本文是目标契约；`packages/lib` 不读策略，`packages/omp-onlyne` 与 `external-integrations/tern-onlyne` 是参考宿主，符合性以第 7 节场景为准。

RFC 0017 §4 要求每对节点的信任关系「逐对显式建立」。本 RFC 把「显式」扩展为**显式委派**：人类可以预先授权 agent 在界定范围内代替自己确认，同时保留收回授权、逐条复核与撤销的能力。协议线格式不变，库不感知策略；改变的是宿主在提交本地批准之前做什么判断，以及邀请如何抵达 agent。

## 1. 问题

两个现场事实：

- agent 无法自行建立对端关系。`tern-onlyne` 的 `/admin/contact` 与 `/admin/trust/accept` 无条件执行（`external-integrations/tern-onlyne/server/main.ts`），要么人类每次在场，要么整个能力关掉，没有中间态。
- 入站陈述只进日志，不进对话。桥接层收到 `trust` 事件只 `log` 并顺带观察发现记录（`external-integrations/tern-onlyne/server/bridge.ts:106-115`），所以一条 `invited` 行可以停很久而 agent 完全不知道有人敲门。

结果：放开就等于全放开，收紧就等于全收紧；而过早收紧会让对端以为「发了请求没人理」。

## 2. 对端获取策略

宿主维护一个策略，取值三档：

| 取值 | 含义 |
|---|---|
| `all` | agent 可对任意对端发起交换并自动确认任何人送来的陈述 |
| `segment`（默认） | 只对落在允许集合内的对端自动；默认集合为回环（`127.0.0.0/8`、`::1/128`） |
| `none` | agent 不发起、不自动确认；读写分家，写入留给人类 |

规范要求：

- 策略 MUST 在提交本地批准之前求值，约束的是 agent 发起的 `contact`／`trust_accept`／`trust_begin`／发现刷新，以及宿主自动确认。后两项同样是出站请求：不盖住它们，「不向未批准的地址发出请求」就是空话。人类在面板上的确认 MUST NOT 受策略限制：面板是最后一道闸，策略越权不生效于此。
- 策略变更 MUST NOT 回溯已成立的信任。放宽不自动补批历史被拒的行，收紧不自动撤销已有关系。
- 策略是宿主配置，持久在宿主侧。库 MUST 只看到 `accept()` 的有无，MUST NOT 因策略改变任何协议状态机行为。
- 策略判定 MUST 记录为可审计事实：时间、节点、指纹、判定输入（观测地址与声明地址各一份）、命中规则、结论、是否人类超控（RFC 0016 §4 的记录要求同样适用于此）。
- `segment` 的允许集合可配置。把它设成整个私有网段是合法用法，但那等于允许局域网内任意主机与 agent 建立关系，宿主在 UI 上 MUST 明确提示这一点。

### 2.1 判定输入：观测地址，不是声明地址

对端在陈述里写的 `base_url` 由对端自己填写。签名只证明身份，不证明位置，因此**声明地址不能作为策略输入**。

- 判定 MUST 使用观测地址：陈述到达时，宿主按 `(node_id, fingerprint)` 持久记录本次连接的来源地址；批准时用这条记录判定，MUST NOT 在批准那一刻重新取连接地址（二者是不同的请求）。
- 入站观测地址取自 HTTP 请求本身（`Bun.serve` 的 `server.requestIP`）。库在 `receive()` 内同步发出 `trust` 通知（`packages/lib/src/keys.ts:423`），宿主以 `AsyncLocalStorage` 包裹自己的 fetch 入口即可在同一调用栈取到来源地址。
- 出站判定的输入是该 `node_id` 名下**目录里已有的每条记录地址**；一条记录都没有时，用信任行里的 `base_url`（库在 `peerBase()` 里正是这么回退的）。
- 宿主 MUST NOT 为了取得判定输入而调用会先发起探测的 `resolve()`：探测本身就是请求，用它换取「连接目标」等于先向未批准的地址发过一轮。判定必须发生在任何出站请求之前。
- 声明地址与观测地址不一致时，MUST 按观测地址判定并记一条审计（节点、声明地址、观测地址、命中规则）。
- 声明地址的主机部分是主机名而不是 IP 字面量时，MUST 解析后逐地址判定；无法解析或解析结果任一不在允许集合内，即 `policy_denied`。允许集合的条目本身可以是主机名，命中即通过——否则 `bind = "localhost"` 的对端会被永久拒绝，与「回环默认放行」自相矛盾。

### 2.2 自动批准也必须约束出站目标

策略只约束「谁进来」是不够的。库在首次接触时把陈述里的 `base_url` 原样存进信任行（`keys.ts:385` 只做协议检查，`411` 落库），发现记录查不到该节点时，出站连接会回退到这条声明地址（`keys.ts:227-237`）。

还有第二条出站路径：`discovery.resolve()` 会先对该 `node_id` 名下**每一条**发现记录的地址并行重探（`packages/lib/src/discovery.ts` 的 `resolve()` 内 `Promise.all(records.map(... observe(record.base_url ...)))`），而桥接层收到陈述时会用陈述里的 `base_url` 写一条发现记录。于是声明地址即使不进信任行，也会经发现记录变成一次出站请求。

因此自动批准 MUST 同时满足三个条件，任一不满足即记为 `policy_denied`，保留原行，不静默放行：

1. 观测来源地址落在允许集合内；
2. 陈述声明的 `base_url` 落在同一集合内；
3. 该 `node_id` 名下已存在的**每一条**发现记录地址都落在同一集合内。

第 3 条的判定时点是**陈述到达那一刻目录里已有的记录**；宿主随后把声明地址写成的那条派生记录不在判定范围内，否则第 2、3 条会同时成立或同时失效，两条条件退化成一条。

只查声明地址不够：第 3 条是发现目录被写入之后的实际出站入口。否则一个从回环进来的陌生节点只要声明任意 HTTPS 地址，宿主就会主动去取它的 `/keys` 或向它发探测，再把本节点 `node_id`、公钥与指纹送过去。

### 2.3 预置种子（`plugins.trust_seeds`）不在策略范围内

`trust_seeds` 是人类的预授权：配置了种子的对端，其入站陈述在库内直接提交为已批准（`keys.ts:388-389` 与 `408`），宿主一次回调都拿不到，`peers.acquire = "none"` 无法阻止。

本 RFC 明确：种子属于人类动作，不受策略约束；写入种子 MUST 记为一次人类超控审计，且宿主 MUST NOT 让 agent 写入种子。这条与 §2 的「agent 不自动确认」不冲突——绕过策略的是人类，不是 agent。

种子存放在宿主配置文件里（OMP 侧为项目配置的 trust 表，经 `createOnlyneNode` 的 `trust_seeds` 传入）。**配置文件写入面不是策略的管辖对象**：一个能改配置文件的进程可以绕过任何策略。宿主 MUST NOT 宣称策略能约束这一点，宿主 MUST 在启动时输出当前种子清单（节点、指纹、来源文件），让绕过路径可见。

## 3. 握手投递为会话消息

`trust` 事件目前是提示（RFC 0017 §6：事件是提示而非事实来源）。本 RFC 增加一条宿主义务：把需要 agent 知情的信任状态变化投递为会话内消息，与 Onlyne 业务消息共用投递通道与消费语义。

- 投递范围：`invited`（本地未批，等人决策）与 `requested`（本地已批，待对端确认）两种状态 MUST 投递；`exchanged` 与 `revoked` MUST 投递一条状态更新，但不计为待办。
- 只有 `invited` 计为待办并 MUST 唤起一轮：它有可执行动作。`requested` 在等对端，宿主侧没有可做的事，MUST 投递但 MUST NOT 为此唤起一轮，正文里写明在等对端。把 `requested` 也唤起只会占掉一轮而什么也推进不了。
- 消息 MUST 含：对端 `node_id`、指纹、声明 `base_url`、观测来源地址、命中策略与结论、以及可执行的批准／拒绝动作标识。
- 策略已自动批准的，MUST 只投递结果、不投递待办，MUST NOT 向 agent 索取动作。需要人决策或 agent 决策的条目才带动作标识。这两类条目的区别 MUST 在正文里写明，不能靠 agent 自己猜。
- 策略为 `none` 时 MUST 仍然投递：agent 需要知道「有人在敲门而我没有权限」，但只能查看，不能批准。让申请静默挂起是本文第 1 节要消掉的现象。
- 去重键为 `(node_id, fingerprint, phase)`。重复陈述 MUST NOT 重复投递；指纹变化（轮换）MUST 作为新条目重新投递，并在正文标明它是轮换而非首次接触。
- 消费语义与业务消息一致：agent 明确处理（批准、拒绝、忽略）后结算；未结算的条目保持 owed，维护环重投同一 `(node_id, fingerprint, phase)` MUST NOT 产生新条目。
- 投递 MUST NOT 被当作协议事实。宿主漏投或漏消费时，库的下一次维护环收敛；agent 看到的消息是提示，权威仍是 `trust.list` 的阶段投影（RFC 0017 §6）。

### 3.1 动作入口

批准与拒绝必须能从模型入口执行，否则「可执行动作标识」是空话。OMP 侧只保留一个 `msg` 入口（RFC 0008），因此信任动作 MUST 作为 `msg` 的机械 `op` 存在，例如 `op: "trust_accept"` 与 `op: "trust_revoke"`，随 `node_id` 与 `fingerprint` 传入，不经判定直接映射到库接口。

理由：`decider` 的显式分支目前只认 thread `op`、`resource` 与 `scope`（`packages/omp-onlyne/src/decider.ts:868-918`），没有信任动作的位置。机械解析而不是新增一次判定，符合 RFC 0016 §5「引用解析是确定性动作」。

本节只规定「必须有机械入口」，不规定入口长什么样：OMP 宿主把信任动作做成 `msg` 的 `op`，Tern 宿主本来就有 `trust_accept`／`trust_revoke` 导出，直接映射即可。宿主 MUST NOT 为信任动作新增一次判定。

### 3.2 会话归属

握手条目 MUST 落在本节点自己持有的本地 thread 上，成员只有本节点，条目不出网。库只有 thread 这一种容器，本地追加不产生任何对端请求。

- 该 thread MUST NOT 混入业务 thread 树：混入会让业务历史被系统事件切碎，也会让 `in_reply_to` 指向一条没有业务正文的消息。
- 该 thread MUST NOT 出现在 thread 与 joined thread 的列表里，同时 MUST 能被精确引用打开：入站条目自带指向它的链接，链接打不开等于条目读不到。精确引用包括它的 id 与 `owner/id` 两种写法。
- 投递 MUST 带上绑定的 `plan.context`，指向该宿主投递路由实际使用的主会话别名（OMP 是 `main`，Tern 宿主是 `carly`）。有绑定时 `decideInbound` 直接采用、不调判定（`decider.ts:520-524`），两个宿主才对同一件事给出同一个落点。别名以宿主自身路由为准，不要求跨宿主同名。
- 本版不给该 thread 单独的执行上下文。

## 4. 与 RFC 0017 及宿主契约的关系

- §4「逐对显式建立」不变。委派是显式的一种形式：人类先授权，agent 在授权范围内代替确认，人类可随时收回并复核。
- §6 宿主义务新增三条：投递需要 agent 知情的信任变化；持久记录观测来源地址；记录策略判定的输入与结论。
- §7 验收的「同域节点之间未经显式确认不发生任何密钥交换」在 `all` 与 `segment` 下按委派成立：确认由 agent 代为完成，仍在策略范围内显式。策略为 `none` 且未配置种子时该条按原样成立。

### 4.1 需要同步修订的契约条款

下列条款与本 RFC 直接冲突，随本 RFC 一并修订，否则实现方照契约写就会拒绝委派确认：

- 《lib 宿主契约》§5「宿主 MUST 在确认界面同时显示双方指纹……MUST NOT 自动确认或跳过展示」（`docs/contracts/lib-host.md:131`）：改为分档——委派允许自动确认，但自动确认 MUST 记录判定输入与结论、可从审计复核，并 MUST 在面板中可撤销；人类面板上的确认仍须展示双方指纹。
- 《OMP 宿主契约》：增加 `msg` 的信任动作 `op`（§3.1）与握手条目的投递形状（§3）。
- 《OMP 宿主契约》§4：策略属于宿主配置，`[peers]` 表的字段与默认值以本 RFC §2 与 §5 为准。

### 4.2 实现注记（库侧事实，供宿主与契约参考）

- `messages.admit` 的幂等摘要包含 `retry_until`：同一个 idempotency key 的重复投递必然 `id_conflict`。`threads.create` 同理。所以「固定 key 幂等创建」在本版不成立，宿主 MUST 先探测再创建，MUST NOT 把重投当成幂等保障。
- 宿主打包产物优先于源码（`dist/companion.js` 存在时 `host.luau` 跑它）。改源码后必须重建，否则实机继续跑旧代码——这一条写进各宿主的构建说明，不写进协议。
- 信任已 `exchanged`、但发现记录尚未核实的对端，用 `to` 寄不出去：解析只认已核实记录。这是发现层挡在投递路径上，与 §5.1「发现不决定信任」相冲突，按缺陷单独记。

## 5. 宿主接口（参考形状）

配置键（宿主自定义，库不读）：

```toml
[acquisition]
policy = "segment"                      # all | segment | none
allow = ["127.0.0.0/8", "::1/128"]      # 仅 policy = "segment" 时生效
```

配置键的其余部分：种子用顶层 `trust` 表（`[{node_id, fingerprint}]`），两个宿主同名，宿主 MUST NOT 静默丢弃它。

`public_url` 按主机分两种情形，宿主 MUST 先判主机再判端口：

- 主机能在本地绑上（回环或本机网卡地址）：宿主 MUST 绑它声明的端口，`endpoint` 等于 `public_url`；端口被占用时回落临时端口，并把 `endpoint` 改成实际绑定的地址。否则对端存下的地址指向一个没人监听的端口。
- 主机绑不上（外部域名，反向代理部署）：`endpoint` MUST 保持 `public_url` 原样，本地绑定另由 `bind` 决定，启动日志 MUST 标明这是代理声明、本地不监听该端口。这一层不得因为「本地没绑 443」就改写 `endpoint`——那会把代理部署的唯一正确地址删掉。

不带显式端口的 `public_url` 不按 scheme 的隐含端口尝试绑定（本地绑 443 需要特权），判定顺序是主机优先。

表名 MUST NOT 复用 `peers`：OMP 宿主已把 `peers` 列为退役键并在解析时拒绝（`packages/omp-onlyne/src/config.ts` 的 `rejectRetired` 调用 `rejectKey(raw, "peers", …)`，`config.test.ts` 有对应断言）。复活一个退役名会让旧配置被静默地按新语义解释，因此新表另取名字，退役拒绝保持原样。

### 5.1 与 `allow_loopback` 的分工

发现层已有一个默认相反的开关：`exchangeable(value, allowLoopback = false)` 在默认值下排除回环，由 `plugins.allow_loopback` 打开（`packages/lib/src/discovery.ts`）。两者管的事不同，默认相反是设计结果，不是冲突：

| 轴 | 管什么 | 默认 |
|---|---|---|
| `plugins.allow_loopback` | 什么地址可以进入发现目录并成为可探测候选 | 排除回环 |
| `acquisition.policy` + `allow` | 什么对端可以不经人类确认被批准 | 只回环 |

- 发现层不决定信任，获取策略不决定发现（RFC 0011：发现不授予任何投递权或信任）。
- 获取策略 MUST NOT 因为某地址不在发现目录里就自动批准它；发现层 MUST NOT 因为策略允许就放宽 `exchangeable` 的判定。
- 默认组合（排除回环发现 + 只批准回环获取）意味着：远程对端既不会被发现，也不会被自动批准。这是本版意图内的默认姿态，宿主 UI MUST 在调整任一项时说明另一项的当前值，避免「只放宽一处却以为放开了」。

面板 MUST 提供：策略切换、允许集合查看与修改、当前 `invited` 行列表（含指纹、声明地址与观测地址）、逐条批准／撤销、以及人类超控记录。面板动作、agent 动作与种子预授权 MUST 在审计里可区分。

面板的形态不限定：自绘 UI、命令面板（toast 加输入框）、或子命令都算，只要五项能力可达、可回读、且审计能区分人机。密钥轮换也 MUST 有一个可达入口，否则轮换投递路径在生产里不可达、也无法验收。

## 6. 验收

- `none`：agent 调用 `contact`、`trust_accept`、`trust_begin` 与发现刷新均被拒并返回 `policy_denied` + 命中策略；对端 `invited` 行保留，未被置为 revoked。
- 对端先撤销过本节点、陈述被 `forbidden` 拒绝：这不是策略拒绝，也不是本条的「保留 invited 行」，而是对端主动拒绝。宿主 MUST 把它与 `policy_denied` 分开呈现。
- `none` + 已配置种子：该节点陈述仍直接到 `exchanged`，落一条人类超控审计。这是设计内行为，不是策略失效。
- `segment` + 默认允许集合：回环对端自动到 `exchanged`，不产生待办投递；非回环对端停在 `invited`，产生一条待办投递。
- `all`：任意对端自动到 `exchanged`；人类面板仍可撤销，撤销后该节点不再自动重建信任。
- 陈述声明 `base_url` 为外网地址但实际连接来自回环：按观测地址判定，声明地址不在允许集合内，结论为 `policy_denied`，并落审计。反过来声明回环、实际来自外网时 MUST NOT 自动批准。
- 同一条 `invited` 陈述重复送达：只一条待办，不重复提醒；轮换后新指纹产生新条目并标明轮换。
- 人类在面板上批准一条被策略拦下的 `invited` 行：成功，且审计记录为人类超控。
- 策略从 `none` 改为 `all`：历史被拦下的行不自动补批，只对之后到达的陈述生效。
- 策略自动批准时只投递结果条目，agent 未被要求动作。
- agent 用宿主的机械入口（OMP 的 `msg` `op`，或 Tern 宿主的 `trust_accept`）批准一条 `invited` 行：成功，且该条目结算，不再作为待办出现。
- `requested` 条目投递后不唤起一轮：待办列表不因它增加，`invited` 才增加。
- 声明地址是主机名且解析结果落在允许集合内：自动批准；无法解析或任一解析结果在集合外：`policy_denied`。
- 发现目录为空时刷新目录：`segment` 下放行且不产生任何出站请求（没有地址可发，就不违背「不向未批准地址发请求」），`none` 下仍 `policy_denied`。
- 拒绝一条邀请用撤销：本版库没有独立的 reject 入口，撤销是唯一的否定动作。宿主 MUST NOT 把二者说成语义等价，正文里要写明「你拒绝的是这条邀请」而不是「你撤销了一段关系」；库补上 reject 之后两者再分开。
- `public_url` 指向外部域名（代理部署）：`endpoint` 保持声明值，本地不绑该端口，启动日志标明代理声明；指向本机地址时端口被占用：`endpoint` 改成实际绑定地址并记日志。

- `node_id` 名下已有一条外网发现记录、本次陈述来自回环：结论为 `policy_denied`（第 3 条条件不满足），且 MUST NOT 向该外网地址发出探测或取钥请求。
- 宿主配置里出现 `peers` 表：启动即报退役错误，MUST NOT 把它当成 `acquisition` 读取。
- `allow_loopback` 为假且 `policy = "segment"`：回环对端可以自动批准，但不会出现在发现候选中；宿主 UI 同时显示两项当前值。
- 启动时输出种子清单：每个种子的节点、指纹与来源文件各一行，且该清单可从日志复核。

已知不覆盖：反向代理后的真实来源地址；DNS 解析与实际连接目标不一致（出站只按 `resolve()` 返回值判定）；跨主机的地址判定细则。宿主 MUST 在 UI 上提示这些限制。
