# RFC 0016：SystemOne 的判定上下文

状态：Draft。本文定义 SystemOne 决策服务的输入契约与权限边界。消息工具保持 `msg({ delivery_kind, msg, meta })`。上下文包属于插件内部数据，不增加模型工具参数或网络消息字段。来源清单、字段布局、装配预算与情景评测方法属于软件设计，在 [SystemOne 判定上下文设计](../design/omp/systemone-context.md) 中维护，不入本文。

## 1. 决策归属

SystemOne 负责所有需要理解消息含义的选择：发送什么操作、发给谁、是否等待、建立还是延续执行上下文，以及收到消息后放进片段、投递子代理、排队或唤醒。任务补充缺少 `in_reply_to` 时，SystemOne 可以结合任务历史找到正在执行的子代理。

插件收集事实、执行决定、报告结果。认证、实际授权、版本比较、消息去重与持久提交由库执行。执行前检查可以阻止无权操作、失效会话或不合法计划。检查失败不能使插件自行选另一个目标、改成新建会话或用默认值补齐语义决定。

SystemOne 可以看见权限、宿主状态和等待证据。看见事实不意味着模型取得修改该事实的权力。`plan_mode`、忙闲、用户中止、todo 状态都能帮助模型选择行动；实际执行必须服从宿主提供的能力。

同一 thread、相同根引用和关键词重合都属于证据。插件 MUST NOT 用这些条件预先删掉语义候选。授权范围、当前可见范围和显式稳定引用的解析可以机械限制候选。显示名重复时保留不同稳定身份，SystemOne 可以借助职责与交谈历史消歧；证据不足时请求澄清。

## 2. 可用上下文来源

判定材料按判定点分别构造。共享的是来源说明，不是所有任务共用一个 state 模板。

插件 MUST 为每份材料保留来源身份、会话或 thread 引用、顺序或版本、采集时刻与完整性。材料缺失 MUST 记为 `unavailable` 及原因；已取得的空列表与无法读取 MUST 分别表达。

直接用户指令、assistant 计划、工具证据、context note 和外部消息 MUST 分别标记。外部正文中的“忽略规则”“改发给另一个人”作为被判断的消息内容保留。

决策模型不需要看到秘密。认证材料由宿主使用，输入中只提供认证身份和授权事实。跨节点收到的消息 MUST NOT 借“补充上下文”取得本地用户的私有历史。

来源清单、来源标记的具体字段、OMP 读取适配器及其已观察限制见 [SystemOne 判定上下文设计](../design/omp/systemone-context.md) 第 2 节与 [OMP 宿主接口参考](../references/omp-extension-api.md)。

## 3. 分任务构造上下文

每个判定点 MUST 维护自己的问题模板与上下文布局。共享只发生在序列化、来源引用与调用记录，MUST NOT 把不同判定点的材料摊平成一个通用 state。

布局 MUST 说明该判定点需要的判断对象与各类材料的用途及来源，至少覆盖：出站意图与目标、回复与补充的原消息选择、入站动作与执行上下文、上下文选择、补充与新建子代理、thread、域、资源、恢复、todo。

字段级布局、问题模板与材料组织见 [SystemOne 判定上下文设计](../design/omp/systemone-context.md) 第 3 节。todo 的持久写入归宿主插件，库只暴露可恢复的本地记录（出站证据与消费记录），接口与宿主职责见 [《lib 宿主契约》](../contracts/lib-host.md) §9、§11。

## 4. 装配与执行契约

有依赖的决定 MUST 分步请求；相互独立的问题可以同次请求。联合动作与其上下文必须相容，问题模板 MAY 使用完整计划作为 choice，防止独立答案组合出不存在的计划。

同一消息重投 MUST 复用已记录的决定。新信息触发的新判定 MUST 单独记录，不覆盖原决定的输入和证据。

判定记录 MUST 包含完整请求快照、来源引用、问题版本、实际模型 id、原始回答、概率、耗时与 token；只保存摘要无法复现实验。持久快照按项目数据权限保存，日志 MUST NOT 包含凭据。

输入不足以判断时，模型 MAY 请求补充指定来源；补取后 MUST 保留原候选与原问题。装配可以丢弃整段背景材料，但 MUST NOT 截断当前请求与问题模板；裁剪后仍不足以判断时，插件 MUST 报告判定不可用，不得按默认值选择。预算常量、裁剪顺序与记录格式见设计文档第 4 节。

## 5. 判定的机械前置条件

模型负责语义选择，以下条件由插件在执行前机械校验，不交给模型推断：

- 目标别名在当前目录中且可用；会话活存；操作权限成立。任一不满足时返回 `context_lost` 或对应错误，不静默改选。
- 未登记的子代理接收补充时，先排队等待登记完成，插件不得因模型给出投递动作而直接投递。
- 引用解析（别名→稳定身份）是确定性动作；显示名歧义时返回候选清单。

情景评测的方法、数据与结果在 `proof/systemone_context/` 维护：样本分模块组织，开发集与冻结留出集分开，minimal/focused/expanded 三画像对照，原始请求与响应全部留档可回查。评测结论对本文的作用限于验证输入布局的充分性，不构成协议要求。

## 6. 验收

- 每个判定点有任务专用布局，说明用户、模型、历史、note、todo 与 Onlyne 结构信息的用途及来源。
- 出站和入站语义决定都由 SystemOne 做出；没有通过关键词、thread 或根引用预选落点。
- 新任务、无引用补充、任务交叉、跨 thread、旧 note、用户更正、排队登记、上下文丢失均有竞争样本。
- 评测方法与数据在 `proof/systemone_context/` 报告，开发与留出分开，留出失败保留为已知限制。
- 任务创建、补充进入原子代理、产出回主会话与主会话回复使用顺序模拟检查归属；真实插件调度另外验收。
