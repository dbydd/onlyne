# RFC 0013：计算作业资源节点

状态：Draft。依赖：RFC 0001、0006、0011、0015。

## 1. 定位

计算服务是作业驱动型资源节点。提交只表示请求被受理，不表示作业运行成功。提交回执、作业事件和最终产物是三个独立事实。

| 事实 | 谁确认 | 含义 |
|---|---|---|
| 提交受理 | 计算服务 | 作业已进入队列，参数已校验 |
| 作业状态变更 | 计算服务 | 排队中、运行中、已完成、失败、取消 |
| 产物可用 | 计算服务 | 产物已写入可寻址位置 |

三者独立。受理不代表运行成功，运行成功不代表产物可取。取消请求与取消生效也是两个事实。

## 2. 资源模型

作业是计算服务管理的一类资源。作业提交后得到稳定引用：

```json
{
  "job_ref": {"owner": "urn:onlyne:compute:lab", "id": "job-42"},
  "kind": "compute_job",
  "submitter": "urn:onlyne:agent:lazuli",
  "state": "queued",
  "operations": ["read", "cancel", "list_events", "transfer", "describe"],
  "requires": ["compute_submit"]
}
```

作业 id 由计算服务分配。提交方不指定 id，只用 `operation_id` 做幂等。重投同一 `operation_id` 返回原 `job_ref`，不创建第二个作业。

作业状态由计算服务自己报告：

| 状态 | 含义 |
|---|---|
| `queued` | 已受理，等待资源 |
| `running` | 正在执行 |
| `completed` | 正常结束，产物可用 |
| `failed` | 执行失败，原因由服务报告 |
| `canceled` | 已取消 |

Onlyne 不为作业建立第二份状态机。本地保存的是对端报告的快照和事件游标。

## 3. 三项授权分离

作业有三项彼此独立的授权：

| 授权 | 授予什么 | 变更操作 |
|---|---|---|
| 事件接收 | 谁能收到作业状态事件 | `transfer_events` |
| 结果接收 | 谁能读取产物 | `transfer_results` |
| 控制权限 | 谁能取消、修改、重新提交 | `transfer_control` |

三项可以分别授予不同节点。交接操作必须指明变更哪几项，未指明的保持原样。

- 提交者默认持有全部三项。
- 只转观察订阅不改变提交者的控制权。
- 删除一方的结果接收权不影响作业继续运行。
- 取消作业需要控制权限，观察者不能取消。

```json
{
  "resource_ref": {"owner": "urn:onlyne:compute:lab", "id": "job-42"},
  "submitter": "urn:onlyne:agent:lazuli",
  "event_recipients": ["urn:onlyne:agent:lazuli"],
  "result_recipients": ["urn:onlyne:agent:lazuli", "urn:onlyne:agent:dpdp"],
  "controllers": ["urn:onlyne:agent:lazuli"],
  "revision": "rev-a"
}
```

授权表是计算服务的局部状态。转交排队中或执行中的作业时，提交者、计费和配额归属保持原记录。新增结果接收者不重新提交作业。

## 4. 提交

```json
{
  "operation_id": "op-01",
  "retry_until": "2026-10-23T04:00:00Z",
  "operation": "submit",
  "data": {
    "spec": {"image": "lab/train:3", "command": ["python", "run.py"]},
    "artifacts": ["/abs/path/data.parquet"]
  }
}
```

校验顺序：

1. 认证调用方，确认它有 `compute_submit` 授权。
2. 校验 `data` 匹配提交 schema。
3. 按 `operation_id` 查重。命中返回原 `job_ref`。
4. 受理并返回 `job_ref` 和 `state: "queued"`。

提交返回的是受理事实。作业何时完成、是否成功、产物在哪，都由后续事件和查询回答。

产物引用在提交时声明为路径清单。计算服务按授权读取这些路径，不承担文件传输。产物输出由服务声明为可寻址位置，接收方凭结果接收权读取。

## 5. 事件与产物

作业事件经 SSE 送达：

```text
id: 902
event: job_event
data: {"job_ref":{"owner":"urn:onlyne:compute:lab","id":"job-42"},"event_id":"77","state":"running","at":"2026-10-23T03:10:00Z"}
```

- `event_id` 由计算服务在该作业内分配，十进制递增字符串，不复用。
- 事件只承载状态和引用。产物内容经 `read` 操作取，不塞进事件。
- 事件按授权过滤：只有事件接收者收到推送。

产物寻址：

```json
{
  "artifacts": [
    {"name": "model.ckpt", "uri": "https://lab.example/artifacts/job-42/model.ckpt", "size": 1048576}
  ]
}
```

产物 URI 是数据位置，不授予访问权。读取产物需要结果接收授权，授权在每次读取时检查。

## 6. 取消

取消请求与取消生效是两个事实。

```json
{
  "operation_id": "op-02",
  "retry_until": "2026-10-23T05:00:00Z",
  "operation": "cancel",
  "expected_revision": "rev-a"
}
```

- 取消需要控制权限。
- 已终态的作业返回 `invalid_request`，`details` 说明作业已结束并附原状态，保留服务原文。作业终态不复用 thread 的 `thread_closed`。
- 取消受理后作业进入 `canceled` 或保持原状态直到真正停止。协议不承诺取消立即生效。
- 已产生的产物在取消后是否保留由计算服务声明。

## 7. 交接

按 RFC 0006 §5 的五步执行，并遵守 RFC 0006 §6 的积压前置条件。计算作业的交接只变更授权表，不迁移作业本身。

- 计算服务继续持有作业。
- 交接提交是生效点。提交前的事件保留首次接收者，提交后的新事件取提交后的授权表。
- 交接提交前，未确认事件必须先由原接收者确认或按保留期给出终态，使积压为零；有积压时提交返回 `conflict`。协议不提供把积压转给接手者的操作。
- 已经接收的事件留在原接收者。接手材料包含 `cutoff_event_id` 之前、目标仍需读取的事件引用和该截点，只给引用，不给接收责任。

三项授权分别交接时，一次交接可以只改一项。并发交接只有一个能基于同一预期 revision 成功。

## 8. 恢复

### 计算服务重启

重启后从持久记录恢复作业状态、授权表和事件游标。作业状态由计算服务报告，本地快照缺状态时标记为本地 `unknown`，不写成服务报告的状态，也不假定仍在运行。

计算服务 MUST 持久化授权表。授权表丢失时，已授予的接收权和观察订阅无法恢复，只能按提交者重建并明确报告降级。

### 事件恢复

事件游标必须持久化，与事件分配同一事务。断开期间的事件按游标补齐。无法补齐的事件明确报告缺失。

`transfer` 操作本身按 RFC 0006 §1 与 RFC 0001 §5 的重投规则处理。交接邀请作为消息送达目标，目标回复的落点由本地绑定决定。

### 产物恢复

产物 URI 在作业完成后保持可寻址。保留期限由计算服务声明。过期后 `read` 返回 `not_found`，不把同一 URI 分给其他作业的产物。

产物已在但接收方未收到通知时，按 `job_ref` 查询可重新发现。协议不要求推送可靠。

### 未确认投递

计算服务与集群链路之间的未确认投递在新连接建立时重新入队。重放可能产生重复事件，下游按 `event_id` 去重。

### 已取消与已失败

取消生效后作业不再产生新事件。已产生的事件保留可查。失败作业的产物按服务策略处理，部分产物可用时明确标注。

## 9. 与 IM 资源的区别

| 维度 | IM 会话（0012） | 计算作业（0013） |
|---|---|---|
| 事件来源 | 平台推送 | 作业自身执行 |
| 处理者 | 单一 assignee | 事件接收、结果接收、控制三项可分离 |
| 交接内容 | 切换 assignee 和发送权 | 变更授权表中的指定项 |
| 凭据 | 平台令牌留在 endpoint | 提交者提供的输入路径 |
| 产物 | 平台消息 | 可寻址的作业产物 |

计算服务的三项授权分离是它与 IM 资源的主要差别。IM 的 assignee 是单一人选，计算的接收关系可以是一组节点。

## 10. 验收

- 提交重投同一 `operation_id` 返回原 `job_ref`，不创建第二个作业。
- 提交受理与作业完成分别报告，受理不被当作成功。
- 三项授权分别变更时，未指定项保持原样。
- 只转观察订阅不改变提交者的控制权，观察者不能取消作业。
- 取消需要控制权限，已终态作业的取消被拒绝并保留原文。
- 交接提交后新事件进入新接收者，已接收事件留在原接收者。
- 产物 URI 需要结果接收授权，未授权读取返回 `not_found`。
- 计算服务重启后作业状态和授权表从持久记录恢复，未恢复的标记 `unknown`。
- 事件游标持久化，断开期间可补齐，补不齐的明确报告缺失。
- 产物过期后 `read` 返回 `not_found`，不把 URI 分给其他作业。
