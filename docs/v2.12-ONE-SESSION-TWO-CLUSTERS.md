# One session, two clusters

A resident `pi` process can serve one role in more than one cluster at once. The shape that
needs it: a centre cluster owns the work, a member cluster owns a slice of the same work, and
the same role — same name, same key, same person — is the representative on both sides. Today
the plugin mounts one socket and the second cluster is reachable only by shelling `onlyne
--server-root` from the model, which puts an operator's tool in the model's hands and leaves
inbound work on the far side unread.

This document settles the mount model, the routing rules, the process-lifetime rule, and the
two defects that made a lost message invisible.

## 1. Scope

`pi-onlyne` only. The core does not change: a client still registers one role in one cluster,
the server still routes by role within its own spec, and the adapter protocol still carries one
`assign` per delivery. A mount is one client link; several mounts are several links in one
process. Nothing about the server's ACL, the ledger, or the federation of aggregates changes.

## 2. Configuration

`.pi/onlyne.json` gains `mounts`, an array. The existing single-value keys (`role`, `cluster`,
`workspace`, `sessionId`) keep working and mean a one-element list, so a file written before
this key existed reads exactly as it did.

```json
{
  "mounts": [
    { "role": "lazuli", "cluster": "daily-workbench", "workspace": "…/daily-workbench/lazuli" },
    { "role": "lazuli", "cluster": "research-chamber", "workspace": "…/ResearchChamber/lazuli" }
  ]
}
```

| key | required | meaning |
|---|---|---|
| `role` | yes | the role this mount registers as |
| `cluster` | no | the serving cluster's `[server] name`; unset falls back to the workspace tree |
| `workspace` | no | the role workspace, when the body runs outside it; relative paths resolve against the pi working directory |
| `sessionId` | no | the session id this mount registers; unset reuses the session that mounted the plugin |

A malformed entry is skipped with one warning line naming its index, and the rest still mount:
one typo must not take a working link down. An empty `mounts` array falls back to the single-key
shape.

Multi-mount applies to a **resident** plugin only. A session the client spawned carries
`ONLYNE_TASK_ID` and one client's socket path in its environment; a second mount there would
mean a second client spawning the same process, which the client does not do and the plugin
must not invent.

## 3. Routing out

Every mount holds its own `OnlyneAgent`, and therefore its own `welcome`, roster, heartbeat,
reconnect and task table. Tools are registered once and route by target.

**`onlyne_send({ to })` and `onlyne_handoff({ to })`** accept two spellings:

- `cluster:role` — the mount serving that cluster, with that role as the recipient. An unknown
  cluster is refused with the list of mounted clusters.
- a bare `role` — the mount that owns the work in flight. With no work in flight and exactly one
  mount, that mount. With no work in flight and several mounts, the call is refused and every
  mount is listed, because the plugin has no roster to prove which cluster holds the role: the
  adapter socket answers `query_roles` for the client's own role only, and inventing a roster
  would be a guess.

**`onlyne_complete` and `onlyne_handoff`** go back to the mount that delivered the task. An
optional `cluster` parameter disambiguates when two mounts have work in flight at the same time;
without it the plugin resolves the single mount holding an open task and refuses when there is
more than one. A reply never leaves on "the first mount".

## 4. Routing in

An `assign` from any mount enters the same session. Nothing about the delivery text changes —
the client still renders it — but the delivery card names the mount, so the model can tell
which layer handed the work over and can name the cluster when it replies:

```
From dpdp · task · 3f2a91c8
via daily-workbench

<delivery text>
```

The `via` line appears only when the plugin holds more than one mount; a single-mount session
prints exactly what it printed before.

Heartbeats, reconnect backoff, `reclaim` and duplicate suppression stay per mount. One client
disconnecting does not touch another's session row, and the plugin does not retire a session
because a sibling link went away.

## 5. Process lifetime

A multi-mount session is resident by definition, so it never ends the process on a completion.
`complete` suppresses its exit, and `recycle` from one mount stops that mount only; the process
exits when the last mount is gone, or when the operator closes it. The single-mount rule is
unchanged: `oneshot` leaves, `task` and `role` stay.

Without this, a `oneshot` mount's completion would kill the process and take the other cluster's
session with it — the same defect the scope rules already forbid across sessions.

## 6. Prose and ACL

Each mount carries the prose its own `welcome` delivered. Both are written into the run's
instruction layer:

- identical prose from two mounts is written once — one fact repeated is not two facts;
- different prose from two mounts is written once per mount, each headed with its cluster, so
  neither role spec silently replaces the other.

ACL is not merged and cannot be: each server authorizes its own link against its own
`allowed_targets`. The plugin adds no second check and passes each server's refusal through.

## 7. A refusal is not a delivery

Two defects made a message that never arrived look sent. Both are fixed here.

- **The plugin claimed delivery for a queued send.** `sendFromTool` answered `sent to X`
  whenever the local call returned, including the client's `{queued: true}` answer for a send
  that only reached `client.db`. The tool now reports the two cases differently: `sent` only
  when the server took the envelope, `queued locally` when the client parked it, and a thrown
  error carrying the server's own code and message when it refused.
- **The client deleted a permanently refused intent without a trace.** A refusal in
  `PERMANENT_ERRORS` (`acl_denied`, `conflict`, `forbidden`, `unknown_role`, `not_admin`,
  `bad_frame`, `frame_too_large`, `protocol_version`) removed the intent row and left one
  `tracing` line. `invalid` is deliberately not on that list: the server answers it for
  conditions a retry clears, and exhaustion keeps the row visible as a fault. Nothing
  durable recorded the loss, so a lost message was invisible to `onlyne fault`, to the
  ledger, and to the operator. The intent machine now records an `intent_dropped` fault
  (task, code, message) before it deletes the row, which also appends a `Report::Fault`
  event, exactly as an exhausted intent does.

Those two defects compounded into the reported symptom. With the link down, `forward` parks
the envelope and answers `{queued: true}`, which the tool called "sent"; the client later
flushes the row into a permanent refusal and deletes it. Nothing anywhere said the message
was gone. A live link already returned the refusal to the plugin as a refused body — that
half was never broken.

## 8. Acceptance

The member cluster's live tree can prove every clause:

1. one `pi`, cwd in the member cluster, `mounts` naming both clusters;
2. `onlyne roles` in both clusters lists the role online with one attached session;
3. a task from the member layer and a task from the centre layer both reach the one session,
   and each completion lands in the ledger of its own cluster;
4. `cluster:role` and bare `role` both resolve; an ambiguous bare role is refused with the
   clusters listed;
5. a deliberately wrong ACL makes `onlyne_send` throw with `acl_denied`, and the client records
   an `intent_dropped` fault;
6. killing one client leaves the other mount's session attached and able to work.
