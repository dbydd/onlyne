# 视图会把一条 `rejected` 一直显示成 `waiting`

状态：**已修复**。2026-10-16 由 alexandria 集群 supervisor 提交（omp 会话）。
现场：server 账本读该行是 `rejected: task_settled`，而**同一个 server** 的视图
（`GET /api/view`，web 与 TUI 共用的那个 reducer）读它仍是 `in_flight`，
于是看板上那张卡片停在 `waiting`。

> **修复记录（2026-10-17）。** 采纳 §A，并对范围做了一处收缩：账本里的终态没有出边
> （`onlyne-store/src/lib.rs:25-35`），所以只采纳「视图非终态 → 账本终态」，连同
> `reason` 与 `acked_at`。非终态之间的分歧可能是愈合读跑在事件之前，采纳会回退正确
> 状态，因此不动。`outcome` 不参与对账，账本没有这一列。
>
> 前端武装点也修了，否则只改 reducer 修不到：web 的 `needs_heal` 原先要求行缺 family，
> 一个已愈合的行再丢终态事件就永不再武装；现在每个 `ledger_state` 事件都武装一次
> 250 ms 去抖读（live 流与 subscribe 回放页都算）。TUI 原先**没有**愈合路径，现在同样
> 武装一次性读并通过新的 `Event::Ledger` 喂给共享 reducer。仍然没有轮询。
>
> §B 的半帧怀疑**不成立**：`onlyne-wire` 的 `FrameReader` 把已读字节放在结构体字段里，
> `next` 只 await cancel-safe 的 `read_buf`，超时与 `select!` 取消都不会丢半帧。
> §C 的自检出口没有加。
>
> 回归：`crates/onlyne-proto/src/view.rs` 的
> `a_ledger_read_recovers_a_missed_settlement_without_reverting_live_events` 覆盖三个终态、
> 保持 `outcome`/事件尾不动、以及不把终态改回非终态；既有「只填缺失列」用例继续通过。

## 一句话

一条 `ledger_state` 转换如果在**订阅链路上丢掉一次**，视图就永久停在旧状态：
愈合路径只补「因果列」（family/hop/时间…），**从不改 `state`**；
而全量重建只在 `subscription` 为 `None`（链路出错重连）时才跑。
只要链路一直 `live`，这个错就没有任何一条路径能修回来。

## 现场（两处读数，同一个 server）

```text
$ onlyne ledger --server-root <root> --msg-id 81b5e247-df6e-420e-91f1-3d524ec044a3
state=rejected  reason=task_settled  acked_at=null   ← 账本

$ curl -s "http://127.0.0.1:56692/api/view?token=<token>" | jq '.view.deliveries["81b5e247-…"]'
{ "state": "in_flight", "reason": "task_settled", "acked_at": null,
  "kind": "completion", "hop": 6, "family": "051c77f6-…", "outcome": null }   ← 视图
```

同一条行里 **`reason` 是新的（`task_settled`）、`state` 是旧的（`in_flight`）**。
看板据此把它排进 `waiting`（`Card::column`：`InFlight` + 会话非 `Busy` → `Waiting`），
操作员读到的是「已交出、还没人干」——**真相是「被拒了」**。

全量对照：当时视图 314 条投递行 vs 账本 442 条，**state 不一致的只有这一条**。

```bash
# 一条命令复现这条对照（vuew 的 token 在 onlyne-web 启动时打印在 URL 里）
onlyne ledger --server-root <root> --msg-id <id>          # state=rejected
curl -s "http://127.0.0.1:<port>/api/view?token=<token>"  # .view.deliveries["<id>"].state
```

## 机制（哪一步该修而没修）

订阅链路（`crates/onlyne-web/src/admin.rs:136-284`）只有两条更新路径：

1. **折事件**：`Event::LedgerState(reported) => stored.absorb(reported)`
   （`onlyne-proto/src/view.rs:793-800`）。`absorb`（同文件 `256-265`）**确实会写
   `state`** —— 所以只要这条事件折进来过，状态就是对的。**它没折进来。**
2. **愈合读**：`read_ledger` + `View::merge_ledger`（同文件 `661-670`）。
   而 `absorb_causality`（`281-295`）只对 `family / hop / origin / attempt /
   out_head / enqueued_at / acked_at / reason` 做 `fill_absent`，
   **没有 `state`**。文档也这么写：「fills those columns and touches nothing else」。

于是三条合起来构成缺口：

- **愈合不修状态**：`merge_ledger` 读的是账本全量行，手里就有正确 `state`，
  却按设计不碰它；
- **只有重连才全量重建**：`view = snapshot_to_view(&snapshot)` 只在
  `subscription.is_none()` 的分支里跑（`admin.rs:214-229`）；链路一直 `live`
  就永远不跑；
- **没有任何「我漏了一帧」的信号**：服务端只在订阅者落后于事件环时才发
  `resync_lag`。本次事件环完整（保留 seq 1..2846，无缺口），
  `onlyne history` 全文里 `resync_lag` 计数为 **0**，所以链路不认为自己脏。

一个可查的怀疑点：读帧的超时被当成「什么都没发生」。
`admin.rs:204-206` 是 `Ok(_) | Err(ExchangeError::Timeout) => {}`，
而 `FrameReader` 是带缓冲的流式读——**超时落在半帧中间时，已消费的头部/半截体
既没交给 `update`，也没有留下任何痕迹**，下一次读从残局继续。
单个事件丢失、且只丢一个，与这里的行为吻合。
（此段是**待验证的怀疑**，不是已证结论；请以链路日志或给 `FrameReader` 加断言来确认。）

## 影响面

- **中高**。症状不吓人但会骗人：看板把一个**被拒**的投递画成**等待中**，
  于是「有活卡住了」和「有活被吞了」在屏幕上长得一样。本例里被吞掉的正是
  本族的定稿放行（见 `v2.6-TASK-SETTLED-SWALLOWS-THE-LAST-HOP.md`）——
  **两个缺陷叠在同一行上**：server 把它判成 `rejected`，视图又把它画成 `waiting`，
  操作员两次都读不到真相。
- **不会自愈**。只要 web 进程/链路不重连，这条行就一直错下去；
  重启 web 进程会好——**所以它也很容易被当成「偶发显示问题」放过去**。
- **面窄但重复可期**：314 行里 1 行，比例低，但只要链路丢帧就可能再出现一条，
  且每次都要人工去比对账本才发现。

## 三个可改点（按性价比排序）

### A. 愈合读把 `state` 一起对齐（最小）

`absorb_causality` 现在是「只填空」。给它加一条**只在不一致时**写 `state` 的分支：
账本是权威（它是折叠的数据源，也是 `onlyne ledger` 的答案），
视图里的 `state` 与账本不符就以账本为准；`reason`/`acked_at` 同理。
这样把「填因果」升格为「对账」，`merge_ledger` 那一跳就变成一次真正的 reconcile。
要点：**只在 live 链路空闲时跑**（现在是 250 ms 去抖后跑一次），别让它成为轮询。

### B. 半帧超时要留痕，不能吞

`Ok(_) | Err(ExchangeError::Timeout) => {}` 这条臂要能区分
「本次没有帧」与「读到一半断了」。后者应当作链路错误处理（重连 + 全量重建），
至少也要计入一个可读的计数，让运维看得见丢帧。

### C. 给视图一个「与账本不一致」的自检出口

对操作员来说，现在唯一的办法是手工 `curl /api/view` 再和 `onlyne ledger` 逐行比。
建议加一个只读查询（或 `status` 里加一格）：**视图里 state 与账本不符的行数与行 id**。
这既是自检，也是本缺陷以后复现时的第一条证据。

## 与现有语义的关系

- 视图是「快照 + 事件折叠」的投影，设计上**不承诺**与账本逐行一致
  （`docs/v2-PLAN.md` 的 one-model-two-renderers）；本 draft 不推翻这一点，
  只主张**当两者不一致且不一致可检时，操作面要有机会被告知**——
  现在的缺口是「不一致永远不可检、也不会自愈」。
- 与 `v2.6-TASK-SETTLED-SWALLOWS-THE-LAST-HOP.md` 同源同帧：那条讲**为什么这条行被拒**，
  这条讲**为什么视图还在说它在飞**。两条一起看才还原当晚那一行的全貌。
