# v2.11 — Lifecycle is declared, not inferred

状态：实现已落地，主验收使用独立联邦集群副本。

## 0. 这份文档回答什么

集群运行至今的故障分成两类：**路由问题**（一条消息去了哪里）和**生命周期问题**（谁还活着、谁拥有什么资源）。本文只处理第二类。

这一类的每次故障，形状都相同：**一个已经存在的声明被消费者丢掉了，消费者改用环境推断身份和存活。** 于是每修一个场景就加一条守卫，守卫之间再互相踩。

本文把这个形状写成契约，并给出四类修复：会话归属、插件身份、服务端持有式空拉取，以及网关保留尚未消费的后端事件。它不新增 wire 字段、不做迁移、不做兼容层。

## 1. 故障的共同形状

| 观察 | 被当成 | 实际情况 |
|---|---|---|
| 一条插件连接关闭 | 整个 role/session 退出 | 一条连接结束，同会话可能还有别的连接 |
| 最后一条连接关闭 | 保留作用域的会话退出 | 声明了 `resume` 的会话可以挂起并由后续交付恢复 |
| 会话自己的首条交付已完成 | 会话退出 | 槽可能仍由 `task` 或 `role` 作用域保留 |
| 网关启动时等待后端列表答复 | 后端没有入站消息 | 答复前到达的事件被请求循环读走并丢弃 |
| 一个 task 子会话进程退出 | 主管 resident 退出 | 一个子会话结束，主管进程与连接都还在 |
| cwd 下 `.pi/onlyne.json` 声明 `resident` | 这个进程就是 resident | 任何同 cwd 会话都能冒用这个声明 |
| `hold_ms` 被请求、空拉取立即返回 | 空闲 | 客户端在忙循环，服务端从未挂起 |
| 会话的最后一条连接消失 | 会话 `exited` | 传输事实，不是所有者判决 |

两类误用贯穿全部五条：

- **身份靠环境推断**：cwd、进程、socket 被当成"我是谁"的依据。
- **存活靠传输推断**：连接关闭、进程退出、工厂重入被当成"谁还活着"的判决。

在一个 role 可以对应 N 个进程、N 条连接、N 个会话的系统里，这两类推断都不成立。

### 已发生的两次

**`caerulea-main` 被误标 `exited`（2026-10-19 17:55:08Z）。** 父 omp 进程存活、父连接仍在，但一个 task 子会话被空闲回收时：

1. 子会话的插件工厂是新实例，`boundSessionId === null`，resident 分支的守卫只在 `boundSessionId !== null` 时比较，于是放行；子会话用同 cwd 配置开了一条冒用 `caerulea-main` 的连接。
2. 子会话 `session_shutdown` 发 `detach` 关闭自己那条连接。
3. 客户端 `release_connection` 只看同名 slot 是否服务中，不看是否还有别的连接声明同一会话，直接 `feed_agent_gone` + `feed_resource_closed`，服务端镜像成 `exited`。

**IM 网关存在无等待的空拉取路径。** `onlyne-im` 每轮 `pull` 都带 `hold_ms: Some(20_000)`，服务端未使用这个字段，空队列立即回空；客户端拿到空列表后立即发起下一轮。2026-10-20 的现场采样记录了 `lo0` 约 6.6 万包/秒，ENER 报告 server 与 IM 的 CPU 时间合计约 1 核。该接口计数覆盖全部本地环回流量，不能直接换算成 Onlyne 的 RPC 次数。现场二进制的调用栈缺少符号，尚不能按函数归属 TLS、JSON 与 SQLite 的 CPU 成本。

## 2. 规则

> **身份与存活由所有者声明；传输事件只是证据，永远不是判决。**

五条推论，分别对应连接归属、作用域保留、插件身份、事件读取和空拉取：

1. **一条连接只代表它自己。** 会话是否结束，由声明了它的连接判断；一条 parked 连接的离开不是会话的终态。未声明该会话的 `standing` 连接不参与保活。
2. **resident 挂载读取运行时声明的会话身份。** OMP 的 `ctx.agent.kind === "sub"` 标识子会话，子会话不得注册父会话的连接和工具。主会话的 `/new`、`/resume` 沿运行时的会话切换事件更新绑定。
3. **挂起能力由运行时声明。** 会话槽记住连接声明的 `resume` 能力；连接离开后，清理扫描按槽的绑定和保留策略判断是否挂起或退出。
4. **请求期间到达的异步事件仍属于事件循环。** 网关请求后端会话列表时，先到达的事件暂存在 `BackendHost`，答复返回后再交给事件循环。
5. **空拉取由服务端等待。** `hold_ms` 指定等待窗口；挂起期间连接必须仍能承载 `report`、`ack`、`send` 与 `ping`。

## 3. 声明本来就在，只是被丢了

这是本次修复成本低的根本原因。三处需要的声明都已经在线上传输或已经在配置里：

| 声明 | 现在的位置 | 消费者怎么丢的 |
|---|---|---|
| 这条连接为哪个会话挂载 | `hello` 的 `mount.session`（`crates/onlyne-proto/src/adapter.rs`），客户端在 `serve.rs::hand_over` 已经拿到 `session_id` | `park_transport(io, capabilities)` 只存两元组，会话名被丢弃；认领后又写进以交付 id 为键的 `transports`，别名无处可读 |
| 这个进程是不是 resident | 插件的 resident 配置与会话自身 id | 守卫写成 `boundSessionId !== null`，新工厂实例恒为 `null`，等于没有守卫 |
| 这个会话能否在释放后恢复 | agent 挂载的 `Capability::Resume` | 清理扫描在连接离开后才询问能力，活连接的 `transports` 已无此声明 |
| 会话当前服务的交付 | 槽上的绑定与 `keeps_idle` | 部分终态判断只读会话 id 对应的首条交付；`Done` 被误读为会话退出 |
| 后端已经发送的入站事件 | 后端帧流中的 `BackendOp::Event` | 网关的列表请求循环把非列表答复的帧读走并丢弃 |
| 这次拉取可以挂起多久 | `PullArgs.hold_ms` | `relay::pull` 末尾 `let _ = args;` |

所以修复不需要新的 lease 类型，也不需要新的 wire 字段：**把已经声明的东西留在原地，并在判断时读它。**

## 4. 修复

### 4.1 客户端：会话终态只由声明了该会话的连接判定

**文件**：`crates/onlyne-client/src/session/dispatch/{state,transport,retire,delivery,slots,idle,reports/tests}.rs`、`crates/onlyne-client/src/session/adapter_socket/serve.rs`

**改什么**

- `parked` 从 `Vec<(AdapterIo, Vec<Capability>)>` 变成一个带声明的小结构：

  ```rust
  pub(super) struct ParkedMount {
      pub io: AdapterIo,
      pub capabilities: Vec<Capability>,
      /// 这条连接挂载时声明的会话，没有声明时为 `None`。
      pub session: Option<String>,
  }
  ```

- `park_transport` 接收 `serve.rs::hand_over` 已经拿到的 `session_id`，原样存入；`hand_over` 在 `named.is_none()` 分支把挂载名传下去。`hand_over` 在 `let Some(session_id) = named else` 遮蔽之前先保存原始声明，否则被丢弃的正是这个名字。
- 认领会把连接写进以交付 id 为键的 `transports`，挂载的别名在那一步就没有表可读。因此客户端另存一份 `declarations: Vec<(String, AdapterIo)>`：等待时由 park 持有，绑定后随声明移入，重新 park 时随连接回队列。
- `release_connection` 先移除离开的连接，再判定候选会话：`resident_session_name` 的结果与这条连接自己的声明，二者并列。**候选与会话是否曾被 park 无关**——resident 被交付认领后 `transports` 以任务 id 为键，`was_parked` 会漏掉它，导致进程在服务中退出时别名行永不退出。别名退出依赖存储行存在，且此时没有别的活连接声明它。
- 保活判据：除离开的连接外，还有活连接声明同一会话（`parked` 的声明字段、`declarations`、`transports` 的会话 key、`revived` 的声明），按精确字符串比较，别的别名不算。未声明该会话的 `standing` 连接不参与保活。有声明者时不写 `agent_gone`/`resource_closed`。`transports` 的键不作为退出候选，那些行走正常的优雅退休路径。
- `retire.rs` 把 resident 连接放回 park 时，同样带上它声明的会话。
- 其余 `parked` 读点（`claim_parked_transport`、`note_target`、`has_mounted_adapter`、`delivery.rs` 的 `parked_external`）只跟着类型改，行为不变。
- **作用域保留的会话，最后一条连接离开只是挂起。** 槽由 `task`/`role` 作用域保留、且运行时声明了 `resume` 时，连接离开与 `idle_close` 到点是**同一个动作**（`suspend_locked`）：会话行保持 `idle`，家族的下一条交付仍恢复同一个会话。判定读**槽上记住的声明**，不读当时还活着的连接——两个判定点（连接释放分支、清理扫描）都在连接已经消失之后才发问，从 `transports` 读 `Capability::Resume` 恒为假，于是会话被当成"所有者已走"退掉。
- **"这个会话是否结束"必须经过槽来问。** 槽是绑定的持有者，保留中的槽不服务任何交付时答案是 `Pending`（`binding_task_state`），会话行据此投影为 `idle`。拿会话 id 自己那条交付记录去问是错的：那条记录是这条会话服务的**第一条**交付，早已 `Done`，于是一个闲置但被保留的会话被判成 `exited`，清理扫描下一拍就把它退掉，家族的下一条交付只能另开一条会话——一条链上出现两个会话，正是 `task` 作用域要避免的事。
- `hand_staged` 在认领连接和上报 `Ready` 前，先从槽解析会话 id。恢复后的新交付继续使用原会话 id，上报中的交付 id 单独保留，服务端不会生成一条以新交付 id 命名的会话。

**验收**

- 新增表驱动/单元用例：同一 role 下两条 parked 连接声明同一会话，其中一条离开时不产生 `agent_gone`；两条都离开、或唯一声明者离开时才产生。
- 现有 `scenario_16_suspend_frees_the_slot_and_the_family_resumes_it` 验证同族交付恢复原会话，并保持资源为 `attached`。
- 现有 `a_note_wakes_a_parked_resident_transport` 与 retire 用例保持绿。
- 真实验收：父主管挂载后启动并回收一个 task 子任务，父 socket 不断，服务端会话保持 `working`/`idle`；父连接真正离开时仍正确 `exited`。

### 4.2 插件：子会话不得认领父会话身份

**文件**：`plugins/onlyne-agent-pi/src/index.ts`（代码与测试；README 由主会话更新）

**改什么**

- `session_start` 在读取 resident 或 spawned 身份之前检查宿主声明。`ctx.agent.kind === "sub"` 时返回，不建连接、不注册工具、不认领 alias。该结构通过能力检测读取，不引入 OMP 包依赖。
- OMP 复用已准备的插件 factory 模块，为每个子会话重新调用 factory。独立 factory 闭包中的 `boundSessionId` 无法隔离子会话。
- pi 未提供 `ctx.agent` 时，模块级 `residentClaim` 保存该进程已认领的会话。resident 分支在挂载前检查：
  - 已有认领且新 id 不同，且事件未声明主会话切换 → 返回，不建连接、不注册工具。
  - 没有认领 → 认领 `starting`，继续挂载。
  - `starting === null`（宿主不提供会话 id）→ 保持原有行为，不写入字符串认领。
- `session_shutdown` 只在 `boundSessionId === residentClaim` 时清空认领，子会话的 shutdown 无权释放。
- `syncSessionContext` 换绑当前会话时同步更新认领。OMP 用 `session_switch` 声明 `new`、`resume`、`fork`；pi 用带相应 `reason` 的 `session_start`。未挂载的子会话不得通过切换事件取得父会话身份。

**验收**

- 新用例：同一模块里先 resident 挂载会话 A，再以会话 B 触发 `session_start`，B 不产生连接、不注册工具；B 的 `session_shutdown` 不清除 A 的认领；A 的 `session_shutdown` 清除认领。
- 现有 `session-scope` 与 `agent` 用例保持绿。

### 4.3 服务端：`hold_ms` 成为服务端持有的等待

**文件**：`crates/onlyne-server/src/{router,lib,relay}.rs`

**为什么不能直接 await**

`role_connection_with_io` 的循环（`crates/onlyne-server/src/lib.rs`）对每个 `Req` 是**内联**处理的：`dispatch_client(...).await` 之后当场写回。在这条路径上挂起 20 秒，会让同一条连接上的 `report`、`ack`、`send`、`ping` 全部停摆，心跳超时会把会话判死。所以挂起必须离开读循环。

**改什么**

- `dispatch_client` 的返回从 `ResBody` 变成两位枚举：

  ```rust
  pub enum Answer {
      Immediate(ResBody),
      /// 回复由派生任务经 `session.sender` 写回。
      Deferred,
  }
  ```

  其余所有分支返回 `Immediate`，只改返回类型与循环里的匹配。
- `ClientOp::Pull(args)`（`router.rs`）：
  1. 先 `state.subscribe_frames()` 订阅，再调用一次 `relay::pull`。这个顺序消除丢唤醒竞态。
  2. 有投递或 `hold_ms` 为零/缺省 → `Immediate`。
  3. 否则 `tokio::spawn` 一个任务：循环「等待下一个事件或剩余期限 → 重新 `relay::pull`」，直到拿到投递或到期；然后把 `Frame::res(id, body)` 送进 `session.sender`。返回 `Deferred`。
  4. 事件等待把 `Lagged` 当作唤醒（重新拉取），`Closed` 与超时都回空。
  5. 服务端对 `hold_ms` 取上限（建议 30 s），防止一个坏客户端长期占住任务。
- `lib.rs` 的循环：`Answer::Immediate(body)` 照旧写回，`Answer::Deferred` 什么都不写。发送失败（连接已关）时派生任务自然结束。

**验收**

- 新测试用 `role_connection_with_io` 与一个双工流（`RoleIo` 是 public trait）：发一个 `hold_ms=1000` 的空 `pull`，在挂起期间发 `report`，断言 `report` 的 `res` 先到、`pull` 的 `res` 在约 1 s 后到且为空；再测「挂起期间一条发往该 role 的 `send` 唤醒 `pull`」。
- 真实验收：在限定窗口内记录副本网关的 CPU 时间增量，并验证空队列等待期间仍能及时处理投递。机器级 `lo0` 包率包含生产流量，单独报告运行与停止副本网关时的差值，不将它归属到某个进程。

### 4.4 网关：请求应答不能丢弃后端事件

**文件**：`crates/onlyne-im/src/backend_host.rs`

网关完成后端 `hello` 后会请求会话列表，再进入常驻事件循环。后端可以在列表答复前发送入站事件。旧的 `list_conversations` 循环把所有非列表答复的帧都读走并丢弃，导致触发器从未运行。

`BackendHost` 把请求期间收到的非应答帧按顺序放入待处理队列。`next_op` 先逐条返回这些帧，再读取后续帧。列表、登录和发送请求都从 wire 直接读取应答，并缓存中间事件，保证事件只交给常驻循环一次。

**验收**

- 后端在列表答复前发出的事件，随后由 `next_op` 读取一次；事件内容与原帧一致。
- 全功能副本的 IM 链路观察到后端入站事件、`[[im.push]]` 投递、角色回复和后端出站消息 id。

### 4.5 网关：上报期间保留正在等待的拉取

**文件**：`crates/onlyne-im/src/link.rs`

网关同时等待拉取答复、fault 上报和关闭信号。上报分支完成后，原先的拉取 future 必须继续等待。重新创建拉取会在服务端已有挂起请求时发出第二次请求，收到 `conflict` 并导致链接重连。

网关保留同一个拉取 future，直到拉取及其渲染完成，再开始下一轮。验收在挂起期间发送上报，并检查随后仍能收到投递。

## 5. 明确不改的

- **不新增 wire 字段，不新增 lease 类型。** 声明已经在 `mount.session`、`hold_ms` 与插件配置里。加一层协议只会多一份要同步的事实。
- **不做客户端兜底 sleep。** 服务端挂起是契约；给客户端加"空拉取就睡一会儿"会把服务端缺陷藏起来。升级时 server 与 gateway 同批替换（同一 release）。
- **不动路由。** ACL、chat key、`direct_notes` 是另一类问题，本文不涉及。

## 6. 未决项：`exited` 与 `offline`

现在的模型把「没有活连接」也写成 `exited`，而 `exited` 又不可逆。本文的修复让误判不再发生，但没有改变这个语义。

候选方案：`exited` 只由会话所有者显式上报（插件 `detach`、客户端生命周期终态），连接全丢只降为 `offline`，有连接回来可复活。

- 代价：动 reducer、镜像投影、note 资格判定与看板语义，是一次真正的状态机改动。
- 触发条件：如果 4.1–4.3 落地后仍出现「父连接存活但会话被误判终态」，说明职责边界还有一处没归位，届时按该方案做。

在此之前，`can_receive_note` 仍然只认「有 working/idle 会话或声明了 `direct_notes` 的活连接」。

## 7. 验证清单

### 7.1 主验收：复刻本机联邦集群，跑真实链路

主验收是**照本机联邦集群复刻一个可运行副本**，把会话、插件、拉取和网关修复放进同一条真实链路里跑：

1. **复刻当前部署**：一个中心 server，`dpdp`、`caerulea`、`lazuli` 的 client workspace 位于中心目录。后两者的 OMP 工作目录分别位于 Alexandria 与 ResearchChamber，通过显式 `workspace` 配置连接中心 client。现场两个成员 server 没有运行，不能把当前布局描述成三台 server 已互联。
2. **联邦模式补充验收**：另外启动成员 server，代表角色接收中心任务后向成员角色交付工作，并把成员结果回给中心。`aggregate` 是代表声明，不能代替真实的跨边界消息和两边账本回执。
3. **IM 通信**：真实 `onlyne-im` 进程接收可控后端的入站事件，经 `[[im.push]]` 脚本投递给角色，再经网关发送回复。记录后端确认的出站消息 id。生产布局使用飞书与 QQ；未运行的平台单独标明。
4. **多 role 会话生命周期**：`dpdp`、`caerulea`、`lazuli` 交流 task、note 和完成回执。在父会话里启动真实 task 子会话并回收，父会话保留可用状态。父会话真正退出时，副本应记录退出。

复刻品跑在独立临时根（默认 `/tmp/onlyne-lifecycle`，可用环境变量改），使用新端口、密钥和账本。生产目录仅用于只读核对拓扑。平台后端需要凭据时，使用独立测试机器人或可控的后端进程；缺少凭据不能记作平台验证通过。

两条不可跳过的真实项：

- **真实 OMP 父 / task 子会话**：插件修复（4.2）只能由真实 omp 宿主加载真实的 `plugins/onlyne-agent-pi/src/index.ts` 来验证——真实父会话挂载、真实 task 子会话被回收、父连接存活。模拟工厂重入或手工连 socket 证明不了这一条；它是误判 `exited` 的触发路径本身。
- **IM 走真实后端进程，不共用生产凭据。** 副本的 `onlyne-im` 用 `onlyne-im-backend-fake`，或在操作者另有独立机器人凭据时用它；**绝不复制生产机器人凭据**——两个网关订阅同一个平台 bot 会互相抢事件，这是复刻品不该制造的事故。判断标准是链路真实：独立网关进程、真实帧、真实 `[[im.push]]` 脚本、真实出站渲染，而不是假想一个网关。
