## 两个预设问题

- **0001 需要补 `unknown` 的语义，但不能把它加进错误码表。** `unknown` 不是错误码，而是没有服务响应时的终态结果（`0003-messages.md:87` 用作 `admission.state`，`0006-resources-and-handover.md:71` 用作操作结果）。`0001-core.md:97` 只在正文里顺带提了一句，码表里没有它的定义，也没有说明它不出现在 `error` 对象里。`0007-bindings.md:23` 又要求所有绑定把 `error.code` 限定在 0001 的集合内，两处缺一边，实现方只能自己推断。
- **0000 完全没有提四态。** 全文没有 `unknown`，§3 只写 received/replied（`0000-overview.md:53`），§5 不变量也没有 `unknown`（`0000-overview.md:75-85`）。0000 还停在 O1 之前的叙述。

## P0：直接矛盾

**1. `0013:151` 把积压转给接手者，与 `0006:188`、`0006:190` 相反**

`0013-compute-job-resource.md:151` 写“交接提交时，尚未持久送达的事件随接手材料转给新的事件接收者，读取与接收责任一并转移”。`0006-resources-and-handover.md:188` 规定“有积压时不得交接……存在积压时，提交返回 `conflict`”；`0006:190` 明确“协议不提供把积压转给另一个节点的操作”。按 0006 的定义，0013 的“尚未持久送达的事件”正是积压，这种交接根本无法提交，该句描述的状态永远不会出现。`0013:147` 声称“按 RFC 0006 §5 的五步执行”，但 0006 的积压前置条件在 §6，0013 §7 整节都没有带上。

建议：`0013:151` 改为“未确认事件留在原接收者，清空积压后才允许提交；接手材料只给引用，不给接收责任”。

**2. 0006 内部：零积压前置条件与“接手材料含未解决事件”互斥**

`0006:188` 要求提交时没有“已持久接收、但没有确认记录”的投递义务；`0006:196` 却要求“接手材料至少包含 endpoint 记录中的未解决事件引用”，并且自带定义“未解决指该事件没有确认记录”。两条的判定条件完全相同，前者要求集合为空，后者要求集合非空。`0012:121` 与 `0012:123` 复刻了同一对矛盾。

建议：把 `0006:196` 的“未解决”改成接手者仍需要读取的历史事件（例如“交接截点之前、接收者仍需读取的事件”），不要再用“没有确认记录”。

**3. `conflict` 是未定义错误码，却被四个文件当作返回值使用**

`0001:77-88` 的码表里没有 `conflict`，只有 `id_conflict` 与 `revision_conflict`。而 `0006:188`、`0006:220`、`0012:121`、`0012:221` 都写“返回 `conflict`”，`0007:23` 又要求所有绑定的 `error.code` 必须属于 0001 的集合。这是 O2 新增规则带来的新码，码表没有同步。

建议：在 `0001:81` 的 409 行补 `conflict`（含义：存在未清空的投递义务，阻止本次资源关系变更），或在 0006/0012 改用 `revision_conflict` 并另设 `backlog_pending`。

**4. `0003:64` 禁止确认已过期义务，`0004:87` 允许并定义了这一行为**

`0003-messages.md:64`：“确认（`ack`）表示成员已经在本节点持久保存该条目的正文或可恢复引用……成员在持久保存之前不得确认。”`0004-events-and-views.md:87`：“过期的义务可以被确认：成员在持久记录这个过期结局之后确认它。这次确认表示成员记录了结局，不表示成员仍持有正文。”内容已过期的成员必然没有持久保存正文，按 0003 永远不能确认，按 0004 必须能确认。O2 在资源侧确立了“确认与过期证据并存”（`0012:102`、`0006:190`），thread 侧没有同步，0003 仍是旧模型。

建议：`0003:64` 补一句“内容已按保留策略过期时，成员在持久记录该过期结局后可确认该义务；此确认不表示持有正文”，与 `0004:87` 逐字对齐。

## P1：语义冲突或修订漏同步

**5. `0012:187` 用“尚未注入模型”定义 thread 关注义务，owner 无法观测这个状态**

`0012-im-resource-node.md:187` 的积压分层表写“thread 关注义务 | 已进入 thread、尚未注入模型的消息 | 持有者 owner 与成员”。但 `0004:153` 明确注入游标是运行时本地状态、“不对外发布”，`0008:160` 也把注入记录限定在单个 OMP 上下文。所以 owner 既没有这份义务，也无法按“是否注入”判定积压。同时 `0003:64` 定义的义务终点是确认，不是注入。

建议：该层改为“已进入 thread、尚未确认的关注义务”，恢复方式写“关注清单与确认”，删掉注入字样。

**6. 0001 缺 `unknown` 与 `expired` 的结果语义，也缺“查回”的机制**

`expired` 只出现在 `0006:75`（“明确报告 `unknown` 或 `expired`”），0001 的码表里没有单独的 `expired`，只有 `cursor_expired` 与 `retry_window_expired`。另外 `0001:97` 说“保留原操作 ID 查回或重投”，但只有资源操作定义了按 `operation_id` 查询（`0004:147`、`0006:75`）；thread 与成员变更的“查回”实际只能重投，而 `0001:112` 规定窗口过后返回 `retry_window_expired`，结果就查不回来了。`0003:221` 对消息说了“可查询原结果”，其余操作类型没有对应说法。

建议：在 0001 §4 增加一小节“结果未知”：`unknown` 不是错误码、不出现在 `error` 对象、只在调用方本地记录；`expired` 作为查询结果值单独定义；分别说明消息、资源操作、thread/成员变更三类“查回”的路径与窗口外行为。

**7. 0000 总览没有反映 O1–O4 中的任何一项**

逐处证据：§2 规范表把 0003 描述为“消息发送、持久接纳、回执与回复”（`0000:21`），把 0004 描述为“消息列表、事件续传、索引和多行展示”（`0000:22`），都没有关注义务与确认；§3 对象表（`0000:39-47`）没有 Obligation，只有 Receipt；§5 不变量（`0000:75-85`）没有 unknown 是终态、确认与过期并存、todo 原子提交、await 与片段共用消费记录；§6 第 101 行仍然写“错误码只表达「这次操作失败了」”，而 O1 的核心恰恰是“结果可能未知且不是失败”。

建议：§3 增加 Obligation 一行；§5 补四条不变量；§6 第 101 行改为“错误码只表达失败，未知结果不是错误码也不是失败”；§2 两张描述补上义务与确认。

**8. `preparing` 不属于 0006 定义的四态**

`0000:55` 写“资源交接的 preparing/committed/aborted”，`0008:97` 写“交接结果为 preparing 时显示‘交接待决’”。但 `0006:71` 是封闭的四态 `committed`/`pending`/`aborted`/`unknown`，0006 §5 全文没有 `preparing` 这个值，`0006:176` 只说查回 `committed` 或 `aborted`。交接进行中的正确取值是 `pending`。

建议：`0000:55` 与 `0008:97` 统一改用 `pending`；若确实需要区分“准备中”，必须在 `0006:71` 明确登记为第五态并改掉“四态”的措辞。

**9. 0007 的绑定契约没有 unknown 这一行**

`0007-bindings.md:9-17` 要求每个绑定回答七件事，其中“持久接纳”只覆盖 durable 与 binding-defined；`0007:23` 把错误翻译限定在错误码集合内，而 unknown 不是错误码；0007 §6 验收（`0007:127-131`）也没有 unknown。O1 之后，每个绑定都必须回答“没有响应时如何落到 unknown”，否则 A2A/ANP 绑定可能把超时写成 refused 或 accepted。

建议：`0007:9-17` 增一行“结果未知 | 无响应/超时时如何记录为 unknown，保留哪个引用供查回”，并在 §6 增一条验收。

**10. 0013 引入两个未定义结果值，且 `unknown` 作业态不在状态表内**

`0013:141`：“已终态的作业返回 `thread_closed` 语义的作业版本：`invalid_request` 或明确的 `job_terminal` 错误码”。`thread_closed` 是 0001 中 thread 专用的 410 码，`job_terminal` 不在 0001 集合内，违反 `0007:23`。另 `0013:160` 写“未恢复的作业标记为 `unknown`”，但 `0013:36-42` 的作业状态表只有 queued/running/completed/failed/canceled，而且 `0013:34` 声明“作业状态由计算服务自己报告”，本地无法恢复的标记不是服务报告的状态。

建议：141 行改用 0001 已有的码（终态作业用 `invalid_request` 加 details 说明，或申请登记 `job_terminal`）；160 行改称“本地快照标记为 unknown，不作为服务报告的状态”，并在状态表外注明。

**11. 0012 的 `fault` 是未定义值**

`0012:100`“平台失败记 fault 并保留原文”、`0012:227`“平台发送失败时 fault 保留平台原文”。O1 之后，平台失败只有两种合法记录：确证无副作用记 `aborted`，无法确证记 `unknown`（`0006:71`、`0015:55`）。`fault` 在整个 RFC 集里只出现在 0012 这三处（另有 `0012:197` 的推送脚本失败）。

建议：100 与 227 行改为“平台明确拒绝记 `aborted`，平台结果不明记 `unknown`，原文进 `details.source`”；197 行的脚本 fault 属于本地运行日志，注明它不是协议结果值。

## P2：引用或覆盖面问题

**12. `0013:168` 引错 RFC。**“`transfer` 操作本身按 RFC 0003 的重投规则处理”——0003 §8 是消息 ID 重投窗口与 MessageRef 去重；资源操作的重投在 `0006:70`（`Idempotency-Key` 加 `operation_id` 进身份摘要）与 `0001:105-115`。建议改引 0006 §1 与 0001 §5。

**13. O3 的必须项只写在 0008，通用契约没有。**`0008:200` 要求“todo 快照与 MessageRef 关联 MUST 由同一可恢复的持久提交记录确定”，但 `0005:120` 的“todo 写入”只写“来信可写进运行时待办”，`0007:119` 同样只有一句，`0005:119` 的“恢复”也不含 todo 关联重建。换一个运行时接入，按 0005/0007 全部满足、按 0008 却不合格。

建议：`0005:120` 与 `0007:119` 各补“快照与消息关联的原子提交及恢复”，`0005` §6 增一条验收。

**14. `0004:156` 把折叠义务派给了库，但游标归运行时。**`0004:153` 写“运行时维护自己的注入游标……不对外发布”，`0008:128/268` 把映射与游标推进放在接入层。库看不到模型上下文，无法执行“库 MUST 折叠为一次展示”。

建议：改为“接入层 MUST 折叠；库提供以 `(context, ThreadRef, seq)` 为键的共用消费记录”。

**15. `0004:7` 与 `0004:153` 冲突。**第 7 行说“received、replied、已注入是视图的派生结果”，但注入游标是本地状态、不对外发布、§2 的读取参数里也没有注入过滤。O4 之后“已注入”不属于对外视图。

建议：第 7 行删掉“已注入”，或写明“已注入是运行时本地视图的派生结果”。

**16. 同一事物的三个名字。**注入游标（`0004:151/153`、`0008:128`）、消费记录（`0004:158`、`0005:84`、`0008:192`）、消费状态（`0004:156`）指同一份数据，`0005:84` 一句里同时用了两个名字。建议在 0004 §5 首次出现处定为“消费记录（注入游标）”，其余处统一。

**17. `0001:92` 的“已公开 thread”没有定义。**0002 全文没有“公开”概念，只有成员表（`0002:85`）与 `not_a_member`（`0002:132`、`0002:155`）。实现方无法判断“已公开”的边界，会在 `not_found` 与 `not_a_member` 之间各写一套。

建议：在 0002 定义“已公开”（例如调用者持有有效回复许可或曾是成员），或把 `0001:92` 改为按成员表与回复许可逐项判定。

**18. 0010 用原生 ANP 码作为返回，没有映射。**`0010:220` 返回 `anp.invalid_target_binding`、`0010:221` 返回 `anp.idempotency_conflict`，都没有给出 0001 对应码；`0001:93` 要求同键异内容统一返回 `id_conflict`，`0007:23` 要求 `error.code` 属于 0001 集合。0009 有完整的映射列（`0009:115-125`），0010 §7 只是列出了 ANP 自己的码表。

建议：仿照 `0009:115-125` 给 `0010:163-176` 加“Onlyne 映射”列，至少补 `idempotency_conflict → id_conflict`。

**19. 0009 与 0010 都没写无响应如何落到 unknown。**`0009:151/161` 只说“A2A 核心未定义持久接纳，只能声明 binding-defined”，`0010:199/211` 只说 `accepted: true` 记为目标入口接纳。两者都覆盖了成功路径，没有覆盖 O1 的“无响应 = unknown 终态”，实现方容易把超时写成 `refused` 或 `binding-defined`。

建议：各补一条：“传输层无响应按 RFC 0003 §3 记录为 `admission.state: unknown`，不写成拒绝。”

**20. 0014 内部：订阅“不补发”与“窗口内可补齐”冲突。**`0014:147`“断开期间的变更通知会丢失，重连后不补发”，`0014:149-150` 也说恢复靠重新查询；`0014:153` 却写“数据源声明自己的事件保留窗口。窗口内可按游标补齐”。窗口大于 0 时，这两句给出相反结论。

建议：147 行限定为“实时通知不补发；是否可按游标补齐由 153 行的保留窗口决定”。

**21. `0002:34` 与 `0003:62` 引用了关注清单，但接口只定义在 0004。**`0004:74-80` 定义了 `GET /threads/.../attention` 与 `POST .../ack`，而 0004 声明依赖 0003（`0004:3`），`0003:3` 的依赖又不含 0004，0002 同理。结果是 `0003:62-66` 与 `0002:34` 的义务读写在各自的依赖闭包内无法实现。另 0004 的 `attention` 参数写在 §1（`0004:66-70`），§2 读取端点的参数表（`0004:97-103`）没有它。

建议：在 `0003:62` 与 `0002:34` 加“接口见 RFC 0004 §1”的交叉引用（只作文本指向，不改变依赖方向）；把 `attention` 并入 `0004:97` 的参数表。

## P3：术语擦边，不影响可执行性

**22. `0006:134` 的 `transferred` 不在四态内。**“库明确返回 `transferred` 和交接引用”没有说明它是操作结果、库返回还是字段值。建议注明它是库层等待转移的返回，不是资源操作结果值。

**23. `0003:7` 与 `0003:87` 的 `pending` 撞名。**`0003:7` 说“completed、pending、failed、blocked 这些词不描述消息”，`0003:79/87` 又让 `admission.state` 取 `pending`。读快了会以为投递在途也不能叫 pending。建议在 `0003:7` 加半句“投递记录的 `admission.state` 不属于任务状态”。

## 核对后未发现矛盾的部分

- 0015 §3 结果表与 O1 的收紧定义一致，`0015:55` 正确回指 `0006:71`；`unavailable` 落在 0001 的 503 内。
- 0009 §7 的九个 A2A 错误全部映射进 0001 的码表（`0009:115-125`），无越界码。
- O4 三处（`0004:156`、`0005:84`、`0008:192`）在键 `(context, ThreadRef, seq)`、崩溃保留未确认、禁止提前推进消费记录上完全一致，没有互相矛盾。
- 0014 §3-§4 的授权过滤（范围外 `not_found`、订阅扩权 `forbidden`）与 `0006:49` 的“无权即 not_found”一致。
- 0002 的成员状态、关闭幂等、默认 thread 解析与 `0001:82` 的 `thread_closed`、`0003:122` 的默认落点记录一致。

## 建议修复顺序

1. 先定 0001：补 `conflict` 与“结果未知”小节（第 3、6 项）——这两条决定 0006/0012/0013/0015 的措辞。
2. 再修 0006 的积压自洽（第 2 项）与 0013 的交接段（第 1 项），然后 0012 的分层表与 `fault`（第 5、11 项）。
3. 0003 的 ack 例外（第 4 项）与 0004 的折叠义务归属（第 14 项）。
4. 最后同步 0000 总览（第 7 项）与 0007 的绑定契约（第 9 项），其余 P2/P3 一并收尾。
