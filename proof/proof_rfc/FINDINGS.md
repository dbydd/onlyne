# Onlyne v3 RFC 故障发现与修订

本轮追加效果重合检查，发现恢复契约缺口、结果定义冲突与跨表面展示缺口。规范以 `docs/rfcs/` 为准，修订候选保留在本文。

## 1. 方法与边界

形式化规格在 `proof/proof_rfc/design/architecture/`，通过 `ssot check`。可执行有限状态搜索在 `proof/proof_rfc/design/appendix/reference/`，每个脚本覆盖一条状态转换，输出最短见证轨迹、探索状态数与有界范围内的结论。


效果重合分两类：同一事实被两条路径各自推进，两条机制承担同一职责但缺少唯一提交点。本文件只记录反例或明确缺失的契约；回归探针的拒绝轨迹不记为缺陷。

故障假设：消息可重复、乱序、丢失；节点可在任意一步崩溃或长时间离线；平台侧结果未知；注入返回不代表已消费；游标与通知可丢失。公平性只在明确写出时成立。

## 6. 复现方式

```sh
ssot check proof/proof_rfc/design
python3 proof/proof_rfc/design/appendix/reference/check_faults.py
```

第一条做类型检查、QuickCheck 与证明义务统计。第二条汇总当前规则的有限状态搜索。两条都通过，只说明在这些边界内没有反例或找到了预期反例。

## 7. 效果重合检查

脚本 `effect_overlap.py` 搜索接纳重投、mention 与 reply、确认与过期、决定与恢复、资源调用查回、域修改与历史重投。现行规则与去掉守卫的反事实探针分别输出。探针复现重合说明搜索能识别该失效情形；探针本身不构成 RFC 缺陷。

交接场景的现行守卫依据 `docs/rfcs/0006-resources-and-handover.md:165-177`：提交原子写入归属、版本与交接结果，同一 expected revision 只允许一次成功，恢复只接管尚未终结的准备。资源操作场景不宣称恰好一次外部效果：`docs/rfcs/0015-mcp-resource-node.md:90-97` 允许副作用重发，协议只承诺本地 `operation_id` 去重与结果查回。终态标签优先级在现行 RFC 未规定，脚本不建模它。

确认与过期可以各自留下证据，清除的是同一份待投递义务。模型使用幂等集合移除，允许 acked 与 expired 并存。决定与恢复受同一预期版本和未终结准备约束。首次搜索中这两处守卫不对称产生的见证属于模型错误，已按相应契约修正。

## 8. 待定项与修订候选

本轮区分语义歧义、定义冲突、恢复契约缺口和策略缺口。修订候选尚未写入 RFC 正文。

| 编号 | 待定问题 | 最短轨迹 | 修订候选 |
|---|---|---|---|
| O1 | 确认与过期的终态展示及迟到确认语义未明确；未发现必然重复清除积压 | 接收事件，先过期，再收到有效确认 | 保留接收证据；确认与过期幂等移除同一待投递义务，不重建；另行决定终态展示优先级 |
| O2 | `aborted` 语义冲突：0006 定义无外部效果，0015 允许业务失败映射 `aborted` 且承认可能已发生副作用 | 工具执行部分副作用后返回 `isError: true`，endpoint 记录 `aborted` | `aborted` 只在 endpoint 已确认本次调用未产生外部效果时使用；否则记 `unknown`，业务错误与原文进 `details.source` |
| O3 | todo 快照与来源关联分两次写，崩溃后恢复查不到关联，重放追加第二条 todo | 写快照，崩溃，本地关联缺失，重放追加 | 快照与 `message_ref` 到待办的稳定关联放进同一可恢复提交记录，宿主投影与本地索引在其后派生；恢复先重放该记录再决定是否建项 |
| O4 | await 工具结果与自动片段可以重复展示同一 reply，两处没有共用消费记录 | 宿主确认工具结果中的 reply 已被消费，自动片段仍再次展示 | 两者共用 `(context, ThreadRef, seq)` 消费记录与协调调度；在宿主确认消费后推进记录，消费未知时仍保留重投边界 |

O1 的依据为 `docs/rfcs/0006-resources-and-handover.md:185-190` 与 `docs/rfcs/0012-im-resource-node.md:102,176`。集合幂等移除足以结束投递义务，终态标签优先级仍需澄清。

O2 是明确的定义冲突：`docs/rfcs/0006-resources-and-handover.md:71` 要求 aborted 没有外部效果，`docs/rfcs/0015-mcp-resource-node.md:48-54` 将可能已有副作用的业务失败映射为 aborted。部分副作用后返回 `isError: true` 即满足冲突输入。建议保留通用定义，缺少无副作用证据时记录 unknown 并保留业务错误。

O3 由 `docs/rfcs/0008-omp-surface.md:196-217` 的两次写入与恢复步骤产生，违反其 `:291` 的无重复验收。`todo_effect_overlap.py` 将该过程缺口与同一可恢复提交记录的候选方案分别搜索。快照记录须显式携带稳定来源关联；只向 todo 条目加未知字段会被宿主 schema 丢弃（`:268`）。

O4 的依据为 `docs/rfcs/0005-delivery-and-runtime.md:73-80` 与 `docs/rfcs/0008-omp-surface.md:122-128,186-190,264`。`reply_exposure_overlap.py` 搜索工具结果与自动片段的已确认重复消费。现行 RFC 没有禁止这种跨表面重复，结论为策略缺口。候选协调方案只覆盖已确认消费；void 返回或提交成功不足以确认消费。

职责审查还核对了各机制是否可以合并。接纳证明服务保存消息，关注确认成员持久保存，注入确认上下文消费，wait 只结束本地等待，todo 保存持续工作状态。它们分别持有不同事实。域分组、thread 授权与 ingress 连通性也分别承担不同职责，共同成员关系不替代后二者。

## 9. 剩余边界

- 有积压不得交接是一条活性取舍。处理者永久离线时，资源只能等保留期终态；协议不提供把积压交给别人的路径。
- 69 条证明义务中 26 条可证、43 条未定。未定项与语义审查的 27 个候选分别记录在 `proof/proof_rfc/SSOT.md`，没有视为完全证明。
- MCP 的外部副作用无法承诺恰好一次。协议只保证调用身份保留与 `unknown` 结局。
- 有限状态搜索只覆盖每个脚本写明的事件数、页数与深度。
- 效果重合检查只覆盖单个场景内两条路径。跨场景的职责重复，例如多个机制都声称推进同一条外部作业，尚未建模。

## 10. 信任交换模型的边界（修订记录）

`trust_exchange_liveness.py` 在 2026-10-25 按 RFC 0017 §3.5 的送达义务语义重写为双节点模型：两端各有持久行、批准两半、密钥代次与最多一条待送达义务；每条发送都显式分出「对端拒绝」「送达但回执丢失」「送达且回执到达」三种结局。状态空间 205 个可达状态，逐事件穷举。五项检查全部通过：

- `trust.phase-invariant`：任一节点的持久字段与 `trustPhase` 投影不矛盾。
- `trust.obligation-settles-only-on-own-reply`：义务只由本方收到应答本次投递的回执或本方撤销结束；对端发来的任何陈述都不清除本方义务，对端的拒绝只让该次尝试退避、永不删除义务（`/introductions` 的拒绝本身不可认证）。旧实现正是这条被违反。
- `trust.revoked-carries-no-obligation`：已撤销的行不携带义务。
- `trust.bilateral-approval-converges`：在双方都批准、无人撤销的每个可达状态里，只对仍欠陈述的一侧各做一次成功送达，就到达两端 `exchanged` 且义务清空。调度里不含任何宿主动作，也不需要再次人工确认；批准本身就写下了义务。
- `trust.rotation-settles-on-round-trip`：轮换义务在回执到达时清空；发送方批准位不变，接收方自己的批准位也不变（有效轮换是身份连续，不降级）。

前提分开写清：模型假定「某时刻之后发送与回执都能到达」，即网络最终恢复；它不建模调度公平性、真实计时、重试窗口，也不建模攻击者（nonce 复用、冒充、重放）。收敛检查覆盖模型编码的每个可达状态，因此它证明的是「这些状态里没有任何一个需要比一次成功送达更多的条件」，不是「维护环一定会在有限时间内尝试」，也不是「真实实现覆盖了全部协议状态」。维护环会尝试的依据是它在义务存在时保持活跃节奏，由 `packages/lib/tests/verify.ts` 的 `maintenance.*` 与 `auth.owed.*` 覆盖。

模型的状态空间是对称的：两端要么都有行，要么都没有，且陈述不读密钥代次。因此它表示不了「一端有行、另一端没有行，同时有行的一方换了钥」这类轨迹。独立审查给出过一条这样的轨迹，属于协议边界而非实现缺陷，已写进 RFC 0017 §2：

- C 读到 A 的旧钥并确认，陈述在途中丢失（C 有行，A 无行）。
- A 在断网期间轮换；A 没有 C 的行，轮换窗口不覆盖 C，旧钥在窗口关闭后删除。
- 网络恢复，C 按 A 的当前钥重驱，A 建立 invited 行并批准；C 收到无旧钥证明的新钥，`id_conflict`。双方都已本地批准、无人撤销、网络正常，但只能撤销后重新确认恢复。

不本地修复的理由：A 无从知道 C 钉的是哪把钥，旧钥已删；让 C 在单边行上无证明接受新钥会破坏 `confirm` 时展示指纹的信任锚。协议扩展（陈述携带「对端钉住的指纹」并保留旧钥到这类关系解决）单列设计项，不属本版。

模型与实现的分工必须分开说：模型编码 RFC 规则，不证明代码符合规则。本轮据此发现并修掉两处实现缺陷——「收到陈述清除义务」与「只重驱 `pending` 行」——模型在放回这两条规则时都立即报见证。另有一处相反的情况：有效轮换在实现里把接收方的本侧批准清成 false（`receive` 的 `changed ? false` 分支），使双方从 `exchanged` 掉到 `invited`；模型按 RFC 规则建模，因此看不见这个偏差。该偏差由 `verify.ts` 的 `auth.rotate.phase` 固定，模型不宣称覆盖实现对应性。

独立读码审查又找出十三处实现缺陷，都已修并各自固定：轮换降级（`auth.rotate.phase`）、双端同时轮换时陈述指向过期钥（`auth.twin.*`）、未认证拒绝可销毁义务（`auth.forged-refusal.*`）、OMP 换钥钩子拒绝覆盖已有私钥（`tests/keys.test.ts`）、轮换窗口在零 peer 与撤销最后对端时泄漏（`auth.rotate.no-peers`、`window-closed`）、慢换钥被按年龄误弃（`auth.rotate.slow-hook-*`）、换钥钩子换完再抛错时窗口被误弃（`auth.rotate.hook-failed-*`）、重复确认覆盖在途轮换义务（`auth.refresh.*`）、轮换漏掉 invited 关系（`auth.rotate.invited-proof`）、`redrive` 用整轮快照覆盖并发写入（`compareObligation`）、无时钟宿主无合法路径重驱义务（`auth.noclock.*`）、未信任候选的公开描述被签名 transport 拒绝（`auth.discover.untrusted`）、轮换旧钥落在未按秘密保管的 SQLite（OMP 存储 0700/0600）。共同点：测试验证意图、模型验证规则，两者都不检查实现是否就是那套规则；逐行读代码是第三种仪器。

边界，逐条留待而非隐藏：

- 轮换只建模一次，密钥代次取 0 与 1；一次在途轮换由持久窗口与进程内互斥保证，回归 `auth.rotate.second-refused`、`auth.rotate.slow-hook-*`。
- 旧私钥随轮换义务保留到对端回执或本方撤销，同时最多一把，保留时长没有上限。对端永久离线时它一直留在存储里；加了过期反而会把仍钉旧钥的对端变成不可解释的 `id_conflict`。保密由宿主存储承担：OMP 的数据库目录 0700、db/WAL/SHM 0600，契约要求同样待遇。
- 不可认证的拒绝只让该次尝试退避 600 秒，退避期间 `hasPendingWork` 为假、由空闲节奏照看。这是恢复延迟，不是活性缺陷。
- 进程内互斥不覆盖多进程共用同一存储；契约规定一个节点的 storage 由单个进程持有。
- 宿主的换钥 hook 可以任意慢：本进程正在换钥时维护环无限等待，只有重启后遗留的窗口才被丢弃。
- 安全性（签名、时间窗、nonce 单次消费、撤销、拒绝不可认证）由 RFC 0017 §3.4 与实现侧校验承担，不由此脚本证明。此前「无死锁已证明」一类表述仍然作废。
