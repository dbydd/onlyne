# Onlyne v3 形式化：SSOT 与故障边界

本文记录 RFC 缺陷搜索的范围与证据。规范以 `docs/rfcs/` 为准。修订候选与现行规则分开建模。

## 1. 这次形式化要回答的问题

形式化检查以下风险：

| 风险 | 含义 |
|---|---|
| 消息阻塞 | 一条消息已经产生，但永远没有节点把它推进到下一状态 |
| 队列阻塞 | 一条待处理项卡在队头，后面的项无法推进 |
| 信息丢失 | 某个节点曾经知道的事实，在之后的状态里无法恢复，且没有标记为未知 |
| 节点掉线卡死 | 一个节点离线或重启后，没有规则让它重新取得推进条件 |
| 效果重合 | 同一事实经多条路径重复提交，或多个机制重复承担同一可观察职责 |

## 2. SSOT 用法

每条事实只有一个权威写入点。其他位置保存的是投影或观察值，不各自决定状态。

| 事实 | 权威写入点 | 派生位置 |
|---|---|---|
| 消息是否接纳 | 接收节点（0003 §3、§4） | 发送方出站记录 `admission` |
| 消息存盘条目与 seq | thread 的 owner（0002 §1） | 任何成员的列表视图 |
| 关注义务是否产生 | thread owner 在接纳事务内记录 | 接收成员的持久队列与 agent inbox 视图 |
| 注入是否发生 | 运行时注入游标（0004 §5、0008 §4） | 工具结果与提示 |
| 等待是否解除 | 发送方库等待者（0005 §3） | 工具返回的答复 |
| 资源绑定与 revision | 资源 endpoint（0006 §4） | agent 缓存 |
| 资源操作结果 | 资源 endpoint（0006 §1） | 调用方的 `pending`/`committed` 观察 |
| todo 是否存在 | 运行时（0005 §4、0008 §6） | Onlyne 的本地来源关联 |
| 节点属于哪个域 | 该节点自己的成员记录（0011） | 候选目录、远端发现结果与服务描述 |

SSOT 在这里的具体用法：**当两个位置都能声称同一事实时，只有权威写入点能推进状态。** 派生位置落后是允许的，前提是它明确标记为落后或未知，而不是自行判定。

## 3. 抽象掉的表面实体

建模时不区分这些表面的差异，只保留它们对推进条件的影响：

- thread、IM 会话、计算作业、数据源、MCP server 都抽象为「一个有权威写入点的对象」。
- 具体错误码抽象为三类：可重试、终态拒绝、未知。
- `@all`、`@role`、引用回复、普通通信抽象为「是否产生一个必须被消费的关注项」。
- 域保留本节点的单一 active 成员关系、退出墓碑与版本围栏。候选结果抽象为已核对声明和查询失败。
- 机器与 ingress 抽象为可达性及委托有效性。域声明不改变它们，也不授予 thread 成员资格或资源权限。

## 4. 故障假设

模型允许这些事发生：

- 消息重复到达、乱序到达、永不到达。
- 节点在任意一步之后崩溃或长时间离线。
- 资源 endpoint 接受请求后，平台侧结果未知。
- 运行时注入返回不代表已消费（OMP 的 `sendMessage` 返回 void）。
- 游标和订阅通知可以丢失，且不一定能补齐。

## 5. 不检查什么

- 不检查加密算法、认证强度。
- 不检查性能与容量。
- 不证明系统正确。**有界状态搜索只能否证性质，不能证明性质。**
- 不把「模型没找到反例」写成「不存在反例」。

## 6. 当前产出

- `proof/proof_rfc/design/`：5 个 VDM 模块。类型检查无错误，QuickCheck 未找到反例；69 条证明义务中 26 条可证，43 条未定。
- `proof/proof_rfc/design/appendix/reference/`：可执行有限状态搜索脚本。每个脚本只覆盖一个状态转换，输出最短见证轨迹、探索状态数与有界范围内的结论。
- `proof/proof_rfc/FINDINGS.md`：候选缺陷、分类、RFC 依据与最小修订建议。

检查入口为 `python3 proof/proof_rfc/design/appendix/reference/check_faults.py`，注册 11 个模块、共 56 项检查。`check_pass` 表示实际结果符合该行预期：现行规则的风险见证、反事实探针、修订候选的无见证结果均可能通过。它不表示全部 RFC 没有缺陷。

## 7. 证明义务的处理

`ssot check` 报告 69 条证明义务，其中 26 条可证、43 条未定、0 条未评估。下表覆盖全部未定项。人工核对提供上下文依据，没有把未定项升级为机械证明。

| 模块 | 未定项 | 上下文依据与剩余限制 |
|---|---|---|
| Admission | 4：Accept、Expire 的 total function 与 satisfiability | Accept 分支先测试身份是否存在；Expire 的 pre 要求身份存在。新接纳、拒绝、重投和墓碑各分支均给定结果与状态 |
| Attention | 16：状态约束 5，Admit 1，Queue 2，Ack 3，Inject 3，Automatic 2 | 状态约束在集合包含关系前检查 map 的定义域；Queue、Ack、Inject 在访问前检查 context；Automatic 对缺失 context 使用空集合。显式更新给出各操作的候选后态 |
| Binding | 10：初始化、Receive、Handover、Commit、Abort、Ack 2、Expire、Recipient 2 | 空初态满足约束；Ack 与 Recipient 由 pre 保证事件存在。Commit 读取非 nil 的 prepare，并要求 acked 与 expired 的并集覆盖全部事件；提交消耗 prepare；每条更新保留首次归属 |
| Domain | 13：状态约束 2，Create 2，Join 2，Leave 2，Describe 2，Discover 3 | 集合遍历仅取 records/replies 定义域；Join/Leave 先区分缺失关系，再检查版本；Discover 对可选声明先判非 nil。拒绝分支保持状态，成功分支保持本节点和至多一条 active 记录 |

语义反模式审查报告 27 个候选，未取得该层全通过结果。多数候选针对注释复述与散文重复；其中“创建标识由调用边界分配”“保留窗口结束后才能清理”属于规格之外的边界事实，人工核对予以保留。共享 Identity 仅导出 NodeId，审查将其标为名字登记表；该模块作为两个独立权威面的公共身份词汇保留。人工核对还纠正了 Attention README 中“关闭即排除自动片段”的过时说明。其余注释建议未改写状态契约，该层结果独立于机械类型检查。

「没有找到反例」只表示在当前有限边界内没有反例。边界写在每个脚本的输出里。
