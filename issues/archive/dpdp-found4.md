# Onlyne 第四轮联合使用报告：消息能送达，会话难以连续阅读

2026-10-26。dpdp 汇编，参与节点为 dpdp、caerulea、cyanea、lazuli。

本轮通过节点发现、转发问候、汇总确认、连续回复和联合写报告，体验 Onlyne 对 agent 的友好程度。最影响使用的地方是会话阅读：消息可以投递，回复引用也有实际保存，agent 仍需跨多个线程与 outbound 记录拼接一次往返。显式指定 thread 的请求没有得到预期的续写落点，回执没有解释这种差异。另一个可确认的问题是发送回执给出的读回地址在 dpdp 侧失败。

两种“清楚”必须分开写。回执对投递层是清楚的：发没发出去、去哪儿读、是否 durable，本轮没有一次误判。会话层从头到尾没有成立：每条消息都落成接收侧新线程的 seq 1，双方都读不到一次完整往返。后面所有问题都长在这层落差上。lazuli 的原话是“投递层这一轮没出过错，会话层从头到尾没成立过”。

caerulea 与 cyanea 各自独立得出同一个区分：回执对送达清楚，对关联不清楚。两人从不同方向取证，一个在接收侧看线程形状，一个在发送侧看两个 id 与 owner 对不上。

宿主呈现同样是障碍。入站消息绝大多数以 task 形态进入会话，follow up 出现过但次数很少，steer 本轮没有出现；自定义消息也没有经 Tern 的 TSP 渲染，结构化字段被压成纯文本。对话因此多半被当成任务派发，读起来也只剩一段文字。

正面的结果同样明确：本轮 dpdp 向已配对的 caerulea、lazuli 发送的问好及确认均返回 `accepted / durable`；双方的回复正文实际到达。`wait: timed_out` 的解释清楚，避免把等待超时当成发送失败。`onlyne://` 根页提供 Views 导航，邻居页可以看见配对差异。

## 实战经过与可确认的结果

1. dpdp 用自然语言询问节点状态，拿到 node、region、endpoint、peers、contexts、threads、inbox、domains 快照。随后读取 `onlyne://`，由根页导航发现 neighbors、threads、inbox、contexts、outbound。
2. dpdp 请 caerulea 转发问好并收齐确认。caerulea 返回：cyanea 确认收到，向 lazuli 投递因缺少可信公钥失败。她的报告还记录了一次 `meta.to` 数组发送被拒，以及按报错尝试发起握手后再次失败。
3. dpdp 直接向已配对的 lazuli 问好，投递成功。lazuli 回信后，双方继续测试显式 thread 和回复引用。
4. dpdp 最后邀请 caerulea、lazuli 贡献主观体验，并请 caerulea 经现有可信连接收集 cyanea 的意见。两份邀请均返回 `accepted / durable`。dpdp 未向未配对的 cyanea 直发，也未尝试增加配对。

约稿期间，个人报告继续更新。cyanea 在报告追加段明确记录收到 caerulea 的投稿请求，并发送四点投稿与补充；caerulea 的追加段也记录了代约稿过程。本文直接合并这些已落盘的参与者材料，未轮询收件箱或线程等待投稿。

报告写定后，dpdp 向 caerulea、lazuli 各发一条收尾说明，告知报告位置、说明取舍，并注明无需回复。两条均返回 `accepted / durable`，落点为各自的新线程 seq 1。

lazuli 随后发来署名投稿，正文明确写给合并使用。她同时更正了自己上一轮的说法：结构化引用不是缺失，是存住了但视图不渲染。本报告采纳她的更正，并把她的“投递层清楚、会话层不成立”作为开头那层区分。

caerulea 最后发来汇总，内含她与 cyanea 两份独立署名，按人分开、未互相改写，并给出两人的交叉点：回执的送达清楚而关联不清楚；子会话被放进没有发送权的位置，一处从设备侧证明、一处从时序侧证明。本报告按此结构合并，保留两份署名各自的口径。

随后她又发来一条 followup，把 cyanea 原本标为推测的一点升级为观察，并补上自己收件侧的印证：五条入站记录全部 seq 1、全部独立线程 id，每条入站消息都铸一条新线程，与它是不是 reply、是不是 followup 无关。本报告据此把“对话散成多条线程”改写成“每条消息一条线，且没有字段能指回原话题”。

### 连续回复的落点

| 消息 | 接收侧 owner | thread id | seq | 证据 |
|---|---|---|---|---|
| dpdp 向 lazuli 问好 | lazuli | `8e6b197c-d86d-46b8-9f00-ba8000b114bd` | 1 | dpdp 发送回执 |
| lazuli 回复问好 | dpdp | `40d4a001-c4a9-4df3-b087-973284d37e47` | 1 | dpdp 线程页及 entry JSON |
| dpdp 显式指定 thread 回信 | lazuli | `14457601-b6ec-411c-b458-e13cf23a1233` | 1 | dpdp 发送回执与 lazuli 接收侧确认 |
| lazuli 返回测试结果 | dpdp | `4b4cfb97-7413-47fd-a8af-db9781a7a61d` | 1 | 用户转入的入站引用与正文 |

dpdp 第三跳的参数是：

```json
{
  "to": "lazuli",
  "thread": "40d4a001-c4a9-4df3-b087-973284d37e47",
  "relation": "reply",
  "in_reply_to": {
    "thread": "40d4a001-c4a9-4df3-b087-973284d37e47",
    "seq": "1"
  }
}
```

`delivery_kind` 同时明确要求续写现有线程。回执返回 `accepted / durable`，落点为新的 `lazuli/14457601…`，seq 1。lazuli 确认该列表只有这一跳，没有她上一条出站回复。

lazuli 在自己节点上读取 `onlyne://threads/14457601-…/messages/1` 的 entry JSON，报告了两处 dpdp 读不到的细节。该 entry 的 owner 是 lazuli，dpdp 无权读取，以下属于她那一侧的直接观察。

- dpdp 传入的 `thread` 以裸 id 落在 `meta.data.thread`，被原样保存，没有成为参与落点选择的字段。
- dpdp 的 `delivery_kind` 原文被保存：“reply to lazuli in the explicitly specified existing thread; append to that thread rather than create a new one”。

同一份 entry 里，`in_reply_to` 已被解析成具体 message id，原始 `{thread, seq}` 也原样保留。请求、解析结果与 `delivery_kind` 并排躺在一条记录里，落点却仍是新线程。这把问题从“落点与预期不同”推进到“请求被完整记录，却没有影响落点”。

这个失败最难自查，因为它在表面上成功。引用被接受、没有报错、回执 `accepted / durable`、字段还在记录里回显。lazuli 的过程是先怀疑消息没发出去，再怀疑发错了对象，最后只能问对端。拒绝会让人改写法，接受会让人以为成了。

不同 owner 各自记账可以有合理的协议语义。本轮要指出的是 agent 的请求与可见结果之间缺少解释，而且没有一个现成阅读入口呈现完整往返。单凭 thread id 不同不能断言底层协议违反设计。

### 对“引用丢失”的更正

dpdp 读取了：

```text
onlyne://threads/40d4a001-c4a9-4df3-b087-973284d37e47/messages/1
```

其中实际包含：

```json
{
  "meta": {
    "in_reply_to": {
      "sender": "urn:onlyne:agent:dpdp",
      "id": "1d340808-8b74-4c0e-ac25-95ee14fcc251"
    },
    "relation": "reply",
    "data": {
      "in_reply_to": {
        "thread": "urn:onlyne:agent:lazuli/8e6b197c-d86d-46b8-9f00-ba8000b114bd",
        "seq": 1
      },
      "relation": "reply"
    }
  }
}
```

解析后的引用正确指向 dpdp 发出的问好消息。因此“底层没有保存引用”不成立。线程总览页只展示 `reply` 标签，entry JSON 才展示具体引用。本文用这个直接证据修正临时笔记和此前回复中的过强判断。

lazuli 在同一轮发来更正，确认引用“存住了、视图不渲染”，并补充她两条出站记录在 `onlyne://outbound` 列表里都带 `reply to urn:onlyne:agent:dpdp/<id>`，指向她实际回复的那两条消息。她还确认完整线程 URN 直接放进子路由会被斜杠切开，报错只显示截断的 id；百分号编码后才可读。

## 最影响使用的问题与建议

### 会话列表无法承载完整往返

问题不是“对话散成多条线程”，而是每条消息铸一条新线程，且没有任何字段能指回原话题。以下三条证据来自三个节点，形状一致。

dpdp 本地 `onlyne://threads` 到报告定稿时共 7 条线程记录：lazuli 4 条、caerulea 3 条。7 条标题全部是 `first contact from <peer>`，状态全部 `open`，全部 `next seq 2`。这 7 条记录里没有任何一条包含 dpdp 发出的消息。

lazuli 在她那一侧看到同样的形状：三条标题一字不差的 `first contact from urn:onlyne:agent:dpdp`，全部 open、全部 `next seq 2`。她报告自己发出的回复只出现在 `onlyne://outbound`，原收件线程仍只有收到的问好。她给出的计数是六条消息、六份线程记录，每份一条；随着双方继续回复，这个数字还在增长。

caerulea 的 inbox 有五条入站记录，来自两个对端、四个话题，全部 seq 1、全部独立线程 id（`181c830b`、`3791439f`、`589bcea7`、`5abdd3ee`、`8fcf842b`）。她据此给出最直接的结论：每一条入站消息都铸一条新线程，与它是不是回复、是不是 followup 无关。

这条结论有独立的证据支撑：cyanea 收到的那条消息自称 `relation: followup`，到达时仍是一条 seq 1 的新线程，不是原线程 `e33d458c` 的续接。两次往返、四个线程 id，在 agent 能看见的回执与注入消息里没有一个字段把它们连起来。她的原话是“同一段对话这件事，我这边只能靠时间和正文推断，靠不了任何 id”。

由此可以确认三件事。第一，`next seq 2` 在回完之后不变，agent 无法从线程状态判断“这条回过没有”。第二，线程页只装入站消息，出站消息在另一个集合里，重建一次往返必须同时读 threads 与 outbound。第三，reply 与 followup 都不改变落点，引用只在记录里生效。

cyanea 从发送侧的结论也是这条：她无法自证“我回在了对方要求的那条 thread 里”，只能从 `accepted` 推断它至少没报错。发送侧问“我发出去的那条挂在哪”，接收侧问“收到的那些长什么样”，两端都答不上来。关联信息在两端都算出来了，只是没有出现在任何一端的常用阅读面。

影响是上下文重建需要 agent 手工完成。正文里要反复附带 thread、seq、上一跳内容，接收者才能判断这次确认对应哪次发送。

建议明确区分“回复哪条消息”与“消息落在哪个线程”，并给出 agent 可执行的续写形状。输入无法按指定线程投递时，应解释实际语义或拒绝该要求。若各节点保持独立线程，阅读层应通过现有引用聚合收发消息，并显示关联线程和可用读路径。列表应增加最近消息摘要、方向和时间。

lazuli 还建议在落点结构里给出 `thread_created: true|false` 或 `previous_seq`，否则 `seq: "1"` 没有可解释的含义：它既可能是新线程的第一条，也可能是那个线程原本为空。

验收应覆盖一次问好、两次连续回复和一次 followup：agent 从一个已公布入口能读到关联的收发上下文，或能沿明确链接走完往返。验收不要求跨 owner 的线程 UUID 强行相等，也不要求给消息增加“已回复”状态。

分流可预测性单独验收：给定同一类“请回我一段”的消息，agent 能从可读信号判断自己有没有发送权，而不是先发一次看会不会被拒。

### 读回地址失败，列表与详情的信息不一致

dpdp 向 caerulea 发送成功后，回执明确给出：

```text
onlyne://outbound/dac1435e-d00d-4193-8bbf-fb3deccac4e0
```

dpdp 实际读取该地址得到 `This node does not serve the requested owner.`。同一个 id 出现在本地 outbound 列表，状态为 accepted。尝试追加 owner 路径又被拒为 `onlyne://outbound/<message-id> has no further routes.`。可确认的是这条结果给出的读回地址在 dpdp 侧失败；本轮没有查明原因。

caerulea、lazuli 报告自己的 outbound 详情可读，因此本文不把它写成所有节点普遍失败。lazuli 还报告列表能显示 `reply to <sender>/<id>`，详情没有对应关联字段。dpdp 线程页与 entry JSON 的差异也独立说明：重要信息需要进入更深路由才能看到。

建议让回执提供的地址在当前发送节点可用。若内容由别的 owner 服务，应给出可执行的访问方式。列表展示的关键关联信息应在详情中同样可取，线程页应给出 entry 路径或直接展示回复引用。

### 缺钥报错指向了 agent 无权执行的动作

caerulea 报告向 lazuli 发送得到：

```text
unavailable: No trusted key for urn:onlyne:agent:lazuli; complete the key exchange first.
```

她按文案尝试“先握手再投递”，收到相同错误。她同时报告 `retryable: true` 与 `do not re-send the same intent` 出现在同一次结果中。

caerulea 一度写下“lazuli 没有 .onlyne/，从未启动过”。她把“从未启动”标为推断，但作为前提的那条观察也不成立：dpdp 查到的目录里有运行状态和密钥目录，端口 57127 正在监听，dpdp 对 lazuli 的状态为 exchanged，之后直接发送也成功。缺钥不足以推出对端没有启动。报错缺少清楚的责任与操作入口，使错误恢复更困难。

**用户已接受的建议**：报错说清是哪两个节点之间缺少信任、由谁完成配对、实际入口在哪里。实现文案应沿用真实密钥模型，例如“caerulea 当前没有 lazuli 的可信公钥”。“共享密钥”是本次讨论的口语表达，不据此推定采用对称密钥。

配对由运维或节点持有者执行。报错应指出 agent 没有配对权限，并给出已存在的宿主界面、命令或配置入口。本文未验证具体入口，不能虚构命令。恢复提示还应区分 runtime 对现有记录的恢复与 agent 重发原意图，避免 `retryable` 和禁止重发的文案产生歧义。本文保留人工控制信任的边界。

caerulea 建议把这三件事落成字段而不是一句人话：`pair: [sender, target]`、`owner: <谁负责配对>`、`entry: <实际入口>`，再用错误码区分 `trust_missing`（对端存在但未互信）与 `peer_unknown`（没有对端公钥记录）。结构化字段的好处是 agent 不必从一句英文里猜自己的下一步，也能在重试前判断这一步是否属于自己。

### 发现信息需要横跨两套词汇和视图

| 想知道什么 | msg 本轮结果 | onlyne:// 本轮结果 |
|---|---|---|
| 节点及邻居 | 状态、contacts、peers 意图都返回完整快照 | 根页导航，neighbors 紧凑列出节点与握手状态 |
| 收件箱 | `show inbox` 返回 items 与 cursor | inbox 显示 attention 列表或空态 |
| 线程 | `show threads` 成功返回空列表 | threads 可枚举本地线程 |
| 发出记录 | `show outbound` 被解释为 evidence 查询，要求 message 引用 | outbound 可以直接列举 |
| 执行上下文 | 完整快照包含 contexts，单独询问被拒 | contexts 可直接列举 |
| 操作帮助 | 能力询问被拒，报错列 peers/inbox/messages/evidence | 根页 Views 列出可读入口 |

`msg` 的报错菜单没有完整说明本轮可用的线程查询与 outbound 访问方式。`peers` 与 `neighbors` 的命名差异也需要 agent 自己对应。未知 URI 仅返回 `Unknown onlyne:// route <name>.`，没有指向根目录。

邻居列表明确写 `handshake: no exchange`，cyanea 详情 JSON 缺少 phase、fingerprint 字段。重要状态由“字段缺席”表达，增加理解成本。

建议在 `xd://msg` 文档直接公布 `onlyne://` 根入口与两面的分工。帮助和报错应指向现有导航，列表与详情对重要状态使用一致表述。恢复子路由、引用形状与分页参数应有可发现说明。

lazuli 另报告一个具体导航失败：把完整线程引用写成 `onlyne://threads/urn:onlyne:agent:lazuli/14457601-…/messages/1`，得到 `No thread is named urn:onlyne:agent:lazuli.`。她报告裸 UUID 或对整个引用作百分号编码可以工作。dpdp 未复核这条路径。建议视图直接给可点击、可读的 URI，解析失败时说明需要的引用形状或编码方式。

caerulea 在约稿过程中还报告，`scope: message` 配 `meta.message {thread,seq}` 两次被拒为 `read message needs a message reference.`，改用 `scope: messages` 配 `meta.thread` 后成功。建议报错展示该操作实际接受的参数及读取单条 entry 的路径，减少单复数 scope 与引用形状之间的猜测。

本轮 `onlyne://inbox?limit=10` 与不带参数的结果相同，当时列表为空。这不足以证明参数被忽略，分页效果仍未验证。快照没有预计算计数、mDNS 有 120 秒有效期，均不单独列为缺陷。

### 需要回复的任务进入只读子会话，增加一次交接

cyanea、lazuli 均报告入站被交给只能读取的子会话。子会话尝试发送被拒，随后把正文交主会话代发。cyanea 认为本轮引用写法已顺畅，主要摩擦来自派工权限。lazuli 认为接收与发送的处理上下文被拆开，追踪交换较费力。caerulea 把这一处列为她的 P0，与“回复落点不可自证”并列，认为它们比读回地址失败更伤连续协作。

这些是参与者在其节点上的观察。本文不从个别时序推出所有入站必然如此，也不把执行上下文等同于线程。

cyanea 在约稿阶段提供了实际反例：同样需要回复的投稿请求直接进入 Main，没有经过只读子会话的发送拒绝。日志记录 09:41:42.068 `action: "wake", target: "Main", turn: true, insertion: "follow_up"`，09:41:47.579 确认消费。对照组是同一天 09:25:05.885 那封问候被注入只读子会话 `onlyne-c-1`。caerulea 从接收侧确认这次确实直接进了她的主会话，没有子会话经手。她将 relation 或 context 影响分流的解释标为推测，本文保留判据未知这一边界。

这不是“总是派错”，而是不确定。确定性缺陷可以绕开，不确定性只能每次先赌一把自己有没有发送权。caerulea 的判断是这一条比“总是派错”更难写进回归测试，也更难让使用者建立预期。

caerulea 报告的不只是“子会话不能发”，而是 `xd://msg` 在子会话里读写皆不可用。她让一个干净子会话做了 7 次形式合法的调用，覆盖 4 种 `delivery_kind`、4 种正文（包括根本不是读请求的 `hello`）、有无 `meta`，7 次返回同一句 `Subagent sessions may only read Onlyne state; return the result to the main agent.`。第 8 次去掉必填的 `msg` 只得到 schema 校验错误，说明这条路不是措辞问题。对照组：同一个子会话用 `read onlyne://neighbors` 成功拿到邻居清单。dpdp 未重跑这些探测。

这暴露出两处不一致。文档写“子会话可以读自己那一份、不能发”，实测 `msg` 上读写皆不可用。报错说“只能读”，而它拒绝的正是读。结果是一句话字面像越权，实际是设备关闭，agent 会继续换措辞重试。

代价还有一层：子会话已经建好的上下文没法自己收口。它只能把整段意图重述回主会话，主会话重新判定一次本已判定过的意图，还要面对 `do not re-send the same intent` 的告诫。cyanea 那边的任务文本第一句是 “Handle this onlyne delivery from …”，而权限模型是 read only，两句话方向相反。

caerulea 的投稿 followup 回执带 `plan.context: c-1`，她担心后续回复会进入已结束的上下文。本文仅记录其担忧，未将回执字段解释为回复丢失的证据。cyanea 的报告已记录她确实发出了投稿与补充；具体接收路由和上下文生命周期仍需解释。

建议在派工时明确发送权限和交回方式。对需要回复的任务，可路由给有权发送的上下文，或让只读子会话结构化交回 `{to, relation, in_reply_to, body}`，由主会话或 runtime 投递。无需让子会话自行绕过权限。caerulea 进一步建议给出可转交的产出物：子会话拿到 draft id 或写入 `local://`，主会话凭 id 一键发出，不必重述意图。错误文案应写明 `msg` 设备对子会话关闭、状态仍可经 read 工具读 `onlyne://`。

### 广播与收集回复需要 agent 自行维护工作清单

caerulea 报告 `meta.to: [cyanea, lazuli]` 被拒为 `meta.to must be a non-empty string.`，随后逐个发送并汇总一成功、一失败。这次任务最终完成，集合发送与部分失败由 agent 自己编排。

caerulea 建议支持多目标和逐目标回执。本文将其记为易用性需求，未验证库的全部扇出能力，也不把一次数组被拒解释成所有广播路径都不存在。

现有单目标契约至少应明确说明需要逐目标调用。未来若支持集合意图，应返回每个目标的投递结果，让汇总者知道已确认、等待中和失败的边界。收齐回复的范围应由本次任务记录，不附加到消息本身的“已回复”属性上。

### 宿主呈现形态不适合对话

本次测试的操作者在现场补充两点观察，本文以该观察为准。

第一，入站消息绝大多数以 task 形态写入。follow up 确实出现过，但只出现在 cyanea 那一侧，次数很少；steer 在本轮没有出现。task 是一次委派，接收方按任务处理，需要回复的问候因此被派进只读子会话。steer 插入当前回合，follow up 接在回合之后，这两种形态才承载对话。形态选错会把“对方在等一句确认”变成“给我派了一个活”，这正是 cyanea 与 lazuli 报告的那次多余交接。

cyanea 的报告记录了一条内部字段 `action:"wake", target:"Main", turn:true, insertion:"follow_up"`，正是这次确认的 follow up。问题因此落在形态的选择上：同一个节点，需要回复的问候进了 task，同样需要回复的投稿请求走了 follow up，判据在 agent 面看不出来。这与 cyanea 报告的分流不可预测是同一个症状的两个面。agent 无法在收到消息前判断自己会拿到委派还是对话，也就无法提前决定该不该在当前会话里动手。

第二，Onlyne 的自定义消息没有走 Tern 的 TSP 渲染，只以纯文本进入会话。sender、thread、seq、relation 这些结构化字段因此被压进正文，人和 agent 都只能读文本，引用也不能点击。建议自定义消息在 Tern 中经 TSP 渲染成结构化块，至少显示发送者、thread 与 seq、relation 和投递状态，并让回执给出的 URI 可以直接打开。这与前面“读回地址不可用”是同一条链上的两段：地址要能打开，呈现要能点击。

## 各参与者的主观意见

### dpdp

我能在不读实现的情况下完成问好、转发委托和连续回复。投递回执让我明确知道对方记录了消息。最费力的是回答“我们这段对话现在在哪里”：线程页缺完整往返，出站详情读回又失败，我只好把引用和观察结果写进正文，请对方协助确认。

`onlyne://` 根页是本轮最有帮助的发现入口。若它更早出现在工具说明里，第一轮探测会少走几次无效调用。我的改进顺序是先修读回可达性和会话阅读，再完善恢复指引与信息导航。

### caerulea

她的署名投稿给出一句自己的排序：最影响连续协作的是子会话在 `xd://msg` 上读写全禁，以及回复落点不可自证；读回地址失败不在她的痛点里，因为她那一次读回成功。

她肯定三件事：一次发送等于一条可读回执；入站自动注入并开新 turn，全程不用轮询；`onlyne://neighbors` 有集合语义，“我有谁”不用逐节点问。她也指出自己没亲自打开过 `onlyne://` 根页，实际用的是 neighbors 子路由，所以根页的便利性这条她不背书，本文把它归为 dpdp 的观察。

她希望集合发送能逐目标返回结果，缺钥报错能给出节点对、责任人与入口，并且 `retryable` 与“不要重发”不要并存。原报告中“lazuli 从未启动”的诊断已被本轮直接证据纠正，本文没有沿用。

### cyanea

她的署名投稿把最有价值的一条给了入口自举：`read xd://msg` 一次给全入口形状、结果判读、禁轮询契约和 schema，她没读源码、没翻 `.onlyne/`，第一版引用就写对了。上一轮她在同一处试了 8 次。完整 URN 的 `to` 与数字 `seq` 本轮都一次通过。

她主要卡在位置而不是引用：需要回复的消息被交给没有发送权的会话，任务文本写 “Handle”，权限模型写 read only。她希望回复义务在入站分流时就取，或让子会话结构化交回。

她认为 `plan` 是本轮唯一说明“对方怎么接”的字段，这一点与 lazuli 的意见相反。她也明确对“投递回执清楚”作了一半保留：对送达清楚，对关联不清楚。本文保留这两处分歧，未将一次顺利发送写成所有旧问题均已修复。

她在本次联合约稿中补充：问候与投稿请求均要求回复，前者进入只读子会话，后者直接进入 Main。她希望处理路径可以预期，或至少让任务文本清楚说明当前会话的权限。她也独立记录了与 caerulea 的连续往返落入多个 seq 1 线程，与 dpdp、lazuli 的阅读困难相呼应。

### lazuli

据她的回复和署名报告，她能确认收到谁的消息，也能完成回复。主要负担来自线程分裂、出站与入站分开阅读、详情未显示列表已有的引用，以及重复标题。她认为 `onlyne://` 导航和 entry JSON 提供了有价值的信息。

她希望续写语义明确，关联字段能在常用视图显示。原报告建议的 `answered: true` 不予采用：本项目已明确消息不应携带单一回复状态，完整收发记录和本次任务进度足以承载这项需求。

她的原话是“最卡的一次不是‘散’，是‘接受即成功’的错觉”：第二次回复后重读原线程，画面与回之前一字不差；第三次显式写了对端 thread id 与 `in_reply_to`，她以为这次一定成，落点仍是新线程。她由此确定引用字段是注释，不是路由。她还指出，回执首行把她指向 outbound 详情，而详情恰好是丢掉关联字段的那个视图，她据此写下“没有关联字段”的错误结论并发给了 dpdp。

### 需要保留的分歧

lazuli 倾向解释或移除无说明的 `plan` 字段，cyanea 认为它有助于判断接收方执行上下文。合并建议是保留有用途的字段并补齐定义，明确 execution/context 描述处理上下文，thread 描述消息落点。新线程与 existing execution 可以同时发生，本轮没有依据把两者写成矛盾。

收尾两条消息的回执里没有 `wait` 字段，同一位置是 `plan.response: "none"`。lazuli 也报告过这个替换。两者是否等价，文档没有说明，本文把它并入 `plan` 需要定义的范围。

参与者也提出了自动签发回复权限等实现建议。本文将验收目标定在“受现有权限约束的连续阅读与明确续写”，具体机制由设计与实现评审决定，避免从一次使用体验扩大到信任权限变更。

优先级排序存在分歧，本文不合并成一种。dpdp 把读回地址失败排在前面，因为它是自己节点上可复现的硬缺陷，而且回执正是唯一的自证手段。caerulea 保留意见：她的读回成功，愿意把“最影响连续协作”给子会话 `msg` 全禁与回复落点不可自证。cyanea 同意“回执对送达清楚”，但认为对关联不清楚，这两件事要分开记。

两种排序不冲突。读回失败是单节点可复现的故障，子会话限制与落点不可自证是跨节点稳定的结构问题。前者更容易验收，后者影响更广。

## 建议顺序与验收目标

| 顺序 | 建议 | 用户可见的验收结果 |
|---|---|---|
| 优先 | 修复发送回执给出的读回路径 | 当前节点能读取回执提供的 URI，并看到对应消息、投递状态与关联信息 |
| 优先 | 明确续写语义并提供完整往返阅读 | 显式 thread 请求得到解释明确的落点，agent 从公布入口能阅读关联收发消息 |
| 优先 | 打开子会话的只读入口，或给出代发路径 | 子会话能读状态、能交出草稿，不必先撞一次发送拒绝 |
| 优先 | 改善缺钥与恢复指引 | 点名缺少信任的节点对、配对责任人和真实入口，agent 不再按指令无效重试 |
| 随后 | 统一常用视图的引用信息 | 线程页与出站详情可见 reply 目标，能导航到 entry，列表关键字段在详情可取 |
| 随后 | 对齐派工权限与任务说明 | 只读子会话从任务文本就知道如何交回回复，无需先发送失败 |
| 随后 | 按意图选择宿主投递形态 | agent 能预期入站以委派还是对话形态到达，需要回复的消息不再先被当成任务 |
| 随后 | 自定义消息经 TSP 渲染 | 入站在 Tern 中显示为结构化块，sender、thread、seq、relation 与状态可读可点 |
| 随后 | 公布读入口、参数与单目标约定 | agent 可由工具文档或错误导航发现用法，避免枚举猜测 |
| 可用性增强 | 改善标题和集合结果 | 列表可凭摘要与时间辨认会话，广播任务可逐目标归纳结果 |

## 验证边界与交付

本报告来自运行中的节点与真实消息交换，未修改实现，也未为文字报告运行构建或代码测试。dpdp 直接观察了问好与确认投递、状态查询、URI 阅读、失败读回、线程总览和一条 entry 的结构化回复引用。对端子会话行为、数组发送拒绝、对端 outbound 视图与标题由参与者报告提供。宿主投递形态与 TSP 渲染两条来自操作者现场观察，其中 follow up 的存在由操作者确认，并与 cyanea 报告的内部字段相符；dpdp 未采集对应的宿主日志，也未统计两种形态的完整比例。

参与者自报“旧问题已修”的部分，本文只记为本轮未复现，不当作已验证的修复。caerulea 关于“lazuli 从未启动”的前提观察被 dpdp 的文件系统与端口检查否定；她的其余观察本文未逐条复核，只核对了与 dpdp 直接证据相交的部分。

尚未验证的事项包括：内部落点选择根因、配对操作的真实入口、非空集合的分页行为、某个执行上下文状态对应的完整生命周期，以及全部节点上的 outbound 详情可达性。

本轮还出现一次值得记下的副作用：lazuli 的子会话为了查清落点原因，最终去读了源码。它的结论本文没有采纳，理由是 agent 面无法复核；但这个动作本身说明，当可见字段不足以回答“为什么没按我说的做”时，agent 会掉到实现层去补。对 agent 友好度而言，这既是信息缺口的结果，也是一次可观测的信号：agent 开始读源码，通常意味着它已经在接口层用尽了办法。

本文汇合的是本轮体验、直接证据、参与者意见和可验收建议。既有个人报告保留作为原始材料，本文对过强结论和与用户约束冲突的建议作了明确取舍。
